Module 06 — Parser: Functions

Parsing complete function definitions and assembling a full program AST.

Prerequisites: 01 Source 02 Lexer 03 SymTab 04 AST 05 Parser Stmts

Section 01 — The Screenplay Analyst

In Module 05, our Script Analyst was reading individual scenes — statements and expressions inside a single function. Now she reads the whole screenplay.

A screenplay is made of multiple acts. Each act has:

  • A title — the function name
  • A cast list — the parameters
  • A sequence of scenes — the body statements

parse_program walks the whole screenplay, handing each act to parse_function. parse_function reads one act — the return type, the name, the cast list, and the body.

Section 02 — Grammar for Functions

program     = function*

function    = ('int' | 'void') IDENT '(' param_list ')' block

param_list  = ( type IDENT (',' type IDENT)* )?
            | 'void'                         /* zero-parameter marker */

type        = 'int' | 'void'

block       = '{' stmt* '}'

In plain English:

  • A program is zero or more function definitions, one after another.
  • A function starts with a return type (int or void), followed by the function name, then a parenthesised parameter list, then a block body.
  • A param_list is either empty, a single void (meaning no parameters — the C99 convention), or a comma-separated list of type name pairs.
  • Parameters are just variable declarations without initialisers. We reuse AST_VAR_DECL for them.
Note on void parameters: int f(void) and int f() both mean "zero parameters" in our language. We detect the (void) case by peeking: if current is void and next is ), we consume the void and set nargs = 0.

Section 03 — parse_function Implementation

/* parse_function: parse one function definition.
 * Returns an AST_FUNC node. */
Node *parse_function(Parser *p) {
    int line = p->current.line;

    /* Step 1 — Return type */
    char ret_type;
    if (check(p, TOK_KW_INT)) {
        ret_type = 'i';          /* 'i' = int return */
        advance(p);
    } else if (check(p, TOK_KW_VOID)) {
        ret_type = 'v';          /* 'v' = void return */
        advance(p);
    } else {
        error(...); ret_type = 'i';  /* recover */
    }

    /* Step 2 — Function name */
    Token name_tok = p->current;
    expect(p, TOK_IDENT, "function name");

    Node *func = node_new(AST_FUNC, line);
    func->sval = my_strndup(name_tok.start, name_tok.len); /* heap-copy */
    func->op   = ret_type;      /* store return type as char */

    /* Step 3 — Parameter list */
    expect(p, TOK_LPAREN, "'('");

    func->args  = malloc(cap * sizeof(Node *));
    func->nargs = 0;

    /* (void) means zero params */
    if (check(p, TOK_KW_VOID) && p->next.type == TOK_RPAREN) {
        advance(p);           /* consume 'void', nargs stays 0 */
    } else if (!check(p, TOK_RPAREN)) {
        do {
            int param_line = p->current.line;
            advance(p);       /* consume type keyword */
            Token pname = p->current;
            expect(p, TOK_IDENT, "parameter name");

            Node *param = node_new(AST_VAR_DECL, param_line);
            param->sval = my_strndup(pname.start, pname.len);
            param->left = NULL;  /* no initialiser */

            func->args[func->nargs++] = param;  /* append param */
        } while (match(p, TOK_COMMA));   /* loop on ',' */
    }

    expect(p, TOK_RPAREN, "')'");

    /* Step 4 — Body */
    func->right = parse_block(p);   /* brace-enclosed body */

    return func;
}

Key points:

  • The return type is encoded as a char in node->op — reusing an existing field.
  • Parameters are built as AST_VAR_DECL nodes with left = NULL.
  • We grow the args[] array dynamically with realloc when it fills up.
  • The do { ... } while (match(TOK_COMMA)) loop elegantly handles one-or-more parameters with separating commas.

Section 04 — parse_program: Looping Over Functions

Node *parse_program(Parser *p) {
    Node *prog = node_new(AST_PROGRAM, p->current.line);

    prog->args  = malloc(cap * sizeof(Node *));
    prog->nargs = 0;

    /* Keep parsing functions while we see a type keyword. */
    while (check(p, TOK_KW_INT) || check(p, TOK_KW_VOID)) {
        prog->args[prog->nargs++] = parse_function(p);
    }

    /* Warn if we stopped before EOF. */
    if (!check(p, TOK_EOF)) {
        fprintf(stderr, "warning: unexpected token at top level\n");
    }

    return prog;
}

The loop condition check(p, TOK_KW_INT) || check(p, TOK_KW_VOID) is the natural gate for a language where every top-level construct starts with a type keyword. When we reach EOF (or any unexpected token), the loop exits and we return the collected program node.

What happens at EOF? check(p, TOK_EOF) is false for both TOK_KW_INT and TOK_KW_VOID, so the loop naturally stops. We then check check(p, TOK_EOF) to decide whether to emit the "unexpected token" warning.

Section 05 — The Complete AST for sample.c

Running ./parser_func sample.c produces this AST (abbreviated for readability):

=== AST for 'sample.c' ===

PROGRAM (3 functions)
  FUNC 'add' ret='i' (2 params)
    VAR_DECL 'a'
    VAR_DECL 'b'
    body:
      BLOCK (1 stmts)
        RETURN
          BINARY '+'
            IDENT 'a'
            IDENT 'b'
  FUNC 'max' ret='i' (2 params)
    VAR_DECL 'a'
    VAR_DECL 'b'
    body:
      BLOCK (2 stmts)
        IF
          cond:
            BINARY '>'
              IDENT 'a'
              IDENT 'b'
          then:
            BLOCK (1 stmts)
              RETURN
                IDENT 'a'
        RETURN
          IDENT 'b'
  FUNC 'main' ret='i' (0 params)
    body:
      BLOCK (4 stmts)
        VAR_DECL 'x'
        VAR_DECL 'y'
        ASSIGN 'x'
          CALL 'add' (2 args)
            INT 3
            INT 4
        ASSIGN 'y'
          CALL 'max' (2 args)
            IDENT 'x'
            INT 10
        RETURN
          IDENT 'y'

Parsed 3 functions, had_error = 0

Walking through the tree:

  • The root is PROGRAM (3 functions) — three AST_FUNC children.
  • FUNC 'add' ret='i' (2 params) — name is add, returns int, has two params.
  • The params appear as VAR_DECL 'a' and VAR_DECL 'b' with no initialiser child.
  • body: introduces the AST_BLOCK node. Each statement is a direct child.
  • FUNC 'main' ret='i' (0 params) — the (void) parameter list was consumed as a zero-param marker.
  • CALL 'add' (2 args) — the call node lists both arguments as children.

Brain Exercise

Question: What happens if you write x = add(1, 2, 3); in the program — three arguments when add only takes two? Does the parser catch this?

Answer: No. The parser builds a CALL 'add' (3 args) node without complaint. The parser only knows about syntax — it doesn't know how many parameters add was defined with. Catching this mismatch requires semantic analysis, which looks up add in the function table and compares nargs. That's exactly what Module 07 implements.

The parser enforces grammar rules (commas between arguments, closing paren). The semantic analyser enforces meaning rules (right number of arguments, variables exist, types match).

Q & A

Why does my_strndup exist? Why not use the standard strndup?

strndup is a POSIX function, not part of the C11 standard. On Windows (MSVC, MinGW without glibc extensions) it may not be available. Writing my_strndup as a small wrapper around malloc + memcpy makes the code portable across platforms without needing feature-test macros or conditional compilation.

Why is the return type stored in node->op rather than a dedicated field?

The fat-node struct already has an op field used by AST_BINARY and AST_UNARY. An AST_FUNC node never uses op for an operator, so repurposing it for the return type avoids adding a new field to the struct. This is a pragmatic teaching-compiler shortcut. A production compiler would have a dedicated TypeKind ret_type field, or store a pointer to a type table entry.

What would break if two functions had the same name?

The parser would happily build two AST_FUNC nodes both with sval = "foo" and add them both to the program's args[]. The parser does not track names — it only builds the tree. Detecting duplicate function definitions is a semantic error, caught in Module 07 when we try to register "foo" in the function table for the second time.

Could a function return type be something other than int or void?

Not in our language, by design. The grammar only allows int or void as type keywords. If you extended the language with, say, char or pointer types, you would need to expand the type production and change the encoding — likely replacing the single op char with a proper TypeKind enum and a richer type-representation structure.

What's Next — Module 07: Semantic Analysis

The parser built the full tree without checking whether names exist or whether argument counts match. Module 07 — Semantic Analysis walks that tree and reports real programming errors:

  • Undefined variables (return z; when z was never declared)
  • Wrong argument count (add(1, 2, 3) when add takes two)
  • Redeclared variables in the same scope
  • Calls to undefined functions

Module 07 introduces the Sema struct with a scope stack (an array of SymTabs) and a two-pass strategy: first collect all function signatures, then walk each function body checking expressions and statements.
