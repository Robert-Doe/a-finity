Module 02 — Lexer / Tokeniser

Turning raw text into a stream of labelled tokens.

00 Before You Start

Prerequisites: Module 01 — Source & I/O  |  You should know: the Source struct, source_open, and source_free.
Must Know Before Continuing

You must be comfortable with the Source struct from Module 01: what text is (a heap buffer), what len is, and how source_open loads a file. The lexer will never copy text — every token is a pointer into that buffer, so the buffer must stay alive the whole time you use tokens.

You should also know how lexer_next is called: in a loop, one call per token, until you receive TOK_EOF. The lexer does not build a list of all tokens upfront — it produces them lazily, one at a time.

01 The Big Analogy — A Film Production Crew

Imagine a film production crew working from a screenplay. Before anyone can direct or act, the Script Supervisor walks through the script with coloured adhesive tabs, marking each chunk of text with its category.

Head First Moment

The Script Supervisor walks through the screenplay with coloured tabs, marking every scene heading (INT. COFFEE SHOP — DAY), every character name (ALICE), every action direction separately. She does not analyse the story — she just labels every chunk. Your Lexer is that Script Supervisor.

The screenplay is your Source. The tabs are your Token structs. The supervisor herself is the Lexer.

Here is the analogy applied to real C code. The input return a + 3; is seven characters of raw text. The lexer walks through it left to right and produces one token per logical unit:

Raw text Token produced return → TOK_KW_RETURN   "return" a → TOK_IDENT       "a" + → TOK_PLUS        "+" 3 → TOK_INT_LIT     "3" (ival=3) ; → TOK_SEMICOLON   ";"

Whitespace between the tokens is silently discarded. The lexer does not know or care that return a + 3; is a return statement — that is the parser's job (Module 04). The lexer only asks: "What is the next chunk, and what category does it belong to?"

02 What Is a Token?

A Token is a small struct that records everything the rest of the compiler needs to know about one lexical unit:

typedef struct {
    TokenType   type;   /* which category: KW_RETURN, IDENT, PLUS … */
    const char *start;  /* pointer into Source.text — NOT null-terminated */
    size_t      len;    /* how many bytes the lexeme occupies             */
    int         line;   /* 1-based source line where the token starts     */
    int         col;    /* 1-based source column where the token starts   */
    long        ival;   /* parsed value — only valid for TOK_INT_LIT      */
} Token;
FieldMeaning
typeWhich of the 32 token kinds this is.
startPoints at the first byte of the lexeme inside Source.text. Do not free it — the Source owns the memory.
lenNumber of bytes in the lexeme. Together with start this gives you the text: printf("%.*s", (int)tok.len, tok.start).
line / col1-based location for error messages: error at 3:12 means line 3, column 12.
ivalPre-parsed integer value so the parser never needs to call strtol itself. Only meaningful when type == TOK_INT_LIT.

Why a pointer-and-length instead of a copied string?

If we called strdup on every lexeme we would do thousands of small heap allocations per source file. Each allocation has overhead (the allocator must track the block size) and costs cache misses. By storing a pointer into the already-loaded Source buffer we do zero allocations per token and all the lexeme data is already in cache.

Here is what a real Token looks like when printed:

/* for the lexeme "result" at line 8, column 5 */
Token tok;
tok.type  = TOK_IDENT;
tok.start = &src.text[91];   /* points into the source buffer */
tok.len   = 6;
tok.line  = 8;
tok.col   = 5;
tok.ival  = 0;               /* not a number — ignored */

printf("[%d:%d] %s \"%.*s\"\n",
       tok.line, tok.col,
       token_type_name(tok.type),
       (int)tok.len, tok.start);
/* prints: [8:5] IDENT "result" */

03 The Lexer Struct and Scanning Loop

typedef struct {
    const Source *src;  /* the buffer being scanned — not owned by Lexer */
    size_t        pos;  /* byte index of the NEXT character to consume   */
    int           line; /* current 1-based line number                   */
    int           col;  /* current 1-based column number                 */
} Lexer;

The Lexer is purely a scanning cursor. It does not own the source text — it only holds a pointer to it. The four fields are all the state needed to know where we are and what to report in error messages.

Initialisation

void lexer_init(Lexer *lex, const Source *src)
{
    lex->src  = src;  /* attach to the source buffer */
    lex->pos  = 0;    /* start at byte 0 */
    lex->line = 1;    /* editors number lines from 1 */
    lex->col  = 1;    /* columns also start at 1     */
}

Canonical usage loop

Lexer lex;
lexer_init(&lex, &src);

Token tok;
do {
    tok = lexer_next(&lex);
    /* use tok here — print it, feed it to the parser, etc. */
} while (tok.type != TOK_EOF);

Each call to lexer_next advances pos past the lexeme that was returned. The loop stops after consuming the TOK_EOF sentinel (which is safe to print, pass to the parser, etc.).

04 Handling Two-Character Operators

Many operators share a first character: = begins both = (assignment) and == (equality). The lexer uses one character of lookahead — it reads one character ahead without consuming it — to decide which token to produce.

The Greedy (Maximal Munch) Rule

Always match the longest possible token. When you see = and the next character is also =, produce == (two characters), not = then = (two separate tokens).

Here is the actual code from lexer.c for the = / == case:

case '=':
    if (peek(lex) == '=') {   /* next char is also '=' → this is == */
        advance(lex);          /* consume the second '='              */
        tok.type = TOK_EQ;
        tok.len  = 2;
    } else {
        tok.type = TOK_ASSIGN; /* next char is something else → plain = */
    }
    break;

The pattern is:

  1. Consume the first character unconditionally (it is already consumed by the outer advance call at the top of the switch).
  2. Call peek(lex) to look at the next character without consuming it.
  3. If the lookahead matches, consume it with advance and emit the two-character token.
  4. Otherwise emit the one-character token — the lookahead character remains for the next call.

The same pattern handles !=, <=, >=, &&, and ||.

05 Skipping Whitespace and Comments

Before every call to the main scanning code, the lexer discards any whitespace and comments through a single helper:

static void skip_whitespace_and_comments(Lexer *lex)
{
    for (;;) {
        /* skip spaces, tabs, newlines — advance() updates line/col */
        while (isspace((unsigned char)peek(lex))) {
            advance(lex);
        }

        /* // line comment: read to end of line */
        if (peek(lex) == '/' && peek_next(lex) == '/') {
            advance(lex); advance(lex);           /* skip "//"        */
            while (peek(lex) != '\n' && peek(lex) != '\0')
                advance(lex);                     /* skip comment body */
            continue;                             /* loop to skip '\n' */
        }

        /* /* block comment: read to closing star-slash */
        if (peek(lex) == '/' && peek_next(lex) == '*') {
            advance(lex); advance(lex);           /* skip "/*"         */
            while (!(peek(lex) == '*' && peek_next(lex) == '/')
                   && peek(lex) != '\0')
                advance(lex);
            if (peek(lex) == '*') {
                advance(lex); advance(lex);       /* skip "*/"         */
            }
            continue;
        }

        break; /* nothing left to skip */
    }
}

Why handle comments here and not in a preprocessor?

A real C compiler has a preprocessor phase that handles #include, #define, and conditional compilation before the lexer runs. In our compiler we have none of those features, so a separate preprocessor pass would add complexity for no benefit. Stripping comments inside the lexer is simpler and keeps the architecture flat.

07 Brain Exercise

Scenario

Your lexer sees the input ===. What tokens does it produce, in order?

Show answer

Two tokens:

  1. TOK_EQ — the lexer greedily consumes the first two characters ==.
  2. TOK_ASSIGN — the remaining = is consumed as a plain assignment.

The greedy (maximal munch) rule says: always match the longest possible token first. So == is consumed as a unit, then = is consumed separately. You do not get three tokens.

08 There Are No Dumb Questions

Q: Why not just split the source on spaces to get tokens?

Because operators are not surrounded by spaces in real code. The expression a+b has no spaces, and result==7 has no spaces around ==. A space-split would give you "a+b" as a single chunk instead of three tokens IDENT PLUS IDENT. The lexer must understand character-level boundaries.

Q: Why store a pointer into Source.text instead of copying the token text into a new string?

Zero heap allocation. A typical file produces thousands of tokens. Copying each lexeme would require a malloc, a memcpy, and eventually a free for every single token. By storing a pointer-plus-length we reuse the buffer that is already in memory. The cost is a hidden lifetime dependency: if you call source_free while tokens are still alive, their start pointers dangle.

Q: Why does TOK_ERROR exist? Why not just call exit()?

Calling exit() on the first bad character means the user has to fix one mistake, recompile, find the next mistake, and repeat. By returning TOK_ERROR the lexer lets the parser skip the bad token and continue scanning, potentially reporting several independent errors in a single compilation run. The parser decides whether to abort or to try recovering.

Q: Can the lexer handle string literals like "hello"?

Not yet. The current token set has no TOK_STRING_LIT. Handling strings requires scanning from the opening " to the closing " while processing escape sequences like \n. That is a Module 02 extension challenge: add TOK_STRING_LIT to the enum and handle it in lexer_next.
