# Module 02 — Design Decisions

## 1. Hand-written lexer vs. generated (flex / re2c)

**Decision:** The Module 02 lexer is written by hand as a simple state machine rather than using a lexer generator such as flex or re2c.

**Why:** At this stage of the course the goal is to understand what a lexer *does*, not to operate tooling that hides the mechanism. A hand-written scanner maps directly to the concepts taught in class — character-by-character advance, lookahead, the keyword table — so students can read every line and trace execution. A flex specification compiles to a dense DFA table that is correct but opaque.

**Trade-off:** The hand-written approach does an O(n) linear scan of the keyword table for every identifier token. In production compilers (GCC, Clang) keywords are stored in a hash table so lookup is O(1). When this compiler grows to several hundred keywords, the linear scan should be replaced with a perfect-hash table generated by `gperf`.

---

## 2. Storing `start` pointer into Source.text vs. copying token text

**Decision:** The `Token.start` field is a raw pointer into the `Source.text` buffer rather than a separately heap-allocated copy of the lexeme.

**Why:** Copying every lexeme would require a `malloc` and a `free` for each token. A typical source file produces thousands of tokens, so per-token allocation would fragment the heap and slow down scanning noticeably. Pointer-plus-length (the "slice" pattern) avoids all allocation while still giving the parser access to the raw text. The `Source` buffer is loaded once and kept alive for the entire compilation, so the pointers remain valid.

**Trade-off:** The aliasing creates a hidden lifetime dependency: every Token is silently invalidated if `source_free` is called while tokens are still in use. A production compiler would use an arena allocator (a contiguous slab from which strings are bump-allocated) so the lifetime is explicit and string data can be interned for fast equality checks.

---

## 3. Reporting errors as TOK_ERROR tokens vs. calling exit()

**Decision:** Unrecognised characters produce a `TOK_ERROR` token; the lexer does not call `exit()` or `abort()`.

**Why:** A compiler that stops at the first error forces the user to fix one mistake, recompile, discover the next mistake, and repeat. Reporting as many errors as possible in one pass is much friendlier. Returning `TOK_ERROR` lets the parser skip the bad token and continue parsing, so a single compilation run can surface several independent problems.

**Trade-off:** A lenient lexer can allow the parser to enter confused states and generate spurious secondary errors — diagnostics that do not correspond to real bugs in the source. Production compilers implement "error synchronisation" (e.g., advance to the next semicolon or closing brace) to suppress cascading noise.

---

## 4. Tracking line/col in the Lexer struct vs. a separate location table

**Decision:** The current line number and column number are stored directly in the `Lexer` struct and updated character by character as the scan progresses.

**Why:** It is the simplest approach that produces correct `line`/`col` fields in every Token without an extra data structure. At Module 02 we do not yet need random access to source locations — we only ever process tokens in order.

**Trade-off:** Once the source has been fully scanned the `Lexer` struct records only the final position. If the parser later needs to re-derive the location of an arbitrary byte offset (e.g., to format a diagnostic pointing at a closing brace found deep in a token buffer), it cannot do so without re-scanning. Production compilers build a line-offset table (an array of byte offsets where each line begins) during the initial scan so that any offset can be binary-searched back to a line/col pair in O(log n).

---

## 5. Handling comments in the lexer vs. a preprocessor pass

**Decision:** C-style `//` and `/* */` comments are silently consumed inside `skip_whitespace_and_comments`, which runs before each call to `lexer_next`.

**Why:** Adding a separate preprocessor phase would require a second pass over the source buffer and a second I/O or copy step. At Module 02 we have no macro expansion, no `#include`, and no conditional compilation, so every preprocessor feature except comment stripping is unnecessary. Handling comments inline keeps the architecture flat and easier to understand.

**Trade-off:** This design makes it impossible to write a tool (like a documentation generator) that needs access to comment text, because the lexer discards it entirely. A production-grade compiler separates the preprocessor so that IDE tools can query comments, pragma annotations, and source ranges independently of the tokeniser.
