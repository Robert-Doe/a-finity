Parser — Statements

Turning a flat stream of tokens into a tree of meaning:
if, while, return, blocks, declarations, and full programs.

1. Before You Start

In Module 04 you built a parser that handles expressions: things like a + b * 2 or foo(x, y). Expressions are the building blocks, but a real C program is made of statements — instructions that do something: declare a variable, loop while a condition holds, return from a function.

By the end of this module your parser will turn this source code:

int add(int a, int b) {
    return a + b;
}

int main(void) {
    int x;
    int y;
    x = 10;
    y = 0;
    while (x > 0) {
        y = y + x;
        x = x - 1;
    }
    if (y > 40) {
        return y;
    } else {
        return 0;
    }
}

…into a structured tree that every later compiler pass can walk programmatically — no more scanning characters, no more guessing.

What you need
Completion of Modules 01–04. You should already understand what an AST node is, how node_new / node_print / node_free work, and how the lexer produces tokens.

2. The Big Analogy — The Story Analyst

Imagine a film crew. The lexer was the Script Reader who stamped each page of the screenplay with a label: "DIALOGUE", "ACTION", "SCENE HEADING". That is Module 02.

Now meet the Story Analyst. She takes those labelled pages and draws a map:

"Act 1 contains Scene 1 (which has three beats) and Scene 2 (which has two beats, plus a flashback). Scene 1 Beat 2 is a conversation inside a car inside Act 1 Scene 1."

That map is the Abstract Syntax Tree. The Story Analyst does not care about the exact words — she cares about structure: what is inside what, what comes before what, what is optional.

The grammar rules in parser.c are that analyst's checklist: "every scene must have a heading; every function must have a body; every if must have a condition in parentheses." If a page arrives out of order, she calls out the error immediately.

3. The Parser Struct and Two-Token Lookahead

Here is the struct at the heart of this module:

typedef struct {
    Lexer  lex;   /* the underlying lexer */
    Token  cur;   /* the token we are looking at right now */
    Token  peek;  /* the token ONE step ahead */
} Parser;

Why two tokens?

Consider this line inside a function body:

x = 10;

The first token is IDENT "x". Is this an expression statement (like x;) or an assignment? We need to see the second token (=) before we can decide.

With peek we can look without consuming:

if (check(p, TOK_IDENT) && p->peek.type == TOK_ASSIGN) {
    /* it is an assignment */
}

Without peek we would have to consume the identifier, discover the =, then somehow "put back" the identifier — a painful concept called backtracking. Two tokens avoids all of that.

Initialisation

void parser_init(Parser *p, Lexer *lex) {
    p->lex  = *lex;            /* copy the lexer */
    p->cur  = lexer_next(&p->lex);   /* first token */
    p->peek = lexer_next(&p->lex);   /* second token */
}

After this call, cur is the first token in the file and peek is the second. Every call to advance() shifts peek into cur and fetches a fresh token from the lexer into peek.

4. Parsing Statements One by One

The central dispatcher is parse_stmt. Think of it as a switchboard operator: it looks at the first token and routes the call to the right sub-parser.

Node *parse_stmt(Parser *p) {
    if (check(p, TOK_LBRACE))    return parse_block(p);
    if (check(p, TOK_KW_IF))     /* ... if statement ... */
    if (check(p, TOK_KW_WHILE))  /* ... while loop   ... */
    if (check(p, TOK_KW_RETURN)) /* ... return stmt  ... */
    if (check(p, TOK_KW_INT))    /* ... var decl     ... */
    /* default: expression statement */
}

Blocks — { stmt* }

A block is just a list of statements wrapped in curly braces. We grow a dynamic array using realloc:

Node *parse_block(Parser *p) {
    expect(p, TOK_LBRACE, "'{'");
    Node *block  = node_new(AST_BLOCK, line);
    block->args  = NULL;
    block->nargs = 0;

    while (!check(p, TOK_RBRACE) && !check(p, TOK_EOF)) {
        Node *stmt = parse_stmt(p);   /* parse one statement */
        /* append stmt to block->args[] via realloc */
        block->args = realloc(block->args,
                              (block->nargs + 1) * sizeof(Node *));
        block->args[block->nargs++] = stmt;
    }

    expect(p, TOK_RBRACE, "'}'");
    return block;
}

if statements

/* Grammar: "if" "(" expr ")" stmt ("else" stmt)? */
int line = p->cur.line;
advance(p);                            /* consume "if"   */
expect(p, TOK_LPAREN, "'('");
Node *cond = parse_expr(p);
expect(p, TOK_RPAREN, "')'");
Node *then_branch = parse_stmt(p);

Node *else_branch = NULL;
if (match(p, TOK_KW_ELSE)) {          /* optional else  */
    else_branch = parse_stmt(p);
}

Node *n  = node_new(AST_IF, line);
n->left  = cond;
n->right = then_branch;
n->extra = else_branch;               /* NULL if no else */

Notice n->extra — the third child pointer in every Node. For AST_IF it carries the optional else branch, so we do not need a fourth pointer field or a separate struct.

while loops

/* Grammar: "while" "(" expr ")" stmt */
advance(p);                /* consume "while" */
expect(p, TOK_LPAREN, "'('");
Node *cond = parse_expr(p);
expect(p, TOK_RPAREN, "')'");
Node *body = parse_stmt(p);

Node *n  = node_new(AST_WHILE, line);
n->left  = cond;
n->right = body;

return statements

/* Grammar: "return" expr ";" */
advance(p);             /* consume "return" */
Node *n  = node_new(AST_RETURN, line);
n->left  = parse_expr(p);
expect(p, TOK_SEMICOLON, "';'");

Variable declarations

/* Grammar: "int" IDENT ("=" expr)? ";" */
advance(p);             /* consume "int" */
char *name = my_strndup(p->cur.start, p->cur.len);
advance(p);             /* consume the identifier */

Node *decl = node_new(AST_VAR_DECL, line);
decl->sval = name;

if (match(p, TOK_ASSIGN)) {
    decl->left = parse_expr(p);    /* optional initialiser */
}
expect(p, TOK_SEMICOLON, "';'");

Expression statements

When none of the keywords match, the statement must be an expression followed by a semicolon — the catch-all default:

Node *expr = parse_expr(p);
expect(p, TOK_SEMICOLON, "';' after expression");
Node *es   = node_new(AST_EXPR_STMT, line);
es->left   = expr;

5. Expression Parsing with Precedence

Expressions were covered in Module 04, but Module 05 adds assignment at the top of the precedence hierarchy. Here is the complete table:

LevelOperator(s)AssociativityFunction
1 (lowest)=Rightparse_expr
2&& ||Leftparse_logical
3== != < > <= >=Leftparse_comparison
4+ -Leftparse_additive
5* / %Leftparse_multiplicative
6- ! (prefix)Rightparse_unary
7 (highest)literals, idents, calls, (…)—parse_primary

The rule: lower-precedence functions call higher-precedence functions. parse_expr calls parse_logical, which calls parse_comparison, and so on down to parse_primary. The deepest function runs first, so its operators bind tightest.

How assignment is right-associative

Assignment is right-recursive: parse_expr calls itself for the right-hand side:

if (check(p, TOK_IDENT) && p->peek.type == TOK_ASSIGN) {
    char *name = my_strndup(p->cur.start, p->cur.len);
    advance(p);  /* consume ident */
    advance(p);  /* consume '='   */
    Node *rhs   = parse_expr(p);   /* <-- calls itself! */
    /* ... */
}

That means a = b = 5 parses as a = (b = 5) (right-to-left), which is what C specifies.

7. Brain Exercise — No-Brace if

Think About It

C allows an if with no braces around its body:

if (x) return 5;

Question: does the parser in this module handle this correctly? What AST does it produce? Then ask: what happens with the famous "dangling else" problem?

if (a)
    if (b)
        return 1;
    else
        return 2;

Which if does the else belong to? Trace through parse_stmt by hand and see what the code decides.

Answer:

For if (x) return 5; the parser calls parse_stmt after the condition. parse_stmt does not require { — it handles any statement, including return. So the AST is:

IF cond: IDENT 'x' then: RETURN INT 5

For the dangling else, our parser's match(p, TOK_KW_ELSE) call appears immediately after parsing the inner parse_stmt. Because the inner if returns and then immediately tries to match else, the else attaches to the inner if. This is the standard C rule ("else goes with the nearest if") and our recursive descent implements it naturally — no special handling required.

8. Q&A

Why doesn't parse_stmt check for the closing '}' itself?

parse_stmt parses one statement. The closing } ends a block, not a statement. It is parse_block's job to watch for } and stop the loop. If parse_stmt consumed the }, then parse_block would never see it and would loop forever.

This separation of concerns keeps each function responsible for exactly one grammar rule, making the code much easier to read and debug.

Why does parse_expr call itself recursively for the assignment RHS?

We want a = b = 5 to mean a = (b = 5) — right-to-left. Right-recursion achieves this: when we see a =, we call parse_expr again for the RHS. That call sees b =, and calls parse_expr again for the RHS of that, which eventually returns 5. The inner assignment (b = 5) completes first, then the outer one (a = …). That is right-associativity by construction.

If we used a while-loop like the other operators, we would get left-associativity: (a = b) = 5, which is invalid C because you can't assign to the result of an assignment.

What happens if I write a function that returns void?

This module only handles int-returning functions. parse_func calls expect(p, TOK_KW_INT, "'int'") as its first action. If it sees void instead, it will print a parse error and exit. Support for void return types would be added in a later module once the type system is introduced.

void inside the parameter list (as in int main(void)) is handled: the parser detects the single token void and produces a function with zero parameters.

Could I write "int x = 5;" as a declaration with initialiser?

Yes! parse_stmt handles this in the variable-declaration branch:

if (match(p, TOK_ASSIGN)) {
    decl->left = parse_expr(p);    /* parse the initialiser */
}

The optional = expr is parsed if the token after the identifier is =. The resulting AST_VAR_DECL node will have left pointing to the initialiser expression, rather than NULL for an uninitialised declaration like int x;.
