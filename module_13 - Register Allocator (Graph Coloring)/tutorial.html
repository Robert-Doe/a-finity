Section 01

The Analogy: Prop Master

A film has limited backstage space. The Prop Master decides which props stay backstage (within arm's reach, ready to grab) and which go to the warehouse (a long trip every time you need them).

The Prop Master's Rules
  • Backstage slots = hardware registers (rbx, r12–r15, r10). Fast to access — zero extra instructions.
  • Warehouse = the stack ([rbp-8], [rbp-16], …). Every access costs a memory load or store.
  • Props = IR temporaries (t0, t1, t2, …). Each one needs to live somewhere.

Two scenes might need the same prop simultaneously. If scene A needs the golden sword during frames 10–50 and scene B also needs it during frames 30–70, you cannot keep only one copy backstage and share it — there is a conflict. That conflict is called an interference.

The Prop Master's job: assign each prop to a backstage slot, resolving interferences by sending one of the conflicting props to the warehouse. In compiler terms: assign each temporary to a register, and spill the ones that cannot fit.

Why Does It Matter?

A register access is a single CPU cycle. A stack load or store (even in L1 cache) is 4–5 cycles. A function that makes heavy use of temporaries can run 3–5× faster with good register allocation versus naïve "everything on the stack" codegen.

Section 02

What Is Register Allocation? Why Does It Matter?

Up through Module 12, every IR temporary maps directly to a stack slot. The code generator emits something like:

; Without register allocation (Module 12 style)
mov     rax, qword [rbp-8]   ; load t0
mov     rcx, qword [rbp-16]  ; load t1
imul    rax, rcx
mov     qword [rbp-24], rax  ; store t2

With register allocation, if t0 is assigned to r12 and t1 is assigned to r13, the same computation becomes:

; With register allocation (Module 13)
imul    r12, r13              ; t2 = t0 * t1, all in registers

Two instructions become one. The memory traffic disappears entirely.

Register allocation is an NP-complete problem in the general case (it is equivalent to graph coloring). Compilers use heuristics — greedy coloring, linear scan, or more sophisticated algorithms — to find good-enough solutions quickly.

Our allocator uses six registers: rbx, r12, r13, r14, r15 (callee-saved) and r10 (caller-saved scratch). We deliberately avoid the argument registers and rax/rcx/rdx because they carry ABI roles that would complicate the emit logic.

Section 03

Live Ranges and Interference

Before we can color anything, we need to know when each temporary is alive.

Definition: Live Range

The live range of temporary t is the closed interval [first_def, last_use] where first_def is the instruction index where t is first written, and last_use is the last instruction index where t is read.

Consider a simple 3-temporary example:

; Instruction index → what happens
0:  t0 = 4             ; first_def[t0]=0
1:  t1 = 7             ; first_def[t1]=1
2:  t2 = t0 * t1       ; last_use[t0]=2, last_use[t1]=2, first_def[t2]=2
3:  t0 = t2 + 1        ; last_use[t2]=3, last_use[t0] updated=3 (def+use)
4:  return t0          ; last_use[t0]=4

Live range table:

Tempfirst_deflast_useLive during instructions
t0040 – 4 (whole function)
t1121 – 2
t2232 – 3
Definition: Interference

Two temporaries interfere if their live ranges overlap. Ranges [a,b] and [c,d] overlap iff a ≤ d AND c ≤ b. Interfering temporaries cannot share the same register.

Interference check for our example:

t0 [0–4] vs t2 [2–3]0≤3 AND 2≤4 → yesYES
t1 [1–2] vs t2 [2–3]1≤3 AND 2≤2 → yesYES

Section 04

Greedy Graph Coloring

We have 6 colors (registers) and a graph of temporaries connected by interference edges. The goal: assign a color (register) to each node so that no two adjacent nodes share a color. If a node cannot be colored, it is spilled to the stack.

Our algorithm — greedy coloring in temp-number order — works as follows:

  1. Build live ranges — scan every instruction, record first_def[t] and last_use[t] for each temporary t. (Done in compute_live_ranges() in regalloc.c.)
  2. Process temps in order — iterate t = 0, 1, 2, …. For each temp that has been defined (first_def[t] ≥ 0), collect the set of colors already used by interfering, already-colored temps.
  3. Assign the lowest free color — scan colors 0 … NUM_REGS-1. Pick the first one not in the "used" set. Assign it to t.
  4. Spill if no color is free — if all 6 registers are claimed by interfering temps, assign t a stack slot at [rbp - N] and increment the spill counter.

Stepping through our 3-temp example with 2 available colors (for illustration):

StepTempColors used by interfering neighbors already coloredAssignment
1t0none yetcolor 0 → rbx
2t1t0 interferes → color 0 is takencolor 1 → r12
3t2t0 interferes → color 0 taken; t1 interferes → color 1 takenSPILL → [rbp-8]

With our full 6-register pool, t2 would get color 2 → r13 instead of spilling. The example above uses a 2-register limit only to illustrate what a spill looks like.

In the Real dot() Function

The dot function in sample.c has 4 parameters and a handful of temporaries for the multiply-and-add. With 6 allocatable registers, every temp fits — zero spills. The generated assembly uses rbx, r12, r13, r14 directly, with no stack traffic for temporaries.

The emitted assembly for dot looks like this (notice: no [rbp-N] for temporaries):

global dot
dot:
    push    rbp
    mov     rbp, rsp
    push    rbx          ; callee-saved registers used by regmap
    push    r12
    push    r13
    push    r14
    sub     rsp, 32       ; room for 4 local param slots
    mov     qword [rbp-8],  rdi  ; save param a
    mov     qword [rbp-16], rsi  ; save param b
    mov     qword [rbp-24], rdx  ; save param c
    mov     qword [rbp-32], rcx  ; save param d
    mov     rax, qword [rbp-8]   ; load a → rax
    mov     rbx, rax             ; t0 = a  (rbx)
    mov     rax, qword [rbp-24]  ; load c → rax
    mov     r12, rax             ; t2 = c  (r12)
    mov     rax, rbx             ; a*c
    mov     rcx, r12
    imul    rax, rcx
    mov     r13, rax             ; t4 = a*c (r13)
    ; ... b*d similarly into r14 ...
    add     r13, r14             ; t6 = a*c + b*d
    mov     rax, r13             ; return value
    jmp     .dot_epilogue
.dot_epilogue:
    add     rsp, 32
    pop     r14
    pop     r13
    pop     r12
    pop     rbx
    pop     rbp
    ret

Section 06

Brain Exercise

🧠

One Register, Two Contestants

t0 is live from instruction 0 to 5. t1 is live from instruction 3 to 8. We have exactly 1 allocatable register.

Question: Do t0 and t1 interfere? Which one gets the register, and which one spills?

Reveal the Answer

Do they interfere? Check overlap: 0 ≤ 8 AND 3 ≤ 5 — both true. Their ranges overlap during instructions 3–5. Yes, they interfere.

Who gets the register? Our greedy allocator processes temps in ascending order. t0 is processed first (lower temp number = lower first_def). At that point no interfering neighbor has been colored yet, so t0 picks up the only register — say rbx.

Who spills? When t1 is processed, t0 is already colored and interferes with t1, so color 0 (rbx) is off-limits. With only 1 register available, all colors are taken. t1 is spilled to [rbp-8]. Every instruction that reads or writes t1 will get an extra mov to/from the stack slot.

Section 07

Q & A

Q: What does it mean for a temporary to be "spilled"?
Spilling means the register allocator could not find a free register for a temporary — all available registers were already occupied by interfering (simultaneously live) temporaries. The spilled temp is assigned a stack slot instead. The code generator then emits a mov rax, [rbp-N] before every use and a mov [rbp-N], rax after every definition of that temp. The program is still correct, but slower because of the extra memory traffic.
Q: Why do we use callee-saved registers (rbx, r12–r15) rather than caller-saved ones (rax, rcx, rdx)?
Callee-saved registers survive across function calls — the callee is required to preserve them. This means if we allocate t0 to rbx in the middle of a function that itself calls dot or clamp, the value of t0 will still be in rbx after the nested call returns. Caller-saved registers like rax, rcx, rdx are freely clobbered by any callee. Using them for temporaries would require spilling them to the stack before every IR_CALL and reloading afterward — essentially doubling the spill complexity. By using callee-saved registers, we pay the cost once (push/pop in prologue/epilogue) rather than at every call site.
Q: Is live-range analysis the same as full dataflow analysis?
No — live-range analysis as we implement it is a simplification. We compute a single interval [first_def, last_use] per temporary, which is exact for straight-line code and SSA-style temporaries (each temp written once). Full liveness dataflow (iterative gen/kill sets, backward fixed-point) handles loops and branches correctly — a variable may be live at a point even though its last use is elsewhere in a loop. For our IR, which uses explicit temporaries rather than reusing variable names across basic blocks, the interval approximation is precise enough and much simpler to implement and explain.
Q: Could we do better than greedy coloring?
Yes. Chaitin's original graph-coloring allocator (1982) builds a full interference graph, repeatedly removes nodes of degree less than K (where K is the number of registers), and produces an optimal coloring order. It handles spilling more intelligently by choosing which temp to spill based on usage frequency rather than temp-number order. Linear scan allocation (Poletto & Sarkar 1999, used by early LLVM and JVMs) is O(n) and particularly fast for JIT scenarios. Our greedy approach is O(n²) in the number of temps but trivially correct and easy to read. For tutorial programs with a handful of temporaries per function, it produces near-optimal results anyway.
