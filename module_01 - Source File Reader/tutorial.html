01 — The Big Analogy

Head First Moment

Picture a film production crew on day one of shooting. The director is pacing. The camera crew is setting up lights. The actors are in makeup. But nobody has read the screenplay yet — it's still sitting on a shelf in a binder.

Before anyone calls "action", someone has to pick up that binder, make a clean photocopy of every page, and put that copy somewhere the whole crew can reach. That person is the Script Reader. They don't analyse the plot. They don't check whether the dialogue makes sense. They just get the words off the shelf and into the room.

Your source file reader is that Script Reader. It picks up your .c file from disk, copies every byte into a buffer in RAM, and hands that buffer to the rest of the compiler. No analysis happens yet. No tokens. No tree. Just: words in memory.

02 — The Source Struct: Your Screenplay in a Labelled Folder

A good Script Reader doesn't hand the director a loose pile of pages. They put everything in a labelled folder: the pages, the title, the page count. Your Source struct (a struct — a bundle of related data grouped under one name in C) is that folder.

Get it right now and you'll never touch it again. Every module from here to Module 16 passes a Source down the pipeline.

/* source.h — the Source struct.
 * Every later module receives a pointer to one of these.              */

#ifndef MY_COMPILER_SOURCE_H
#define MY_COMPILER_SOURCE_H

#include <stddef.h>    /* size_t: the right unsigned type for memory counts */

typedef struct {
    char       *text;      /* heap-allocated, null-terminated file contents  */
    size_t      len;       /* byte count — always use this, NEVER strlen()   */
    const char *filename;  /* original path, needed for error messages later */
} Source;

Source source_open(const char *path);   /* load a file, return a Source      */
void   source_free(Source *src);        /* release heap memory when done      */

#endif
Why Three Fields and Not Just a char*?

You might wonder why we need a struct at all. Three reasons:

  • text alone is not enough. A C source file can legally contain a null byte inside a string literal: "hello\0world". If you call strlen(text) you'll stop at that embedded null, not the real end of the file. len is always the ground truth.
  • filename is needed for every error message your compiler will ever print. "error on line 5" is useless. "error in main.c on line 5" tells the user where to look.
  • a struct lets you add fields later without changing every function signature. In Module 07 we'll add a line-offset table — every caller gets it for free.

03 — Reading the File: Measure, Allocate, Read, Terminate

The Script Reader's process is always the same: count the pages, get a folder big enough to hold them, copy every page in, then stamp "END" on the last one. Your source_open() does exactly four things in exactly this order.

Source source_open(const char *path)
{
    Source src;
    FILE  *fp;
    long   size;
    size_t bytes_read;

    /* ── Step 1: Open ──────────────────────────────────────────────
     * "rb" = read, binary mode.  On Windows, text mode silently
     * converts every \r\n pair to a single \n, shifting the byte
     * offset of every character that follows.  Binary mode gives
     * us the raw, unmodified bytes; the lexer handles line endings. */
    fp = fopen(path, "rb");
    if (fp == NULL) {
        fprintf(stderr, "error: cannot open '%s'\n", path);
        exit(1);   /* no source file = nothing to compile; stop now  */
    }

    /* ── Step 2: Measure ────────────────────────────────────────────
     * Seek to the end to learn the file size, then rewind so the
     * next read starts at byte 0.                                    */
    fseek(fp, 0, SEEK_END);    /* jump to the last byte              */
    size = ftell(fp);          /* distance from start = total length */
    fseek(fp, 0, SEEK_SET);    /* rewind: next read starts at byte 0 */

    /* ── Step 3: Allocate ───────────────────────────────────────────
     * size bytes for the file content, plus one extra byte for the
     * null terminator we add in step 4.                              */
    src.text = malloc((size_t)size + 1);
    if (src.text == NULL) {
        fprintf(stderr, "error: out of memory reading '%s'\n", path);
        fclose(fp);
        exit(1);   /* malloc returned NULL; cannot proceed without RAM */
    }

    /* ── Step 4: Read ───────────────────────────────────────────────
     * fread returns how many 1-byte items it successfully read.
     * A correct full read returns exactly (size_t)size.              */
    bytes_read = fread(src.text, 1, (size_t)size, fp);
    if ((long)bytes_read != size) {
        fprintf(stderr, "error: partial read of '%s' (%zu of %ld bytes)\n",
                path, bytes_read, size);
        free(src.text);    /* we allocated this; free it before exiting */
        fclose(fp);
        exit(1);
    }

    /* ── Step 5: Null-terminate ─────────────────────────────────────
     * Place '\0' one position past the last byte we read.
     * This makes C string functions safe and gives the lexer a
     * reliable end-of-file sentinel to detect when it's done.        */
    src.text[size] = '\0';
    src.len        = (size_t)size;
    src.filename   = path;    /* borrow caller's pointer; they own it */

    fclose(fp);               /* release the OS file handle           */
    return src;
}
Why One fread Instead of a Loop?

Some tutorials read files line by line with fgets(). Don't. Your lexer doesn't think in lines — it thinks in individual characters, and it needs to look one character ahead to decide whether = is assignment or the start of ==. A flat buffer gives you free random access to any character by index. One fread is also faster than thousands of fgetc calls because it makes one system call instead of one per byte.

04 — Freeing Memory: Strike the Set When You're Done

When a film shoot wraps, the crew strikes the set — they return every piece of equipment and leave nothing behind. Every source_open() must have a matching source_free(). Build this discipline now so it's automatic when you're juggling a dozen files in Module 16.

void source_free(Source *src)
{
    free(src->text);    /* release the heap buffer malloc'd by source_open  */

    /* Pointer poisoning: set text to NULL right after freeing.
     * If any code accidentally uses src->text after this point, it
     * will dereference NULL and crash immediately on that line —
     * loud, traceable, and fixable.  Without poisoning, the stale
     * pointer still holds the old address.  Reads might silently
     * succeed and corrupt something completely unrelated.            */
    src->text = NULL;

    src->len  = 0;      /* mark the struct obviously invalid             */
}
Pointer Poisoning — Build This Habit Now

Setting a pointer to NULL after free() costs one assignment. It buys you a crash that points directly at the bug rather than silent corruption that shows up three modules later in a completely different function. Every professional C codebase does this. Start now.

06 — Brain Exercise

Brain Exercise — Spot the Trap

Your teammate runs ./reader on an empty file — a .c file that is exactly 0 bytes on disk. They're certain the program will crash. Here's their reasoning step by step:

  • ftell() returns 0
  • malloc(0 + 1) allocates 1 byte — odd but probably fine
  • fread(buf, 1, 0, fp) tries to read 0 bytes and returns 0
  • Your check if ((long)bytes_read != size) compares 0 != 0

They bet you it crashes or prints garbage. Walk through all four steps for a 0-byte file. What actually happens? What will the output look like?

Answer — your teammate loses the bet.

Every step works correctly on an empty file. malloc(1) is legal and returns a valid 1-byte buffer. fread(..., 1, 0, fp) reads zero items and returns 0 — which is exactly right, because you asked it to read zero items. The partial-read check compares (long)0 != 0, which is false, so we don't exit. We write src.text[0] = '\0' (legal — we allocated 1 byte), set src.len = 0, and close. Output:

size: 0 bytes  |  lines: 0  |  preview:

The trap: it's easy to assume fread() returning 0 means failure. It doesn't. It means "I read exactly as many items as you asked for." For an empty file that's zero items — a perfectly normal result.

07 — There Are No Dumb Questions

Why read the whole file into RAM at once? That seems wasteful for large files.
Your lexer (Module 02) needs to look one character ahead of its current position to decide if = is assignment or the start of ==. If you stream byte by byte you need to buffer that lookahead anyway — and you end up recreating a flat buffer. A flat buffer also lets every module refer to any character by index, which is how you later print "error at line 5, column 12." Source files in practice are under a few megabytes. When they're not (generated code, large data tables), the fix is mmap() — same flat-buffer interface, zero copy cost, covered in Module 14.
The buffer is null-terminated. Why do I also need src.len? Can't I just use strlen()?
Not safely. A C source file can contain null bytes inside string literals: "hello\0world" is a valid C initialiser. If you call strlen(src.text) on a file containing this, strlen stops at the embedded '\0' and returns the wrong count. src.len came from ftell(), which doesn't care what bytes are in the file. Use src.len everywhere you iterate; use the null terminator only as a sentinel for functions that require one.
Why does source_open() call exit(1) on error? Isn't that bad practice in a library?
You're right that a library must never call exit() — it makes the code untestable and kills any long-running process that uses it. But right now source_open() is not a library; it's part of a single-shot tool. Inventing a result type, an error enum, and a recovery strategy before we've built anything else would mean writing three more modules before reading a single file. DECISIONS.md entry #3 names the exact production fix: a bool out-parameter or a longjmp-based error context. We'll apply it in Module 16 when we assemble the full pipeline.
Why use fseek/ftell to get the file size? I've seen code that uses stat().
stat() is POSIX, not part of the C11 standard. Using it requires #include <sys/stat.h>, a platform dependency we haven't formally introduced yet. fseek/ftell is guaranteed by the C standard and compiles on Linux, WSL, and macOS without changes. The downside — and DECISIONS.md is honest about it — is that fseek(SEEK_END) on a binary stream is technically implementation-defined under C11. It works on every OS you'll encounter. We switch to fstat() in Module 14 when we go deliberately Linux-specific for ELF output.

08 — What's Next

Coming Up: Module 02 — Lexer / Tokeniser

Right now your compiler can read a file. It has no idea what's in the file. It just sees a flat river of bytes: i, n, t,  , m, a, i, n, ( …

Module 02 changes that. The Lexer (your Script Supervisor) walks through Source.text from byte 0 to byte src.len - 1 and groups those bytes into meaningful chunks called tokens (the smallest units of meaning in a program) — int becomes a keyword token, main becomes an identifier token, ( becomes a punctuation token.

Now is exactly the right moment: you have a clean, null-terminated buffer with a known length. The lexer just needs an integer cursor that starts at 0 and walks forward. Everything it needs already lives in your Source struct.
