Everything Parsing · Module 09 · Part II — Lexical Analysis

Input Buffering &Sentinels

Before any automaton, the layer that feeds it characters. A scanner reads ahead, then sometimes backs up one — and the input is too big to hold. The two-buffer scheme with a sentinel byte does this at O(1) amortised cost and one comparison per character.

The two moves that matter

advance reads a character and steps forward; retract steps back one when you've looked too far. Both O(1). The sentinel makes "did I reach the buffer edge?" and "did I reach end-of-input?" the same single check.

01

The Big Analogy — the librarian and the dumbwaiter

A librarian is transcribing a document that arrives one page at a time through a dumbwaiter from the archive below. Her desk has room for exactly two pages.

She reads word by word. A ribbon marks where the current word started (lexemeBegin); her eyes scan ahead of it (forward). When her eyes reach the bottom of page 1, she calls for page 2 — it lands next to page 1. When her eyes reach the bottom of page 2, she calls for page 3, and it replaces page 1 — which she's finished with, because her ribbon has long since moved onto page 2.

Instead of glancing at the page edge after every single word — "am I at the bottom yet?" — she clips a bright red bookmark to the bottom of each page. Her eyes just watch for red. Hit red → either call for the next page, or, if it's the special "END OF DOCUMENT" red card, stop. One thing to watch for, one decision when she sees it.

Sometimes she reads one letter past a word's end to be sure it's over, then slides her eyes back one (retract) — instant. The only rule: no word may be longer than a page, or fetching the next page would overwrite the page her ribbon is on.

02

What Happens, Step by Step

  1. Layout: one array, [ half0 | S | half1 | S ]. The S slots hold the sentinel.
  2. Fill half 0 from the source. If it filled completely, write SENTINEL in its S slot; if the source ran out first, write EOF right after the last real character.
  3. advance(): read data[forward]. If it's SENTINEL → fill the other half, move forward to its start, read again. If it's EOF → return EOF, don't move. Otherwise → return the character, forward++.
  4. mark() sets lexemeBegin = forward.
  5. retract(n) does forward -= n. Throws if that would cross the halfway boundary (lexeme too long).
  6. lexeme() walks lexemeBegin → forward, jumping to the other half when it meets a sentinel, stitching the text.

The sentinel: one check, two meanings

  without a sentinel, every character:      with a sentinel, every character:

    if (forward == halfEnd)   reload           c = data[forward]
    else if (forward == eof)  stop             if (c == SENTINEL)  reload-or-stop
    else  c = data[forward++]                  else                c = data[forward++]

         two comparisons                            one comparison
                                            (and the SAME one for edge and for EOF)

The retract at "12.go"

  read '1' '2'  → NUM so far
  peek '.'      → maybe a FLOAT? advance the '.'
  peek 'g'      → not a digit!  the '.' isn't part of the number
  retract(1)    → forward-- , back onto the '.'
  emit NUM "12"  ;  the '.' is scanned next as its own token
04

The Code, Explained

advance — the whole loop is one sentinel test

fillHalf — SENTINEL if full, EOF inline if the source ran out

private void fillHalf(int half) {
  bufferLoads++;
  int base = halfStart(half);
  int n = Math.min(halfSize, source.length() - sourcePos);
  for (int i = 0; i < n; i++) data[base + i] = source.charAt(sourcePos + i);
  sourcePos += n;
  if (n < halfSize) data[base + n] = EOF;              // source exhausted mid-half
  else             data[sentinelIndex(half)] = SENTINEL; // half full: boundary
}
The -1 / -2, and why chars are int

The sentinel must be a value that cannot be a real character. Java char has no spare value, so the buffer stores ints and advance() returns int — exactly like Reader.read() returning -1 at EOF. -1 = true end, -2 = half boundary. JS uses an Int32Array for the same reason. This is bucket (a), forced — see DECISIONS.md.

05

Limits — what this module cannot do yet

Can't do yet

  • Handle a lexeme longer than one half — retract across the boundary throws (the Dragon Book's own limit).
  • Decide what a token is — the demo scanner is hand-coded; a real one is driven by an automaton (Modules 10–16).
  • Multi-character retract in general — supported, but only within the current half.
  • Anything about Unicode — `charAt` here is a UTF-16 code unit (Appendix X13).
  • Track line/column — that's Module 13's job, layered on top.

Can do

  • Feed a scanner characters from input of any size, block by block.
  • advance / retract at O(1), amortised O(1) buffer loads.
  • One comparison per character, regardless of buffer edges.
  • Stitch a lexeme that spans the halfway split.
  • Report end-of-input idempotently.
  • Expose the exact peek/advance/mark/retract/lexeme interface every later scanner uses.

Getting a blank or broken result?

retract crossed the halfway boundary — a lexeme longer than one half. Raise halfSize above your longest token.
lexeme() returns a truncated string — same cause: the lexeme's start half was reloaded before you asked for it.
Buffer loads one higher than expected — the source length is an exact multiple of halfSize, so a final 0-char fill places the EOF sentinel. That's the +1 in the classic formula.

07

Brain Exercise

The sentinel saves one comparison per character — ~10 million on a 10 MB file. But a modern CPU's branch predictor gets that forward == end check right almost every time, essentially for free.

(1) So is the sentinel still worth it? What does it still buy? (2) Why two halves and not three, or a ring of ten?

Answers

(1) The saved compare is nearly free on modern hardware — the historical motivation is weak now. What endures is structure: the inner loop has one exit condition instead of two, which keeps the hot path (while (isLetter(c = data[forward])) forward++;) tight and predictable, with all the block-management logic outside it. And the trick itself — a value outside the alphabet as a universal boundary marker — recurs constantly: the $ end-marker on the token stream (Module 22), the bottom-of-stack marker in LR parsing (Module 27). Learn it here.

(2) Two is the minimum that lets you fill the next block while still holding the block your lexemeBegin ribbon is in. More blocks would support longer lexemes (retract further back) at a memory cost; some real lexers use a bigger ring, and many just mmap the whole file and skip buffering entirely. Two halves is the classic space-and-simplicity sweet spot, not a law.

08

There Are No Dumb Questions

Why not just read the whole file into a String? Memory is cheap.

For most tools you can, and modern lexers often do — or mmap the file so the OS pages it in. The two-buffer scheme earns its keep for streaming input: stdin, a network socket, a 4 GB log you can't fit. What you actually reuse everywhere is the interface — peek/advance/mark/retract — and the buffering behind it can be a String, two halves, a ring, or an mmap.

What's the sentinel value in a real hand-written lexer? \0?

\0 works only if you're certain the input has no NUL bytes — fine for source code, not for binary. Common real choices: read into int and use EOF = -1 with a separate boundary flag; or mmap plus a guard page that faults on over-read; or, in flex, a two-buffer scheme much like this one with a YY_END_OF_BUFFER_CHAR. The idea (a value outside the alphabet) is constant; the encoding is a taste call.

Retract only works within one buffer. What if my parser needs 2 tokens of lookahead?

Different layer. The parser buffers tokens, not characters, and a token ring of size k is trivial (Module 19 builds one). At the character level, lexers almost never need more than one char of retract — maximal munch reads until the pattern stops matching, then backs up one.

The 12.go case emits NUM . go — shouldn't .go be a method call?

This toy scanner has no concept of . as an operator. The only thing being shown is that the . was not consumed by the number rule and is sitting there for the next scan. A real language's scanner would recognise . as its own token; a real parser would make a.b a member access. That's their job, not the buffer's.

Why does the demo count "forward reads" as 40 for 39 characters?

39 real character reads, plus one extra data[forward] read where advance() hit a SENTINEL and looped. Boundary crossings that happen during peek() (in the lookahead loops) aren't counted. The number is "≈ one per character," which is the point — it does not grow with the number of buffer edges.
