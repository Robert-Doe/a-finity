Everything Parsing · Module 20 · Part III — Top-Down Parsing

The Predictive Parsing Condition

Module 19 chose alternatives by eyeballing the grammar. This module makes it a decision procedure. For every rule A → a₁ | a₂ | …, compute the set of tokens that each alternative could legally start with — its PREDICT set. If no token appears in two of them, one lookahead token is always enough and recursive descent never has to backtrack. That is the whole definition of LL(1).

The payoff

Feed a grammar in, get a verdict out: LL(1) = YES, or a concrete witness — "nonterminal X on token 'else': [X → else S] vs [X → epsilon]." No guessing about whether your hand-written parser will work.

01

The Big Analogy — the road sign at the fork

You're driving and the road forks. There's a sign: left for the coast, right for the mountains. One glance, one decision, no reversing. That works because the two destinations are disjoint — no town is both on the coast and in the mountains.

Now imagine a fork where the sign says left for Springfield, right for Springfield. Useless. You'd have to drive a bit down one road, and if it turns out to be the wrong Springfield, reverse all the way back and try the other. That's backtracking, and for a parser it can blow up exponentially.

Each nonterminal in your grammar is a fork. Each alternative is a road. The PREDICT set of an alternative is the list of tokens that road can start with. The parser reads one token — the sign — and takes the matching road. This only works if the PREDICT sets don't overlap. When they do, the grammar is telling you "left for Springfield, right for Springfield," and you either redraw the map (left factoring, Module 24) or accept that this parsing method won't work here.

02

What Happens, Step by Step

FIRST(a) — the set of terminals that can begin a string derived from the symbol string a. Plus the marker epsilon if a can derive the empty string (is nullable).

FOLLOW(A) — the set of terminals that can appear immediately after A in some sentential form. Plus $ (end of input) if A can be last.

  1. Compute FIRST for every nonterminal: start each empty; for each production A → X₁…Xₙ, add FIRST(X₁); if X₁ is nullable also add FIRST(X₂); and so on. Repeat over all productions until a full pass adds nothing.
  2. Compute FOLLOW: seed FOLLOW(start) = {$}. For each B → a X b: add FIRST(b) \ {epsilon} to FOLLOW(X); if b is nullable, also add FOLLOW(B). Iterate to convergence.
  3. For each production A → a: 
    PREDICT(A -> a) = FIRST(a)                            if a is NOT nullable
               = (FIRST(a) \ {epsilon}) U FOLLOW(A)   if a IS nullable
  4. For each nonterminal, intersect the PREDICT sets of its productions pairwise. Any non-empty intersection is a conflict: report the nonterminal, the shared token, and the two productions.
  5. No conflicts anywhere → the grammar is LL(1) and a backtrack-free predictive parser exists.
03

The state, drawn

The expression grammar — LL(1)

  NT     FIRST                FOLLOW
  E      { ( id num }         { $ ) }
  Ep     { + epsilon }        { $ ) }
  T      { ( id num }         { $ ) + }
  Tp     { * epsilon }        { $ ) + }
  F      { ( id num }         { $ ) * + }

  Ep -> + T Ep    PREDICT { + }
  Ep -> epsilon   PREDICT { $ ) }      nullable, so adds FOLLOW(Ep)
                          ^^^^^ disjoint from { + }  ->  no conflict

  every fork's roads are signed for different towns.  LL(1) = YES

The dangling else — not LL(1)

  S -> if b then S X | other
  X -> else S | epsilon

  FOLLOW(X): X sits at the end of  S -> if b then S X , so FOLLOW(X) gets
  FOLLOW(S). And S sits before X (which is nullable) in that same rule, so
  FOLLOW(S) gets FIRST(X) = { else }. Net:  FOLLOW(X) = { else $ }

  X -> else S    PREDICT { else }
  X -> epsilon   PREDICT { else $ }     nullable, adds FOLLOW(X)
                        ^^^^ 'else' is in BOTH  ->  CONFLICT

  on the token 'else' the parser genuinely cannot tell whether this 'else'
  belongs to the current 'if' or an enclosing one. Real parsers hard-wire
  "take X -> else S" (bind to the nearest if).

A shared prefix — fixable

  S -> a b c | a b d
  PREDICT(a b c) = { a }        PREDICT(a b d) = { a }        CONFLICT on 'a'

  the roads agree for the first two tokens and only diverge at the third.
  left-factor (Module 24):   S -> a b S'      S' -> c | d
  now the fork is at S', where PREDICT { c } and { d } are disjoint.

Why the fixed-point loop, and why it stops

FIRST and FOLLOW are defined circularly — FIRST(E) depends on FIRST(T) which (via F → ( E )) depends back on FIRST(E). You break the circle by starting with empty sets and adding until nothing changes. It terminates because the sets only ever grow, and they can't grow past the finite set of terminals plus {epsilon, $}. Module 21 proves this is not just a fixed point but the least one — the smallest sets consistent with the rules — and that's the one you want.

Getting a blank or broken result?

FOLLOW missing $ — seed FOLLOW(start) = {$} before iterating.
FIRST never stabilises — you're not checking whether a pass actually added anything; loop while changed.
A nullable rule shows no conflict when it should — PREDICT must union FOLLOW(A) for the nullable alternative, not just FIRST.
Left-recursive grammar reported LL(1) — the pair A → A x vs A → y still shares FIRST on y; the conflict scan should catch it.

07

Brain Exercise

(1) Grammar A → B c | d, B → e | epsilon. Compute FIRST(A), FIRST(B c), FOLLOW(B). Is A's fork LL(1)? (2) Why does PREDICT use FOLLOW(A) and not FOLLOW of the whole nullable string a?

Answers

(1) FIRST(B) = {e, epsilon}. FIRST(B c): add FIRST(B)\{epsilon} = {e}; B is nullable so also add FIRST(c) = {c}; c not nullable, stop → {e, c}. FIRST(A) = FIRST(B c) ∪ FIRST(d) = {e, c, d}. PREDICT(A → B c) = {e, c} (not nullable — c is there), PREDICT(A → d) = {d}. Disjoint → LL(1). FOLLOW(B) = {c} (from A → B c).

(2) Because if the parser takes the nullable alternative a and a derives epsilon, then A itself produced nothing — so the next token is whatever follows A. FOLLOW(a) isn't even a defined notion; a is a string, not a nonterminal. The thing that "follows the empty production" is by definition FOLLOW(A).

08

There Are No Dumb Questions

What does the "1" in LL(1) mean, exactly?

One token of lookahead. The parser decides each production from the single next token. LL(2) looks at the next two; LL(k) at k. The first "L" = left-to-right scan; the second "L" = leftmost derivation (which is exactly what recursive descent produces, Module 19).

Is every unambiguous grammar LL(1)?

No — LL(1) is much narrower. The natural left-recursive expression grammar is unambiguous but not LL(1) (or even LL(k)). Ambiguous grammars are never LL(1). And some languages have no LL(1) grammar at all, though most practical ones do after left-factoring and left-recursion removal.

Why report the token, not just "conflict at X"?

Because the token tells you what input triggers the ambiguity, which is how you diagnose and fix it. "Conflict at X on else" immediately says "this is the dangling-else problem." It's also exactly the cell that would be double-booked in the LL(1) table (Module 25).

The dangling-else grammar "works" in real compilers. How, if it's not LL(1)?

They keep the conflicting grammar and add a resolution rule: on else, always take X → else S. The parser generator reports the conflict and tells you how it resolved it. It's a deliberate, documented deviation from pure LL(1) — see Modules 25 and 35.

Does epsilon ever end up in a PREDICT set?

No. PREDICT strips epsilon and, for a nullable alternative, replaces it with the concrete tokens in FOLLOW(A). A PREDICT set is always a set of real terminals (possibly including $).
