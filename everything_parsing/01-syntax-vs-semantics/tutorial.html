Everything Parsing · Module 01 · Part I — Foundations

Syntax vs.Semantics

Before any grammar, any parser, any of it: a string can obey every rule of form and still mean nothing. Form and meaning are checked by two different machines, and this module builds both — small enough to read in one sitting — over a four-symbol language.

The one input that carries the whole module

12 0 /  — the syntax checker says PASS. The evaluator says division by zero. Same six characters. Two verdicts. That gap is why compilers have separate passes, and it is the only thing you must leave here believing.

01

The Big Analogy — the flawless cheque

You write a cheque. There is a right form: today's date, a payee on the "pay to" line, the amount as digits and spelled out, the two matching, your signature at the bottom right. Miss any of that and the cashier hands it straight back at the counter — they never even look up your balance. That check, at the counter, is syntax.

Now the cheque is perfect. Every line filled, amounts agree, signed. The cashier passes it through. And it bounces — because the account behind it holds nothing. Nobody could have known that from the paper. It took a second machine, in a back office, that does the one thing the counter never does: look at what's actually there. That is semantics.

3 4 + + is handed back at the counter — a line left blank. 12 0 / is a flawless cheque drawn on an empty account. The form is immaculate. There is simply nothing to divide into.

Two checkers, two jobs, and a strict order: the back office never sees a cheque the counter rejected. In this module, checkSyntax is the counter and evaluate is the back office, and Main prints (skipped: syntax failed) every time the counter says no.

Why this analogy and not "a grammatical nonsense sentence"

"Colorless green ideas sleep furiously" is the famous linguistics example, but it's slippery — people argue about whether it means something. A bounced cheque is not slippery. The form is objectively complete; the funds are objectively absent; and the two facts were established by two different people who checked two different things. That is exactly the relationship checkSyntax and evaluate have.

02

What Happens, Step by Step

For one input line, e.g. 12 0 /:

  1. Tokenize. Walk the characters. Skip spaces and tabs. Each maximal run of non-space characters becomes a token { text, col }, where col is its 1-based start column. → [{"12",1}, {"0",4}, {"/",6}]
  2. Syntax pass (checkSyntax). Start a counter depth = 0. For each token: if it's all digits, depth += 1; if it's one of + - * /, require depth ≥ 2 then depth -= 1; anything else is an "unknown token" failure. At the end, require depth == 1. No digit is ever converted to a number. No arithmetic happens.
  3. Gate. If the syntax pass failed, print its message and (skipped: syntax failed). Stop. The evaluator never runs.
  4. Semantic pass (evaluate). Only now. Start an empty value stack. Push each integer (as long / BigInt). For each operator, pop b then a, and — for / only — if b == 0, stop with division by zero at that operator's column. Otherwise push a op b.
  5. Report. One block per input; a summary line at the end counting how many inputs passed each stage, and how many passed syntax but failed semantics.
03

The state, drawn

Two different quantities are tracked over the same token stream. The syntax pass tracks a count. The semantic pass tracks values. Here is 12 0 / through both:

token:      12        0         /
            │         │         │
SYNTAX  ───┤ depth=1  depth=2   depth≥2 ok → depth=1   ── end: depth==1  PASS
(a count)  │ (+1)     (+1)      (pop 2, push 1)
            │
SEMANTIC ──┤ stack    stack     pop b=0, pop a=12
(values)   │ [12]     [12,0]    op is '/', b==0  ───────────────────────►  FAIL  col 6: division by zero

The syntax pass reaches depth == 1 and is satisfied — it never learned that the second value was 0, because it never looked at values at all. The semantic pass is the first thing in the pipeline that knows.

And a purely structural failure, 3 4 + +, dies in the syntax pass — the evaluator is never called:

token:      3         4         +                    +
            │         │         │                    │
SYNTAX  ───┤ depth=1  depth=2   depth≥2 ok → depth=1  depth=1, need ≥2  ──►  FAIL  col 7
            │ (+1)     (+1)      (pop 2, push 1)      "operator '+' needs 2 operands, stack has 1"
04

The Code, Explained

The syntax checker — a counter, nothing more

This is the whole thing. Notice what is absent: no parseLong, no + - * / arithmetic, no value stack.

The two are line-for-line the same algorithm. That is deliberate: for the syntax layer the languages agree completely. They diverge only when real numbers appear.

The semantic checker — where the languages split

The evaluator's / case is the entire reason the JS build uses BigInt and not a plain number:

Crazy detail — why not just let it throw?

Delete the if (b == 0) guard and Java throws ArithmeticException: / by zero; JavaScript's BigInt throws RangeError: Division by zero. Two exception types, two messages, neither carrying a source column. The guard exists so both builds emit the identical string col 6: division by zero. Every "why is the code shaped like this" question in this course resolves to one of: forced by the language, forced by an external contract, or a convention we chose — see DECISIONS.md. This one is the external-contract kind: the contract is "both builds print the same bytes."

Columns are 1-based — and that costs exactly one + 1

// tokenize(), the only place a column is computed:
out.add(new Token(line.substring(start, i), start + 1));
                                              // ^^^ 0-based index → 1-based column

Every compiler and editor the learner has ever used reports 1-based columns. Matching that convention here means col 6 in our output lines up with what their editor's status bar shows.

05

Limits — what this module cannot do yet

Can't do yet

  • Parse infix (3 + 4) — no precedence, no associativity, no parentheses.
  • Build a parse tree or an AST. RPN's structure is implicit in operator order; we recognize, we don't yet represent.
  • Handle variables, so "undefined variable" — the other classic semantic error — can't appear.
  • Report more than one error per input.
  • Accept negative literals (-5), floats, or any base but 10.
  • Detect integer overflow (see the Brain Exercise — the two builds actually disagree past 2⁶³).
  • Anything for any language other than this exact four-operator postfix one.

Can do

  • Decide well-formedness of any postfix integer expression with a counter that never does arithmetic.
  • Evaluate a well-formed one to a 64-bit (Java) / exact (JS) integer.
  • Point at the first error with a 1-based column.
  • Prove, with a passing test, that 12 0 / is syntactically valid and semantically not.
  • Name which kind of error each failure is — the skill the rest of the course is built on.

07

Brain Exercise

The course promises the Java and JavaScript builds produce byte-identical output. Section 05 hinted that isn't quite unconditional.

Construct an input that both checkers accept — syntax: PASS, semantics: PASS — where the two builds nonetheless print different value = lines. Then say which of the two is "right," and which of the module's error categories the discrepancy belongs to.

Think first. Then open.

Any product that exceeds 2⁶³ − 1 = 9223372036854775807. For example, twenty 9s followed by nineteen * — i.e. 9²⁰:

java: semantics: PASS  value = -6289078614652622815
js  : semantics: PASS  value = 12157665459056928801

Java's long is 64-bit and wraps silently on overflow — the spec (JLS §15.18.2) mandates two's-complement wraparound, no exception. JavaScript's BigInt is arbitrary precision and gives the exact answer, 9²⁰. The BigInt result is the mathematically correct one.

Neither checker flags it. It isn't malformed syntax — the form is fine. It isn't the one semantic error we defined — nobody divided by zero. It is a third thing: a runtime fault that depends on the machine's integer width. "Semantics" itself has layers — static semantics (types, scope; Modules 42–44) and dynamic semantics (what actually happens when it runs), and overflow lives in the second. The lesson: the syntax/semantics split is real and clean, but "semantics" is not one box.

08

There Are No Dumb Questions

"Unknown token 'x'" is about meaning — isn't that a semantic error?

No. The checker rejects x without knowing, or caring, what x would mean. It fails because x is not a shape the language allows — not all-digits, not one of four operators. That's a lexical/syntactic judgment: is this a legal token at all? Compare a real semantic name error — "variable x used before it was declared" — which requires knowing the rules about what names mean in scope. This language has no names, so it can't have that error.

Operand underflow stops evaluation just like divide-by-zero does. Why is one "syntax" and the other "semantics"?

Because underflow is visible in the structure alone. Count operators and operands as you read left to right; the counts tell you 3 4 + + can't work, without evaluating anything. Divide-by-zero is invisible in the structure: 12 0 / and 12 3 / have the identical shape. Telling them apart needs a runtime value. "Detectable from form alone" vs. "needs a value" is the line.

Couldn't a smarter syntax checker catch 12 0 / by noticing the literal 0?

It could special-case a literal zero divisor — but not 12 5 5 - /, where the divisor is 5 - 5, computed at runtime. To catch that you'd have to evaluate, which is the semantic pass by another name. Constant-folding zero divisors is a real compiler optimization (and warning), but it's an extra, not a redrawing of the syntax/semantics line.

Real compilers report a screenful of errors at once. Why does this one stop at the first?

Reporting error #2 means deciding where to resume after error #1 — which tokens to skip, which to trust. That's error recovery, and doing it without cascading nonsense is genuinely hard. It gets its own module (22). Stopping at the first error keeps SyntaxResult a plain (ok, message, col) triple here.

Where's the parse tree? I thought parsing was all about building trees.

It will be — from Module 5 on. RPN is the one notation where you can get away without a tree, because the order of tokens already encodes the structure (3 4 + 5 * can only mean one thing). This module recognizes — decides yes/no membership — without representing. Separating those two verbs early is worth the detour.
