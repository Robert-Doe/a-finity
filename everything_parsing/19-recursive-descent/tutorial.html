Everything Parsing · Module 19 · Part III — Top-Down Parsing

Recursive-Descent Parsing

Turn a grammar into code the most direct way there is: one function per nonterminal. The function for E calls the functions for whatever is on E's right-hand side. Run it on a token stream and it walks a parse tree top-down, left-to-right — and the chain of pending function calls is a leftmost derivation, the exact object from Module 5.

The payoff

The parser fires productions in this order: E→T E', T→F T', F→num, … Feed that list, unchanged, into a leftmost-derivation replayer and it produces E ⇒ T E' ⇒ F T' E' ⇒ num T' E' ⇒ … ending exactly at the input. Same list. The stack was the derivation all along.

The Big Analogy — the org chart that answers the phone

A company has one department per kind of thing it does. A request comes in the front door. Reception hands it to the Expression department. Expression can't finish it alone — an expression is "a term, then maybe some + terms" — so it calls the Term department for the first piece and keeps the phone line open. Term is "a factor, then maybe some * factors", so it calls Factor. Factor looks at what's actually in front of it: a number? a name? an open paren? If it's an open paren, Factor calls Expression right back — recursion — and waits for the matching close paren.

Every department is a function. Each one consumes the tokens it's responsible for and returns its piece of the tree. The stack of open phone calls at any instant — Expression waiting on Term waiting on Factor waiting on Expression — spells out exactly which part of the grammar you're inside. That stack, snapshotted step by step, is the leftmost derivation.

There's one rule the org chart can't survive: a department that calls itself as its very first action, before doing any work. "Expression is an expression, plus a term" — Expression phones Expression, which phones Expression, forever. That's left recursion, and §05 is about why it's fatal here and what to do instead.

What Happens, Step by Step

The grammar (already free of left recursion — Module 23 produces this shape mechanically):

E  -> T E'
E' -> + T E'  |  epsilon
T  -> F T'
T' -> * F T'  |  epsilon
F  -> ( E )   |  num  |  id
  1. Lex the source into a position-tagged token stream ending in EOF.
  2. Call parseE(). It logs E -> T E', then calls parseT(), then parseEprime().
  3. parseT() logs T -> F T', calls parseF() then parseTprime().
  4. parseF() looks at the current token: ( → F -> ( E ) (and recurse into parseE); num → F -> num; id → F -> id; anything else → syntax error at the token's position.
  5. parseEprime() / parseTprime(): if the next token is + / *, take the recursive alternative; otherwise take epsilon and return.
  6. expect(kind) consumes a terminal or throws. Every method appends its production to rules before recursing, so rules comes out in leftmost order.
  7. Back at the top, expect("EOF") — a complete expression must consume every token (this is what rejects 1 2).
  8. Derivation.replay(rules) starts at [E], applies each production to the leftmost nonterminal, and must land on the token-kind string. If any production doesn't expand the leftmost nonterminal, it throws — the parse wasn't leftmost.

The state, drawn

Call stack ↔ leftmost derivation, for 1 + 2 * 3

  call made            production logged     sentential form after it
  ─────────────────    ──────────────────    ───────────────────────────
  parseE               E -> T E'             T E'
   parseT              T -> F T'             F T' E'
    parseF  (sees num) F -> num              num T' E'
    parseT'  (sees +)  T' -> epsilon         num E'
   parseE'  (sees +)   E' -> + T E'          num + T E'
    parseT             T -> F T'             num + F T' E'
     parseF (sees num) F -> num              num + num T' E'
     parseT' (sees *)  T' -> * F T'          num + num * F T' E'
      parseF (sees num)F -> num              num + num * num T' E'
      parseT'(sees EOF)T' -> epsilon         num + num * num E'
   parseE' (sees EOF)  E' -> epsilon         num + num * num      ← = token kinds

  the right column, read top to bottom, is the leftmost derivation.

The concrete tree — * is deeper than +

  E
  +- T                         "1"  lives under the FIRST T
  |  +- F
  |  |  +- num (1)
  |  +- T'
  |     +- epsilon
  +- E'
     +- +
     +- T                      "2 * 3" is one T, built by  T' -> * F T'
     |  +- F
     |  |  +- num (2)
     |  +- T'
     |     +- *
     |     +- F
     |     |  +- num (3)
     |     +- T'
     |        +- epsilon
     +- E'
        +- epsilon

Because * can only be introduced by T', and T' is reached only through T which is below E', every * ends up deeper in the tree than every +. Precedence is structural — exactly the Module 6 idea, now enforced by the shape of the recursion.

Right lean — a + b + c

  E' -> + T E'  is RIGHT-recursive, so:

     +(a, +(b, c))          not   +(+(a, b), c)

  the concrete tree nests the second '+' INSIDE the first one's E'.
  fine for a language where + is associative; wrong if you need left folding
  for evaluation order or error messages. Fixes: build the AST with a left
  fold (Module 39), or write E' as a loop (§04).

The one helper that reports errors

The loop form of E' — what hand-written parsers actually do 
Node e = parseT();
while (at("+")) { expect("+"); e = plus(e, parseT()); }   // LEFT-leaning
return e;

This is precisely EBNF's E -> T { + T } from Module 8. { … } means "loop", and a loop and a right-recursive epsilon rule accept the identical language. The loop version folds left as it goes, so it gets associativity right for free — which is why real recursive-descent parsers are written this way and the pure-grammar E' form is mostly a teaching device that lines up 1:1 with the productions.

05

Limits — what this module cannot do yet

Left recursion is fatal — not a bug, a theorem

Try to parse Module 6's E -> E + T directly: parseE()'s first statement is parseE(), with the cursor unmoved. No token is consumed between the calls, so the recursion never bottoms out: StackOverflowError, zero progress. Every top-down parser has this limitation — the input is consumed left to right and a left-recursive rule asks you to recognise the big thing before its first token. Module 23 gives the mechanical fix (Paull's algorithm); Module 29 covers what bounded backtracking and ANTLR-style adaptive prediction buy you.

Can't do yet

  • Left-recursive grammars (Module 23 transforms them away).
  • Alternatives whose first tokens overlap — needs left factoring (Module 24).
  • Decide "is this grammar even parsable this way?" without eyeballing — needs FIRST/FOLLOW (Modules 21–22) and the LL(1) table (Module 25).
  • Recover from an error and keep parsing — Module 27 (panic mode with FOLLOW sync sets).
  • Left-associative trees directly (loop form or AST lowering, Module 39).
  • More than one token of lookahead — Module 29 (LL(k), LL(*)).

Can do

  • Parse any non-left-recursive grammar with disjoint per-alternative FIRST sets, by hand, in either language.
  • Build the full concrete syntax tree.
  • Emit the leftmost derivation as an ordered production list — and prove it's leftmost.
  • Enforce precedence and associativity through grammar shape.
  • Report the first syntax error with an exact source position.

Getting a blank or broken result?

StackOverflowError / RangeError — a left-recursive rule. Recursive descent needs the non-left-recursive form (Module 23).
replay throws "not leftmost" — a method recursed before logging its production. Log first, then recurse.
1 2 parses without error — you forgot expect("EOF") after parseE().
Error position is always 0 — read peek().pos at the moment expect fails, not the start token.

Brain Exercise

(1) Add unary minus: F -> - F | ( E ) | num | id. Does recursive descent handle this new rule? Is it left-recursive? (2) Now add exponentiation ^, which is right-associative and binds tighter than *. Write the two productions (P = "power") and say where they slot in.

Answers

(1) Yes — F -> - F is right-recursive: the - token is consumed before the recursive parseF() call, so the cursor advances and the recursion terminates. --x parses as -(-(x)). Only left recursion (recursing with the cursor unmoved) breaks.

(2) F -> P T2'-style isn't needed; insert a level between T''s factor and F: T' -> * P T' | epsilon, P -> F P', P' -> ^ P | epsilon. The recursive alternative ^ P (not ^ F P') recurses on the whole power, so 2 ^ 3 ^ 2 nests right = 2 ^ (3 ^ 2). Right associativity falls straight out of recursing on the higher-level nonterminal instead of threading a prime.

08

There Are No Dumb Questions

Is the "call stack is the leftmost derivation" thing exact, or just a metaphor?

Exact. Each nonterminal method, when it commits to a production, is performing one leftmost derivation step — it expands the leftmost not-yet-expanded nonterminal (itself) and then recurses left-to-right into the result. Snapshot the "sentence so far + pending symbols" at each commit and you get precisely the sentential forms of the leftmost derivation. The module's Derivation.replay reconstructs them from the production list and the test suite checks the endpoint.

Why E' and T' instead of just writing loops?

The primed-nonterminal form maps 1:1 onto grammar productions, which is what makes the derivation correspondence legible. Production parsers use the loop form (E -> T { + T }) because it's shorter and folds left. They accept the same language — Module 8's EBNF↔BNF equivalence.

What decides which alternative parseF takes?

The single current token. ( → ( E ), num → num, id → id. This works because those three sets don't overlap — the predictive parsing condition, made formal in Module 20. When the sets do overlap you either left-factor (Module 24) or you're not LL(1) (Module 25).

The parser stops at the first error. Real compilers report many.

Right — this one throws and unwinds. Module 27 adds panic-mode recovery: on an error, discard tokens until one in a synchronizing set (computed from FOLLOW), then resume. Same idea as the lexer's recovery in Module 17, one layer up.

Is recursive descent used in real compilers, or is it a toy?

Very real. GCC, Clang, the V8 and SpiderMonkey JS engines, the Go compiler, and rustc all use hand-written recursive-descent parsers — for speed, for error-message control, and for handling the parts of real languages that aren't cleanly context-free. The table-driven methods in Modules 25–36 are what parser generators emit.
