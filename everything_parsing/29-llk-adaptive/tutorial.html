LL(k), LL(*) & Backtracking RD

LL(1) uses one lookahead token. Sometimes one isn't enough and two is: FIRST₂ sets that overlap at one token separate at two. Sometimes no fixed number works and you need LL(*) — regular, unbounded lookahead, ANTLR's trick. And sometimes you give up on lookahead and backtrack — which, without memoization, goes exponential. This module measures all three.

The payoff

A labeled-statement grammar: on id the parser can't tell a label from an expression. Peek one more token — colon means label — and it's LL(2). The ambiguous grammar next to it: 2ⁿ parse trees, and a backtracker does 2ⁿ work to find them.

The Big Analogy — telling twins apart

Two people walk toward you and from a distance you can't tell which is which. One glance (LL(1)) isn't enough. Look a moment longer — one is wearing a badge (LL(2)) — and now you know. That's what a second lookahead token buys: the alternatives were identical at token 1, distinct at token 2.

Some pairs need more. You watch them walk across the whole room before one turns toward the door that gives it away. You didn't decide in advance how many steps to watch — you watched until you knew. That's LL(*): a little machine that reads as much lookahead as it needs, then commits.

And some pairs are actual identical twins. No amount of looking helps. Your only option is to guess, follow that guess to its conclusion, and if it's wrong, come back and try the other — backtracking. If the twins have twins who have twins, the number of guesses to check explodes.

What Happens, Step by Step

FIRST_k

  1. FIRST_k(α) = every terminal string of length ≤ k that can begin a derivation from α (shorter than k only if α derives something shorter).
  2. Compute it as a fixed point, exactly like FIRST (Module 21): sets start empty, fold in FIRST_k(rhs) per production, iterate. Joining two prefixes truncates to k tokens.
  3. LL(k) test: for every nonterminal with ≥ 2 productions, the FIRST_k sets of its alternatives must be pairwise disjoint. (The full test also folds FOLLOW_k in for nullable alternatives.)
  4. minLL: k = 1 uses Module 20's exact PREDICT check; k = 2, 3, 4 use the FIRST_k-disjoint test; if none work, the grammar is not LL(k) for small k (often ambiguous).

Backtracking recognizer

  1. To derive a nonterminal at a position, try every production, in order, following all of them — no lookahead pruning.
  2. Track, per end position, the number of ways to get there. The count at end-of-input is the number of parse trees.
  3. Count entries — one per production attempt — as the work. With no memoization, the same (nonterminal, position) is re-solved on every path that reaches it.

The state, drawn

LL(2) resolves what LL(1) can't — label.grammar

  stmt -> label colon stmt | expr semi
  label -> id           expr -> id | id lparen rparen

  FIRST_1(label colon stmt) = { id }
  FIRST_1(expr semi)        = { id }        <- collide on 'id'.  NOT LL(1).

  FIRST_2(label colon stmt) = { id colon }
  FIRST_2(expr semi)        = { id semi , id lparen }
                              ^^^^^^^^^^^^^^^^^^^^^^ disjoint from { id colon }
  minimal k = 2.

  can't left-factor: 'label' and 'expr' are different nonterminals, so 'id'
  isn't a literal shared prefix of one rule.

No k helps — equiv.grammar

  A -> x B | x C | y     B -> A     C -> A

  FIRST_k(x B) and FIRST_k(x C) are IDENTICAL for every k -- B and C both
  derive A, so both alternatives generate exactly x (x|y)* ... .
  minimal k = none.  the grammar is ambiguous: x^n y has 2^n parse trees.

Backtracking cost

  equiv on x^n y (no memoization):
    n   parse trees   production tries
    1   2             11
    3   8             59
    5   32            251
    7   128           1019           <- doubles every step

  expr (LL(1)) on id (+ id)^n:
    tokens  parse trees   production tries
    1       1             9
    7       1             33
    13      1             57          <- linear

  the difference: expr's wrong alternatives fail on the first token and are
  abandoned; equiv's don't -- both "x B" and "x C" match, forever.

The counting recognizer

Why summing the ways gives the parse-tree count

Each production of A that succeeds from pos contributes its own set of (end, ways) pairs. Two different productions reaching the same end position are two different subtrees for A — so their way-counts add. Within a production, the RHS symbols' counts multiply (every combination of sub-parses is a distinct tree). Add across alternatives, multiply along a sequence: the count at end-of-input is exactly the number of parse trees.

Limits — what this module cannot do yet

Can't do yet

  • The full LL(k) condition with FOLLOW_k for nullable alternatives (the fixtures don't need it; the check bails rather than answer wrong).
  • Actually build the LL(*) lookahead DFA — described, not implemented (ANTLR's core; a project on its own).
  • Memoize the backtracking recognizer — that's packrat parsing, Appendix X2.
  • Handle left recursion in the recognizer (would loop forever).
  • PEG-style ordered choice, where the *first* match wins and ambiguity is impossible by definition (Appendix X1).

Can do

  • Compute FIRST_k for any k, as a fixed point.
  • Find the minimal k (or report "none") for a grammar.
  • Show a grammar that is LL(2) but not LL(1), and one that is no LL(k).
  • Count the parse trees of an ambiguous grammar exactly.
  • Measure backtracking work — exponential vs linear — on real inputs.

Getting a blank or broken result?

FIRST_1 has phantom tokens — an empty not-yet-computed nonterminal set is being treated as nullable; it should contribute nothing.
minLL says 1 for a non-LL(1) grammar — use the exact PREDICT check for k=1, not the FIRST_k test.
Recognizer never returns — the grammar has left recursion.
Parse counts overflow — expected on an exponential grammar; cap and report.

07

Brain Exercise

(1) Grammar A → a a b | a a c | a d. Is it LL(1)? LL(2)? LL(3)? Can left factoring make it LL(1)? (2) The equiv grammar has 2ⁿ parse trees for xⁿ y. What single change to the grammar makes it unambiguous (one tree) while generating the same language?

Answers

(1) Not LL(1): all three FIRST_1 = {a}. Not LL(2): a a b and a a c both have FIRST_2 = {a a}. LL(3): FIRST_3 = {a a b}, {a a c}, {a d} — pairwise disjoint. So minimal k = 3. But left factoring makes it LL(1) with no lookahead cost: A → a A', A' → a A'' | d, A'' → b | c. Prefer factoring when the shared part is a literal prefix of one rule.

(2) Merge the two equivalent alternatives. A → x A | y (drop B and C entirely, or make just one of them). Now xⁿ y has exactly one derivation. The ambiguity was purely the pointless choice between x B and x C.

08

There Are No Dumb Questions

If LL(2) is more powerful, why is LL(1) the default?

LL(1) tables are small (one lookahead column) and the theory is clean. Most practical constructs are LL(1) after left-factoring and left-recursion removal. LL(2+) tables grow with k, and the cases that truly need k > 1 are rare enough that hand-written parsers just special-case them with a two-token peek at that one spot.

Is LL(2) strictly more powerful than LL(1)?

Yes — there are languages with an LL(2) grammar and no LL(1) grammar at all (not just "this particular grammar isn't LL(1)"). And LL(k+1) > LL(k) for every k. LL(*) is more powerful still, and LR (Part IV) is more powerful than all of them.

What does ANTLR actually do?

ANTLR 4 uses adaptive LL(*) (ALL(*)): at each decision it simulates the grammar forward, building a DFA over the lookahead on the fly, reading as many tokens as needed. It caches these DFAs. It falls back to full-context prediction (essentially backtracking) only for genuinely ambiguous spots, and then reports the ambiguity.

Backtracking is exponential — is it ever used?

Yes, with memoization it's linear: that's packrat parsing (Appendix X2), the engine behind PEG parser generators. Memoize every (rule, position) result and each is computed once. The cost is linear space.

How do I know if my grammar needs more than LL(1)?

Run Module 28's tool. If section 7 says "not LL(1)" and left-factoring + left-recursion removal don't fix it, you're looking at LL(k), LL(*), LR, or a grammar redesign.
