Lexical Errors &Recovery

Module 16's lexer stops at the first bad character. This one reports it, resynchronizes, and keeps going — so a single scan finds every lexical error, not just the first. Two strategies: one ERROR per bad character, or one per garbage run.

The payoff

@x@y@ — Module 16 throws at position 0 and you learn nothing else. With recovery: 3 errors, at positions 0, 2, 4, plus the tokens x and y in between.

01

The Big Analogy — the proofreader who doesn't quit

A junior proofreader circles the first typo on your page and hands it back: "fix this, then I'll re-read." Ten typos, ten rounds, ten days.

A good proofreader marks every mistake in one pass. And when they hit a stretch of genuine gibberish — a smudge, a coffee stain, three lines of keyboard mash — they don't stop. They draw a box around it, write "??", and resume reading from the next real word.

That's error recovery. PANIC_ONE is circling each bad character individually — precise, but a smudge covering five characters gets five circles. PANIC_TO_SYNC is the box-and-"??" move: one mark around the whole garbled run, then pick up at the next thing that could plausibly be a word.

"Panic mode" is the actual textbook name — the scanner panics, throws away input in a hurry, and scrambles back to solid ground.

02

What Happens, Step by Step

  1. At pos, run the combined-DFA maximal-munch match (Module 16). If it consumed ≥ 1 character → emit the token (unless %skip), advance, repeat.
  2. No progress (lastPos ≤ pos) → a lexical error at pos.
  3. Recover:
    • PANIC_ONE: errEnd = pos + 1.
    • PANIC_TO_SYNC: advance errEnd from pos + 1 while the character there is not a sync point — i.e. not in the alphabet, or the DFA can't start a token there (longestToken(input, errEnd)[0] ≤ errEnd).
  4. Record LexError(pos, errEnd, input[pos..errEnd]); emit an ERROR token for that span; set pos = errEnd.
  5. Continue. errEnd always started at pos + 1, so the scanner always makes progress.

The state, drawn

Both strategies on x@@@#y (alphabet has no @ or #)

  pos:   0   1   2   3   4   5
  input: x   @   @   @   #   y

  PANIC_ONE:
    pos 0: match ID "x"            → pos 1
    pos 1: no match → ERROR "@" @1 → pos 2
    pos 2: no match → ERROR "@" @2 → pos 3
    pos 3: no match → ERROR "@" @3 → pos 4
    pos 4: no match → ERROR "#" @4 → pos 5
    pos 5: match ID "y"            → done
    tokens: ID ERROR ERROR ERROR ERROR ID     errors: 4

  PANIC_TO_SYNC:
    pos 0: match ID "x"                      → pos 1
    pos 1: no match. skip while not a sync point:
           input[2]='@' (not in alphabet) → skip
           input[3]='@' → skip
           input[4]='#' → skip
           input[5]='y' → IN alphabet AND ID starts here → STOP
           ERROR "@@@#" @1                   → pos 5
    pos 5: match ID "y"                      → done
    tokens: ID ERROR ID                      errors: 1  (positions 1..4)

Recovery keeps the good tokens — let.x=@=9

  KW_LET "let" @0   ID "x" @4   ASSIGN "=" @5   ERROR "@" @6   ASSIGN "=" @7   NUM "9" @8

  the '@' is isolated; everything before and after it still tokenises.
  Module 16 would have stopped at position 6 and never seen the "= 9".
04

The Code, Explained

The recovery loop

The sync check is just "can a token start here?"

longestToken(lex, input, errEnd)[0] > errEnd — the maximal-munch match at that position has positive length. No separate "first character of any pattern" set to build and keep in sync; the scanner already has the function. A real parser's sync set is a hand-picked list of boundary tokens (;, }, )) — see the Brain Exercise.

05

Limits — what this module cannot do yet

Can't do yet

  • Suppress cascading follow-on errors (a compiler caps at ~20 and hides errors near a previous one).
  • Repair — insert a missing quote, fix a typo'd character (least-cost repair, Appendix X9).
  • Line-level recovery (no newlines in the toy language; same shape, sync set = {newline}).
  • Recover at the parser level — that's Modules 22 and 27.
  • Pick a good sync set automatically — the parser's FOLLOW sets do that (Module 27).

Can do

  • Report every lexical error in a single scan, with exact positions.
  • Keep the token stream gap-free with ERROR tokens.
  • Recover one-character-at-a-time (PANIC_ONE) or one-run-at-a-time (PANIC_TO_SYNC).
  • Resynchronize on "a character where a token can start."
  • Preserve all valid tokens before and after the garbage.

Getting a blank or broken result?

Recovery loops forever — errEnd must start at pos + 1; one character is always consumed.
PANIC_TO_SYNC makes one giant ERROR to EOF — no later character can start a token. That's correct; the rest is garbage.
A valid-looking character is flagged — it isn't in the spec's alphabet (no rule mentions it). Add a rule.

07

Brain Exercise

(1) Our sync set is "a character where a token can start." A parser's panic-mode recovery syncs on ;, }, ) specifically. Why those? (2) What's the failure mode of a sync set that's too small? Too large?

Answers

(1) ;, }, ) mark the end of a syntactic unit — a statement, a block, a parenthesised group. Recovering there means the parser resumes at a clean boundary where it knows what to expect next, instead of somewhere in the middle of a broken expression. They're also frequent enough that recovery doesn't discard huge spans.

(2) Too small (rare sync tokens): one typo makes the scanner skip most of a function looking for the next sync point — you get one error and lose all the real content after it. Too large (almost anything syncs): recovery lands immediately, often still inside the broken construct, so the parser mis-reads the next few tokens and emits a cascade of spurious follow-on errors. The craft is choosing tokens that are both common and genuinely terminal.

08

There Are No Dumb Questions

Why emit an ERROR token and keep a separate error list?

The token stream stays gap-free — every source character belongs to some token — so a downstream parser can walk it without special-casing holes. The ordered errors list is the human diagnostic (positions, messages). Different consumers, different shapes.

Is "panic mode" really the technical term?

Yes — it's in the Dragon Book. The scanner (or parser) "panics": it abandons its current attempt, discards input as fast as it can, and races to a synchronizing token where it can resume. Crude but robust, and still the default in most production compilers.

PANIC_ONE just produces more errors. Why keep it?

It's the most faithful ("here is literally every character I couldn't handle") and the simplest to reason about. For an editor drawing red squiggles, per-character marks can be exactly what you want. It's a genuine trade-off against PANIC_TO_SYNC's fewer-but-wider errors.

After recovery, compilers often spew nonsense errors. Why?

Recovery guesses about structure, and if it guesses wrong the next tokens are interpreted in the wrong context — a missing } can make every following declaration look misplaced. Mitigations: suppress errors within k tokens of a previous one, cap the total (~20), or use error-correcting recovery (Burke–Fisher) that tries small insertions/deletions to minimise disruption.

Does the parser recover too, or just the lexer?

Both. Module 22 gives the LL parser panic-mode recovery (sync on FOLLOW-set tokens), and Module 27's LR parser has its own. Same idea one layer up: report, discard to a trusted token, resume.
