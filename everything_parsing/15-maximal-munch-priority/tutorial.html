Maximal Munch &Token Priority

Two rules turn a pile of token patterns into a scanner. Longest match wins — iffy is one identifier, not if + fy. Ties go to the pattern declared first — that is exactly how if becomes a keyword and not an identifier.

The mechanism, in one sentence

Run the pattern's DFA over the input, remember the last position it was accepting, and when it gets stuck, back up to that mark and emit a token.

01

The Big Analogy — reading a long word aloud

Read this out loud: understandable. You didn't say "under", "stand", "able" — three real words. You read the whole thing, because as long as the letters keep forming something valid, you keep going. You only commit to a word when the next letter can't continue it, or you hit a space.

That is maximal munch. The scanner extends the current token as far as the characters still form some valid token, and takes the longest such run. iffy: after if it could stop (that's the keyword) — but iffy is also valid (an identifier), and longer, so it keeps going.

Now: some words are spelled the same. "bank" — river's edge, or money? A dictionary lists one sense first and calls it primary. Token priority is that list: when two patterns match the same length, the one written first in your rule list wins. if matches the keyword pattern and the identifier pattern, both at length 2 — the keyword pattern is listed first, so if is a keyword.

And the order is fixed: length first, list-order only to break a tie. Priority never makes a shorter match win.

02

What Happens, Step by Step

  1. Compile each token pattern to a minimal DFA (Modules 12–14).
  2. At position pos, for every pattern:
    • state = dfa.start; lastAccept = -1
    • for i = pos, pos+1, …: step the DFA on input[i]; if the character isn't in the alphabet, stop; if the new state is accepting, lastAccept = i + 1
    • the pattern's match length is lastAccept - pos (or 0 if it never accepted)
  3. RULE 1: the token's length = the maximum match length over all patterns.
  4. RULE 2: among patterns achieving that maximum, the token's kind = the first-declared one. (In code: only update the best on len > bestLen, strictly.)
  5. If the best length is 0 → lexical error at pos. Otherwise emit the token and set pos += length.
03

The state, drawn

Scanning iffy — two patterns, two last-accept marks

  KW_IF  = if
  ID     = (i|f|x|y)(i|f|x|y)*

  pos:      0   1   2   3
  input:    i   f   f   y

  KW_IF DFA:  --i-->  --f-->  (ACCEPT)  --f-->  (stuck)
              last accept = position 2   → match "if", length 2

  ID DFA:     --i--> (ACCEPT) --f--> (ACCEPT) --f--> (ACCEPT) --y--> (ACCEPT)
              last accept = position 4   → match "iffy", length 4

  RULE 1:  max(2, 4) = 4   →   the token is 4 characters
  RULE 2:  only ID reached length 4   →   ID "iffy"

The tie — if

  input:  i f          KW_IF: last accept = 2      ID: last accept = 2

  RULE 1:  max(2, 2) = 2
  RULE 2:  KW_IF and ID both reached 2  →  tie  →  KW_IF   (declared at index 0 < 1)

  swap the declaration order  →  ID would win  →  "if" lexes as an identifier

Operators — ==

  ASSIGN = ==     EQ = =

  input:  = =      EQ: accepts at length 1        ASSIGN: accepts at length 2

  RULE 1:  max(1, 2) = 2   →   ASSIGN "=="        (not EQ + EQ)
  "===" then lexes as  ASSIGN "==" @0  ,  EQ "=" @2
04

The Code, Explained

The last-accept mark — longestAccept

The two rules, in one comparison

for (int i = 0; i < rules.size(); i++) {
  int len = ...longestAccept(...);
  if (len > bestLen) {        // STRICTLY greater
    bestLen = len;              //   → RULE 1: a longer match replaces the best
    bestRule = i;               //   → RULE 2: on a tie (len == bestLen) the earlier i already sits in bestRule
  }
}

That one word — strictly greater — is the entire priority rule. Loop the rules in declaration order and the first to reach the winning length keeps it.

Why lastAccept, not firstAccept

Stop at the first accepting state and iffy tokenises as the keyword if. Stop at the first accepting state and == is two =. The scanner has to keep running past a valid token to see if a longer one is coming, then rewind. This is the same "read ahead, then retract" the input buffer (Module 9) was built for.

05

Limits — what this module cannot do yet

Can't do yet

  • Scan in O(input) total — one DFA per rule means O(rules × input) (Module 16 combines them).
  • Read a token-spec file — the rules are hard-coded (Module 16).
  • Skip whitespace or comments — no such rule here; a space is an error.
  • Attach line/column to tokens (the trivia layer, later).
  • Reject a pattern that matches the empty string at load time (Module 16's "epsilon is not a token").

Can do

  • Apply maximal munch: the token is the longest prefix any pattern matches.
  • Apply priority: ties go to the first-declared pattern.
  • Trace the last-accept mark for any pattern on any input.
  • Tokenise a whole string, or fail with an exact error position.
  • Show that swapping rule order changes which token if becomes.

Getting a blank or broken result?

A keyword lexes as an identifier — the identifier rule is declared before the keyword rule. Keywords first.
iffy → if + fy — you compared first match, not longest. Track the last-accept position.
lexical error at position N — the character at N is in no pattern's alphabet. Add a rule (whitespace, punctuation) — Module 16 handles the full spec.

07

Brain Exercise

(1) In a language with both -- (decrement) and - (minus), maximal munch tokenises a---b as a -- - b — which is a syntax error. A human clearly meant a - (--b) or (a--) - b. Should the lexer be smarter? (2) One DFA per rule is O(rules × input) per token. How does a real lexer get O(input) total?

Answers

(1) No. The lexer runs before and independent of the parser — making it "smart" about intent means feeding parser context back into lexing, which destroys the clean phase separation and can make lexing ambiguous. Real languages either accept the munch and require a space (a-- -b), or add a narrow parser-level fix-up. The famous case: C++ vector<vector<int>> — the >> used to munch as a shift operator and be an error; C++11 added a parser rule to re-split >> into two > in a template context. That special case exists precisely because everyone agrees the lexer itself must stay dumb.

(2) Combine all the rules into one DFA (Module 16): take the union of every rule's NFA, tag each accepting state with which rule it came from (lowest rule index = highest priority), then determinise. Now one left-to-right pass — one DFA step per character — tracks all patterns at once, and each accepting DFA state already knows the winning token kind. Total cost: O(input), regardless of how many rules there are.

08

There Are No Dumb Questions

Why longest match and not shortest?

Shortest would make nearly every identifier one character long and 1234 four separate number tokens. Longest is what matches how people read — PARKING is one word even though PARK is also a word.

The if keyword — why not lex everything as an identifier and look up keywords in a table?

That's the other standard implementation — the "reserved word trick" (Module 18). Lex if as an identifier, then check a keyword table and re-label it. It's equivalent to putting the keyword rule first, and often simpler (one identifier DFA instead of one per keyword). Both are used in real lexers.

What if I want the shorter match in some case?

You don't fight maximal munch — you restructure the token set. If .. and ... are both tokens, .... munches as ... then .; if that's wrong for your language, either forbid .... or make the range operator a parser-level construction from single dots.

The lexer errored on a space. Isn't whitespace normal?

A real lexer has a whitespace rule that matches spaces/tabs/newlines and then either emits a "trivia" token (kept, attached to the next real token) or produces nothing (skipped). This demo deliberately has no such rule so the error path is visible; Module 16 adds one.

Can maximal munch loop forever?

Only if a token pattern matches the empty string — e.g. you wrote x* as a whole token. Then every position "matches" length 0, the scanner advances by 0, and spins. The bestLen == 0 → error guard here catches it; Module 16 rejects such a pattern when the spec is loaded (CSE 340's "epsilon is not a token").
