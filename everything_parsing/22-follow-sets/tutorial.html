Everything Parsing · Module 22 · Part III — Top-Down Parsing

FOLLOW Sets

FIRST answers "what can start this nonterminal?" FOLLOW answers "what can come right after it?" You need FOLLOW to decide a nullable production: if A → ε is on the table, the parser takes it only when the next token is something that could legitimately follow A. Three rules, one more least-fixed-point iteration — this time with FIRST as an input and the $ end-marker as a real element.

The payoff

The dangling-else grammar: FOLLOW(S) needs FOLLOW(X), which needs FOLLOW(S) — a cycle. The iteration doesn't care. Seed $, run two passes, both settle on { else, $ }.

01

The Big Analogy — who's next in the queue

You're a receptionist calling people up. Someone's turn ends. Who's allowed to be next? It depends on where in the process that person was standing. If they were in the middle of the "forms" section, the next person is whoever starts the "documents" section. If they were the last step of a whole procedure, then "next" is whoever the enclosing procedure would call next — you have to look one level out.

FOLLOW(A) is exactly that guest list: the set of tokens allowed to appear immediately after A finishes. Rule 2: if the grammar has B → … A β …, then whatever can start β is on A's list. Rule 3: if β can be empty (or A is literally the last symbol of that rule), then A inherits B's whole guest list — "look one level out." Rule 1: the very first procedure's list always includes $, "the building is closing" — nothing more comes.

The lists reference each other (A inherits from B, and maybe B inherits from A), so you can't fill them in one at a time. You post everyone's list empty, walk the rules adding names, and walk again, until a full lap adds nobody new.

02

What Happens, Step by Step

  1. Compute FIRST and nullable for the grammar (Module 21). Hold them fixed.
  2. Initialise FOLLOW(A) = {} for every nonterminal, then add $ to FOLLOW(start).
  3. Pass over every production B → X₁ … Xₙ. For each position i where Xᵢ is a nonterminal, let β = X₍ᵢ₊₁₎ … Xₙ (possibly empty):
    • add FIRST(β) \ {ε} to FOLLOW(Xᵢ) (rule 2);
    • if β is nullable — ε ∈ FIRST(β), which includes β empty — add all of FOLLOW(B) to FOLLOW(Xᵢ) (rule 3).
  4. If any set changed this pass, go again. Otherwise stop — the sets are the least fixed point.

Note rule 3 reads FOLLOW(B) as it stands right now, mid-iteration. That's fine: the sets only grow, so a value read early is never wrong, just possibly incomplete — and the next pass catches up.

The cycle — danglingelse.grammar

  S -> if b then S X | other        X -> else S | epsilon

  round 0:  FOLLOW(S) = { $ }        FOLLOW(X) = { }        ($ seeded)

  round 1, production S -> if b then S X:
    S at pos 3, beta = "X".  FIRST(X) = { else epsilon }.
       rule 2: FOLLOW(S) += { else }                 -> FOLLOW(S) = { else $ }
       rule 3: X nullable, FOLLOW(S) += FOLLOW(S)    (no-op this pass)
    X at pos 4, beta = "" (empty, nullable).
       rule 3: FOLLOW(X) += FOLLOW(S) = { else $ }   -> FOLLOW(X) = { else $ }

  round 2:  no change  ->  STOP.   FOLLOW(S) = FOLLOW(X) = { else $ }

Operators climbing the primed chain — expr.grammar

  F -> ( E )      contributes ')' to FOLLOW(E)
  Tp -> * F Tp    contributes '*' to FOLLOW(F); Tp nullable so FOLLOW(Tp) flows to FOLLOW(F)
  Ep -> + T Ep    contributes '+' to FOLLOW(T); Ep nullable so FOLLOW(Ep) flows to FOLLOW(T)
  E -> T Ep       Ep is last  ->  FOLLOW(Ep) = FOLLOW(E)

  FOLLOW(E)  = { ) $ }
  FOLLOW(Ep) = { ) $ }
  FOLLOW(T)  = { ) + $ }
  FOLLOW(Tp) = { ) + $ }
  FOLLOW(F)  = { ) * + $ }
04

The Code, Explained

Rule 3 with β empty is the common case

When A is the last symbol of B's right-hand side, β is the empty sequence. FIRST(empty) = {ε}, so rule 2 adds nothing and rule 3 fires: FOLLOW(A) ⊇ FOLLOW(B). That's "whatever follows the whole B also follows its final piece" — the single most frequent FOLLOW contribution, and the one that makes the sets circular.

Why $ genuinely matters

Drop rule 1 and FOLLOW(start) begins empty. Now take a grammar whose start symbol is nullable, or whose last nonterminal has an ε production. The PREDICT set of that ε production is FIRST(ε) \ {ε} ∪ FOLLOW(A) = FOLLOW(A) — and if that's empty, the parser has no token on which it will choose "take ε and return." It gets stuck at end of input on a perfectly legal empty derivation. $ is the token that says "input's done, finishing here is fine." The driver appends a literal $ to the stream (Module 26) so this is a real match, not a special case.

Getting a blank or broken result?

FOLLOW(start) has no $ — seed it before iterating.
A trailing nonterminal's FOLLOW is too small — rule 3 for empty β: FOLLOW(A) ⊇ FOLLOW(B).
ε leaked into a FOLLOW set — rule 2 adds FIRST(β) \ {ε}, not raw FIRST(β).
Dangling-else sets don't match — you stopped after one pass; iterate to convergence.

07

Brain Exercise

(1) Grammar S → A B, A → a, B → b | ε. Compute FOLLOW(A) and FOLLOW(B). Where does $ end up? (2) Add C → S d and make C the start symbol. Now recompute FOLLOW(S), FOLLOW(A), FOLLOW(B).

Answers

(1) S is start, so FOLLOW(S) = {$}. S → A B: A at pos 0, β = B, FIRST(B) = {b, ε} → rule 2 adds {b} to FOLLOW(A); B nullable → rule 3 adds FOLLOW(S) = {$}. So FOLLOW(A) = {b, $}. B at pos 1, β empty, nullable → rule 3: FOLLOW(B) ⊇ FOLLOW(S) = {$}. FOLLOW(B) = {$}.

(2) Now C is start: FOLLOW(C) = {$}. C → S d: S at pos 0, β = d, FIRST(d) = {d} → FOLLOW(S) = {d} (no more $, because S is never last anywhere). Then FOLLOW(A) = {b, d} and FOLLOW(B) = {d} — everything that had $ via FOLLOW(S) now has d instead.

08

There Are No Dumb Questions

Is ε ever in a FOLLOW set?

No. FOLLOW sets contain real terminals and $. Rule 2 explicitly strips ε from FIRST(β) before adding. "A can be followed by nothing" is expressed as $ ∈ FOLLOW(A), not ε.

Why compute FIRST completely before starting FOLLOW?

FOLLOW depends on FIRST but FIRST never depends on FOLLOW — the dependency is one-way. So there's nothing to gain from interleaving them, and a finished FIRST makes the FOLLOW loop a single clean iteration.

Rule 3 reads FOLLOW(B) while it's still being built. Isn't that a bug?

No — it's the point of the iteration. The sets only grow, so a value read early is a subset of the final value, never wrong. Any element missed because FOLLOW(B) wasn't done yet gets added on the next pass. The loop keeps going until a full pass adds nothing, which guarantees everything propagated.

What actually uses FOLLOW?

The PREDICT set of any nullable production (Module 20), which becomes a row of the LL(1) table (Module 25). Also panic-mode error recovery (Module 27) uses FOLLOW sets as the tokens to skip to. In LR parsing (Part IV) SLR reductions are decided by FOLLOW.

Can FOLLOW(A) and FIRST(A) overlap?

Yes, freely — they answer different questions. In the expression grammar FIRST(F) = { ( id num } and FOLLOW(F) = { ) * + $ } happen to be disjoint, but e.g. a grammar with A both starting and following some construct would have ( or an operator in both.
