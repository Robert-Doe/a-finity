Everything Parsing · Module 18 · Part II — Lexical Analysis

Practical Lexemes

The regex-to-DFA pipeline (Modules 12–16) handles the easy 90% of a real token set. This module hand-codes the awkward 10%: the reserved-word trick, string escapes, a number state machine — and nested comments, which are provably beyond regular and need one integer of extra memory a DFA doesn't have.

The payoff

a /* outer /* nested */ still comment */ b — a flat /\*.*\*/ regex closes at the first */ and leaves still comment */ b dangling. The hand-coded scanner with a depth counter consumes the whole thing and returns exactly a and b.

The Big Analogy — the receptionist and the specialist

Picture a clinic front desk. Most arrivals are routine: the receptionist (the combined DFA) checks them in from a list and waves them through. Fast, table-driven, no thinking required.

But a few cases need a specialist. Someone shows up speaking in a code that has to be translated before it means anything — that's a string literal, where \n on the page has to become an actual newline in the record. Someone hands over a form with boxes nested inside boxes — that's a nested comment, and to know when you're finally out you have to count how deep you went in. And there's the person whose name is on the VIP list even though they look like an ordinary walk-in — that's a keyword: you check everyone in as a regular identifier first, then glance at the short VIP list to see who gets a different badge.

The receptionist can't do any of these from a checklist. The counting one in particular is not something a finite checklist can ever do — no matter how long the list, nesting can go one level deeper. That's the whole "not regular" point of this module, and it's why we drop down to a hand-written scanner here.

02

What Happens, Step by Step

lex(src) runs a single loop over the cursor. At each position it dispatches on the first character:

  1. whitespace → advance(), loop.
  2. // → consume to \n or EOF; the \n is not eaten.
  3. /* → skipBlockComment(): depth = 1; on a further /* depth++, on */ depth--; stop when depth == 0. EOF with depth > 0 → "unterminated block comment opened at position N".
  4. letter or _ → identifierOrKeyword(): scan [A-Za-z0-9_]*, then KEYWORDS.contains(text) ? "KW_" + text.toUpperCase() : "ID".
  5. digit → number(): see §03.
  6. " → string(): scan char-by-char, decoding escapes into the value; stop at ", \n, or EOF. Unterminated → an error at the opening position + a STRING? token.
  7. + - * = → an OP token.
  8. anything else → a lexical error at pos; advance one character so the loop always makes progress (Module 17's rule).

04

The Code, Explained

The reserved-word trick

Why not a DFA per keyword?

You could add let, if, … as their own token rules (Module 15's priority ordering breaks the ties). But that's seven more NFAs to union in, and every new keyword means rebuilding the combined automaton. The trick needs one identifier scanner plus a hash-set lookup; a new keyword is a one-word edit. Every production compiler — clang, rustc, go/scanner — does it this way.

The nested-comment depth counter

This int depth is the whole point

A DFA has a fixed, finite set of states. Nested comments require remembering a count that has no upper bound — /* /* /* … */ */ */ can nest arbitrarily deep. By the pumping lemma (Module 7), the language /*ⁿ …*/ⁿ is not regular: it's the same shape as aⁿbⁿ. So no regex, no matter how clever, can match balanced nested comments. One int of unbounded memory — a pushdown-automaton move — is the minimum needed, and that's exactly what the counter is. Languages differ on this: C block comments do not nest (so a regex works), but Rust, Swift, D, and Kotlin comments do.

Limits — what this module cannot do yet

Can't do yet

  • Line/column tracking — positions here are raw character offsets (added when we build the real front end).
  • Multi-line strings (""", backticks), raw strings, string interpolation.
  • Numeric underscores (1_000_000), binary/octal literals, arbitrary-precision integers.
  • Unicode identifiers beyond ASCII letters (Module X13 does the full input layer).
  • Doc comments (/** */, ///) carried through as tokens for tooling.
  • Feed this stream to a parser — that starts in Module 19.

Can do

  • Lex keywords via one identifier scanner + a table (add a keyword in one edit).
  • // line comments and /* */ block comments.
  • Nested /* /* */ */ comments — correctly, with a depth counter.
  • String literals with \n \t \" \\ \uXXXX, decoded into the value.
  • Integers, floats (decimal + exponent), and 0x hex, as one state machine.
  • Report unterminated comments and strings at their opening position, stream still gap-free.

Getting a blank or broken result?

A keyword lexes as ID — it isn't in the KEYWORDS set. Add it; that's the whole trick.
1e becomes one token — you didn't retract when e isn't followed by a digit. Save pos before consuming e; restore if no exponent digit follows.
Nested /* */ leaves trailing garbage — you're stopping at the first */. Use depth++ on /*, depth-- on */, stop at depth == 0.
"a\nb" keeps a literal backslash-n — you appended the escape characters instead of the decoded one. On \, read the next char and append what it means.

07

Brain Exercise

(1) C block comments do not nest. Write the plain regular expression that matches one C block comment. Why does nesting break it? (2) Our scanner stops a string at a bare \n. What would change if the language allowed "..." to span lines — and what new error would you now be unable to report well?

Answers

(1) /\* ( [^*] | \*+[^*/] )* \*+ / — "slash-star, then any run that never completes a */, then */." It's regular because "have I seen */ yet" is a single bit of state. Nesting breaks it because you'd need to match /* and */ in balanced pairs and count the imbalance — and "count to an unbounded number" is exactly what a finite automaton cannot do (pumping lemma, Module 7). You need a stack, or here, one counter.

(2) You'd drop \n from the stop set and only end on " or EOF. The cost: a missing closing quote now silently swallows the rest of the file as string content, and your "unterminated string" error points at EOF instead of at the real mistake. Multi-line-string languages mitigate this with a distinct delimiter (""", backticks) so an accidental single " still terminates at end of line.

08

There Are No Dumb Questions

If nested comments aren't regular, is my whole lexer "not regular" now?

No — only the block-comment sub-scanner. Everything else (identifiers, numbers, strings with a finite escape set, operators) is still regular. The practical lesson is that a real lexer is a regular core with a few hand-coded exceptions bolted on exactly where the theory says you need them.

Why decode \n in the lexer instead of leaving it for the parser?

The value a later stage wants is the string's meaning, not its source spelling. Decoding once, here, means every consumer gets the real characters and nobody re-implements escape rules. The source spelling is still recoverable from the token's span if a tool needs it.

Why emit a STRING? token for an unterminated string at all?

Module 17's principle: the token stream stays gap-free so a parser can walk it without special-casing holes. STRING? carries the partial value and flags "not closed," and the real diagnostic lives in the separate errors list.

Is the reserved-word trick ever wrong?

Only for "contextual keywords" — words that are keywords in one position and identifiers in another (async, yield, await in some languages, record/sealed in Java). Those are resolved by the parser, not the lexer: the lexer still hands them over as ID and the grammar decides.

Why does 12. lex as INT 12 and not FLOAT 12.0?

Because . is also member access in most real languages, so list.map and 12.toString() have to work. We only join . to a number when a digit follows it. A language without member-access dots (or one that requires a digit after the point) can make the other choice.
