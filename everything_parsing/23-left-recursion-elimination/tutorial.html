Left Recursion Elimination

Module 19 said a rule like E → E + T is fatal to recursive descent — parseE calls parseE with the cursor unmoved, forever. This module removes it mechanically. Direct left recursion (A → A α | β) has a two-line rewrite. Indirect left recursion (A → B γ, B → A δ) needs Paull's algorithm: impose an order, substitute, then apply the two-line rewrite. Same language out; recursion now grows rightward.

The payoff

Feed in the natural grammar E → E + T | T, T → T * F | F. Out comes E → T E', E' → + T E' | ε, T → F T', T' → * F T' | ε — the exact grammar Modules 19–22 have been running. It was never invented; it's this transform applied to the obvious one.

The Big Analogy — folding a chain of paperclips

You've got a chain of paperclips and you want to describe how to build it. The left-recursive description is: "a chain is a chain, plus one clip on the right." True, but useless as instructions — to start building "a chain" you first need "a chain," which needs "a chain"… you never pick up a physical clip.

The right-recursive description of the exact same object: "a chain is one clip, followed by the rest of the chain." Now you can start: grab a clip, then recurse on a strictly shorter remainder. It bottoms out.

The transform swaps one description for the other without changing what gets built. It splits each rule into "the part that isn't recursive" (β — the actual first clip) and "the part that is" (α — what repeats), then rebuilds: A → β A', A' → α A' | ε. Read that as "one β, then zero or more αs" — the loop form from Module 8's EBNF.

Indirect recursion is when the chain-defines-chain loop goes through an intermediary: "a chain is a rope plus a clip; a rope is a chain plus a knot." Paull's algorithm untangles it by inlining the rope's definition into the chain's, collapsing the detour into direct recursion you can then rewrite.

02

What Happens, Step by Step

Direct — eliminateDirect(A)

  1. Split A's productions: α-list = the tails of rules A → A α; β-list = every other rule.
  2. If the α-list is empty, A isn't directly left-recursive — return unchanged.
  3. Make a fresh nonterminal A'.
  4. New A rules: A → β A' for each β.
  5. New A' rules: A' → α A' for each α, plus A' → ε.

Indirect — paull(G)

  1. Order the nonterminals A₁ … Aₙ (first-appearance order).
  2. For i = 1 … n:
    • For j = 1 … i−1: for every rule Aᵢ → Aⱼ γ, delete it and add Aᵢ → δ γ for each rule Aⱼ → δ.
    • Now run eliminateDirect(Aᵢ).
  3. Invariant after step i: no Aᵢ production starts with any of A₁ … Aᵢ. After step n, nothing is left-recursive.

The state, drawn

Direct — E → E + T | T

  rules of E:  [E + T]   [T]
               ^^^^^^^ starts with E  -> alpha = "+ T"
                       ^^^ doesn't    -> beta  = "T"

  A' = E'
  E  -> T E'                        (beta  "T"  followed by E')
  E' -> + T E' | epsilon            (alpha "+ T" followed by E', plus epsilon)

  same for T -> T * F | F  =>  T -> F T' ,  T' -> * F T' | epsilon

Indirect — S → A a | b, A → A c | S d | e

  order: S, A

  i = S:  no j below it. eliminateDirect(S): rules [A a], [b] — neither starts
          with S. nothing to do.

  i = A:  j = S. rules of A: [A c], [S d], [e]
            [A c]  starts with A, not S  -> keep
            [S d]  starts with S         -> substitute S -> A a | b :
                                            add [A a d], [b d]
            [e]    keep
          A now: [A c], [A a d], [b d], [e]
          eliminateDirect(A):
            alpha = { "c", "a d" }      beta = { "b d", "e" }
            A  -> b d A' | e A'
            A' -> c A' | a d A' | epsilon

  final:  S  -> A a | b
          A  -> b d A' | e A'
          A' -> c A' | a d A' | epsilon        (Dragon Book 4.18)

Direct elimination

Paull's substitution

Why the order matters

Paull's substitution only replaces Aⱼ for j < i — lower in the order. That's what guarantees progress: after you've cleaned A₁ … Aᵢ₋₁, none of them can start with something that loops back, so inlining them into Aᵢ strictly reduces the tangle. A different order gives a different (still correct) grammar; a random substitution with no order can loop.

Limits — what this module cannot do yet

Can't do yet

  • Keep the parse-tree shape / associativity — that's gone by construction (recover it in Module 39, or use the loop form from Module 19).
  • Left-factor the shared prefixes Paull can introduce — Module 24.
  • Nullable-prefix left recursion (A → B A, B → ε) — needs Module 21's nullable; folded into the Project 2 tool (Module 28).
  • Prove language preservation in general — we check it empirically up to length 6.
  • Minimise the number of new nonterminals / productions (Paull can blow up on adversarial grammars).

Can do

  • Eliminate direct left recursion with the standard rewrite.
  • Eliminate indirect left recursion with Paull's algorithm.
  • Leave a non-left-recursive grammar untouched.
  • Preserve the language (verified by bounded enumeration).
  • Produce exactly the Module 19–22 expression grammar from the natural one.

Getting a blank or broken result?

Still left-recursive after the transform — you did direct only; run the full Paull loop (substitute lower nonterminals first).
Language changed — a dropped alternative. Every non-recursive β gets a β A'; every recursive α gets an α A'; and A' must have its ε.
Enumeration hangs — the grammar still has a no-progress cycle; that's the bug the transform should have fixed.

07

Brain Exercise

(1) Eliminate direct left recursion from L → L , e | e (a comma-separated list). What does L' look like? (2) The result is right-recursive, so a , b , c parses as a , (b , c). For a list that's usually fine — but name one situation where you'd care, and what you'd do about it.

Answers

(1) α = ", e", β = "e". So L → e L' and L' → , e L' | ε. In loop form: L → e { , e }.

(2) If the list elements have side effects and evaluation order matters (e.g. print(a), print(b), print(c) in a language where the parser drives evaluation), right-nesting could reverse the order — or at least make left-to-right handling awkward. The fix: don't build a nested tree at all; write L' as a while loop that appends each element to a flat list as it's parsed. Same grammar, iterative code.

08

There Are No Dumb Questions

If the transform changes the parse trees, how is the language the same?

The set of strings generated is identical — that's the language. Which tree a given string gets is a different question. Left-recursive E → E + T gives a+b+c a left-leaning tree; E → T E' gives it a right-leaning one. Both grammars generate a+b+c; they just structure it differently. Module 39 restores the structure you want when building the AST.

Does every grammar have a non-left-recursive equivalent?

Every context-free grammar without ε-productions and without cycles (A ⇒⁺ A) does — Paull's algorithm always terminates and produces one. Grammars with ε-rules need those handled first (or the nullable-aware version of the algorithm).

Why not just always write the loop form and skip the grammar rewrite?

That's exactly what hand-written parsers do (Module 19). The formal rewrite matters when a tool consumes the grammar — a parser generator, an LL(1) table builder (Module 25), a FIRST/FOLLOW analyser. They work on productions, and productions can't contain a "loop"; the right-recursive A' form is how you express repetition in pure BNF.

Paull's result looks bigger than the input. Does it always grow?

The substitution step can multiply productions (each Aᵢ → Aⱼ γ becomes one rule per Aⱼ alternative). Worst case is exponential in the number of nonterminals, though real grammars stay small. Minimising the blow-up (better orderings, factoring) is an optimisation, not a correctness issue.

Is the order of nonterminals part of the "answer"?

It affects which equivalent grammar you get, not whether the result is correct. We use first-appearance order for determinism. Some orders produce fewer productions than others.
