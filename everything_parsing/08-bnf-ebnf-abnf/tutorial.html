Everything Parsing · Module 08 · Part I — Foundations

BNF, EBNF,ABNF

EBNF's ?, *, +, and ( ) are shorthand. This module parses EBNF and desugars every operator into plain BNF — recursion and epsilon, nothing else — then proves the two describe the same language. Same move as Module 3 made for regex, now for grammars.

The claim, checkable

expr = term (('+'|'-') term)* becomes seven plain BNF rules. Every one of the 220 strings that BNF generates (up to length 7) is accepted by an exact matcher run against the original EBNF. The operators added zero power.

The Big Analogy — stenography

A court stenographer writes "the witness" as one short stroke. Expanded, it's two words. "Objection, sustained" is a squiggle. The transcript that gets typed up later spells everything out — longer, but word-for-word the same testimony.

EBNF is grammar stenography. x* is one stroke meaning "zero or more x." Spelled out in BNF it's a whole extra rule: rep → x rep | ε. x? is a stroke for opt → x | ε. The desugared grammar is longer and has invented rule names, but it accepts exactly the same strings.

And there are competing stenographic systems. Gregg vs. Pitman for shorthand; BNF vs. EBNF vs. ISO-EBNF vs. ABNF for grammars — different symbols (::= vs =, | vs /, x* vs { x } vs *x), same underlying grammar. Learn to read any of them; they transcribe to the same thing.

02

What Happens, Step by Step

  1. Lex the EBNF: quoted strings → terminals, identifiers → names, and the punctuation = ; | ( ) ? * +. // line comments dropped.
  2. Parse by the EBNF meta-grammar (rule → IDENT '=' alt ';', alt → seq ('|' seq)*, …) into an AST of Terminal, Nonterminal, Seq, Alt, Opt, Star, Plus.
  3. Desugar. Walk the AST. Every Opt/Star/ Plus/parenthesised Alt/Seq becomes one fresh nonterminal:
    • x? → opt_N → x | epsilon
    • x* → rep_N → x rep_N | epsilon
    • x+ → plus_N → x plus_N | x
    • ( a | b ) → grp_N → a | b
    Reserve each name before recursing, so helpers print in creation order.
  4. Emit BNF text and hand it to Module 4's Grammar.parse.
  5. Verify: enumerate L(BNF) up to a length bound; check every string is accepted by an exact leftover-suffix matcher run against the original EBNF AST. Plus sample positives and negatives.

The state, drawn

One rule, three notations

  this course :  expr = term (('+' | '-') term)* ;

  ISO-EBNF    :  expr = term { ( '+' | '-' ) term }        { } = zero or more

  pure BNF    :  expr  -> term rep_1
                 rep_1 -> grp_2 rep_1 | epsilon            ← the *
                 grp_2 -> grp_3 term                       ← the ( ... ) group
                 grp_3 -> + | -                             ← the ( '+' | '-' )

The desugaring, as a tree walk

  Seq[ term , Star( Seq[ Alt['+','-'] , term ] ) ]
        │            │         │
        │            │         └─ Alt  → grp_3 -> + | -            (fresh)
        │            └─ Seq     → grp_2 -> grp_3 term              (fresh)
        └─ Star                 → rep_1 -> grp_2 rep_1 | epsilon    (fresh)

  expr's body becomes the two symbols:  term  rep_1
  so:  expr -> term rep_1

The Code, Explained

The desugarer — one fresh nonterminal per operator

Why reserve the name before recursing

If you fill extra after computing the body, the sub-helpers (grp_2, grp_3) get inserted first and the grammar prints inside-out. Reserving rep_1's slot first, then recursing, then filling it means the map's insertion order is rep_1, grp_2, grp_3 — the grammar reads top-down. See DECISIONS.md #7.

The equivalence check — a matcher over the EBNF AST

// exactly Module 3's leftover-suffix method, over token positions instead of characters
case Star st -> {
  out.add(pos);                                    // zero repetitions
  for (int p : leftovers(g, st.inner(), in, pos))
    if (p != pos)                                  // must consume ≥ 1 token — the same guard as regex
      out.addAll(leftovers(g, new Star(st.inner()), in, p));
}
// a token list is accepted iff the start rule can reach position == in.size()

Limits — what this module cannot do yet

Can't do yet

  • Handle full ISO-EBNF or ABNF syntax — just the four core operators.
  • Prove L(BNF) = L(EBNF) exactly — only compare a bounded slice (CFL equivalence is undecidable).
  • Draw an actual railroad diagram — the { } [ ] rendering is its linear form (Appendix X16 draws the tracks).
  • Preserve the parse-tree shape through desugaring — the desugared grammar's trees have extra rep_/grp_ nodes.
  • Desugar EBNF that's left-recursive after expansion (Module 16).

Can do

  • Parse EBNF with ? * + ( ) | and quoted/bare terminals.
  • Desugar every operator to pure BNF: recursion + epsilon.
  • Render the same grammar as-written, ISO-style, and as BNF.
  • Match a token list exactly against an EBNF grammar.
  • Confirm the desugared BNF accepts the same bounded language.
  • Lay the four notations side by side in one table.

07

Brain Exercise

We desugared x* to right-recursion: rep → x rep | ε. Suppose you used left-recursion instead: rep → rep x | ε.

(1) Same language? (2) Same parse trees? (3) Which choice matters, and for what?

Answers

(1) Same language exactly — both generate {ε, x, xx, xxx, …}.

(2) Different tree shapes. Right-recursion builds a right-leaning comb (each rep node has x then a nested rep); left-recursion builds a left-leaning one. For a bare repetition the shape usually carries no meaning, so either is fine.

(3) Two things. Associativity: if the repeated item is ('+'|'-') term — a left-associative operator — then the recursion side determines whether a - b - c parses as (a - b) - c or a - (b - c). EBNF's * is silent about this; you get it from how you desugar, which is why real tools that use EBNF for expressions also specify associativity separately. Parsing method: left-recursion is unusable by a top-down parser (Module 16), so LL tools desugar * right-recursively and rebuild a left-leaning tree afterward if they need one.

08

There Are No Dumb Questions

Is EBNF more powerful than BNF? Can it express a language BNF can't?

No. This module proves it: every EBNF grammar desugars, operator by operator, into a plain BNF grammar for the same language. Both notations express exactly the context-free languages — no more, no less. EBNF buys brevity, not power.

ABNF uses / for "or" and *rule as a prefix. Why so different from EBNF?

ABNF (RFC 5234) comes from the IETF — it's the notation for HTTP, email, URI, and DNS grammars. *rule, 1*rule, 2*4rule express exact repetition counts compactly, which protocol specs lean on ("a header value is 1*(token / quoted-string)"). It's a dialect tuned for a specific audience, describing the same context-free-grammar object.

The desugared grammar has rules like grp_3 -> + | -. Do the names matter?

Not at all — they're fresh, internal, and never referenced by anything a human wrote. A parser generator would leave them anonymous. This course names them opt_/rep_/plus_/grp_ only so the printed grammar tells you which operator each rule came from.

Where are the railroad diagrams — the train-track pictures?

The ISO { x } / [ x ] rendering is a railroad diagram in linear text form: { x } is a loop-back track, [ x ] is a bypass. Drawing them as actual SVG tracks is the grammar workbench in Appendix X16 — it reads a stored grammar (Module 4) and emits both the diagrams and a live parser.

Why bother with BNF at all if EBNF is shorter?

Every parsing algorithm in Parts III–IV — FIRST/FOLLOW, LL tables, LR items — is defined over plain productions. They don't know what * means. Tools that accept EBNF desugar it to BNF internally first, exactly like this module does, then run the algorithm on the result. BNF is the machine format; EBNF is the human one.
