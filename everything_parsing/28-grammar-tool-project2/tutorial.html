Everything Parsing · Module 28 · Part III — Project 2

Grammar Analysis Tool

CSE 340 Project 2 in one program. Feed it any context-free grammar; it reports terminals and nonterminals in appearance order, nullable, FIRST, FOLLOW, a left-recursion-free version, a left-factored version, and the LL(1) verdict with the parsing table (or the conflicts, and whether the transforms fix them). Every section is a component from Modules 20–27, composed — no new algorithm.

The payoff

Hand it the naive expression grammar E → E + T | T. It comes back: 6 LL(1) conflicts, here's the fixed grammar, and yes that one is LL(1). The entire Part III toolkit, one command.

The Big Analogy — the full medical panel

You don't order blood tests one at a time and wait a day between each. You order a panel: one blood draw, one lab run, one sheet back with every marker — and reference ranges printed next to each so you can see at a glance what's in bounds and what isn't. If something's off, the sheet often says what to do about it.

The grammar tool is that panel. One grammar in, one sheet out: the symbol inventory, the nullable markers, the FIRST and FOLLOW ranges, and the LL(1) verdict. When the verdict is "not LL(1)," the sheet doesn't just flag it — it runs the two standard treatments (remove left recursion, left-factor) and reports whether the grammar is healthy afterward.

Each test on the panel was developed and validated separately — that's Modules 21 through 27. The panel itself adds no new chemistry. It draws once and prints one page.

What Happens, Step by Step

  1. Parse the grammar file (%start line + productions, | alternatives, epsilon for empty).
  2. Section 1 — walk the productions once, collecting nonterminals (left-hand sides) and terminals (everything else) in first-appearance order.
  3. Section 2 — FirstSets: the nullable least fixed point.
  4. Section 3 — FirstSets: FIRST for every nonterminal.
  5. Section 4 — FollowSets: FOLLOW, seeded with $ on the start symbol, iterated over FIRST.
  6. Section 5 — LeftRec.paull: substitute lower nonterminals into higher ones (only where it exposes left recursion), then eliminate direct left recursion.
  7. Section 6 — LeftFactor.factor: pull out longest shared prefixes to a fixed point.
  8. Section 7 — Predict: if the PREDICT sets are pairwise disjoint, print the LL1Table. Otherwise list the conflicts, run factor(paull(g)), and report whether that is LL(1).

Section 5 must not over-substitute

  json:  elements -> value | value comma elements     (right-recursive, NOT left)

  textbook Paull would inline 'value' (it comes first in the order):
     elements -> obj | arr | str | ... | obj comma elements | arr comma elements | ...
     (16 alternatives, unreadable, pointless)

     elements -> value | value comma elements        (left alone)

04

The Code, Explained

Serialise, then re-parse

The transforms return a mutable working grammar. toGrammar renders it back to %start X + text and runs it through the same Grammar.parse. So the "is the fixed grammar LL(1)?" check goes through the identical Predict pipeline as everything else — the transformed grammar isn't a special case, it's just another grammar. (This is why the loader has to accept ' in nonterminal names.)

Order of operations: recursion first, then factoring

Paull's substitution step can create shared prefixes. If you left-factor first and then remove left recursion, you can be left with new un-factored prefixes. Recursion-removal → factoring is the order that reaches a fixed point in one pass, and it's what section 7's combined check uses: factor(paull(g)).

Limits — what this module cannot do yet

Can't do yet

  • Grammar hygiene: detect unreachable or non-productive nonterminals, useless productions.
  • Nullable-prefix left recursion (A → B A, B → ε).
  • Emit a runnable parser — that's Module X15 (parser generator).
  • LL(k) / LL(*) analysis (Module 29).
  • Anything LR (Part IV) — this tool is LL-only.
  • Minimise the transformed grammar (fewest new nonterminals).

Can do

  • Full symbol inventory, nullable, FIRST, FOLLOW for any CFG.
  • Left-recursion-free and left-factored versions.
  • LL(1) verdict with a single-valued table, or the conflicts.
  • Answer "can this grammar be made LL(1)?" by running the transforms.
  • Byte-identical Java and JS output on every fixture.

Getting a blank or broken result?

Section 5 bloats a rule that had no left recursion — guard Paull's substitution: only inline Aj into Ai when Aj can leftmost-reach Ai.
"after … LL(1) = NO" for a grammar you know is fixable — you factored before removing recursion, or only did one.
FOLLOW section wrong — FIRST feeds FOLLOW; fix section 3 first.
Transformed grammar won't re-analyse — the loader must accept ' in nonterminal names.

07

Brain Exercise

(1) Run the tool by hand on S → S a | b. Sections 1–4, then 5, then 7. (2) Section 7's combined check is factor(paull(g)). Give a grammar where paull(factor(g)) would give a worse (still-not-LL(1)) result.

Answers

(1) 1: nonterminal S; terminals a b; start S. 2: nothing nullable. 3: FIRST(S) = { b } — the recursion adds nothing new. 4: FOLLOW(S) = { a $ } (the a from S → S a). 5: directly left-recursive → S → b S', S' → a S' | epsilon. 7: the original is not LL(1) — S → S a and S → b both predict b. After the transform: PREDICT(S → b S') = { b }; PREDICT(S' → a S') = { a }; PREDICT(S' → epsilon) = FOLLOW(S') = { $ } (note FOLLOW(S') is just { $ }, not FOLLOW(S) — S' only ever sits at the end). All disjoint → the transformed grammar is LL(1). The tool prints "after left-recursion removal + left factoring: LL(1) = YES".

(2) Any grammar where factoring introduces a nonterminal that then becomes part of an indirect-left-recursion cycle Paull would have broken if it ran first. Concretely, factoring A → B x | B y to A → B A' is harmless, but if B → A …, running Paull after now has to deal with A → B A' and the fresh A' in the cycle. Recursion-first avoids adding names into a tangle you haven't untangled yet.

08

There Are No Dumb Questions

Why is this a whole module if it's "just" composition?

Because composition is where interface mismatches surface: does LeftRec.paull produce something Predict can consume? Does the loader round-trip a transformed grammar? Does the fix order matter? The project forces those questions and the answers are the value.

The tool says "LL(1) = YES after transforms." Is the transformed grammar the "same" grammar?

Same language — it generates the identical set of strings (Modules 23–24 check this by bounded enumeration). Different parse trees, and associativity has to be recovered at AST-build time (Module 39). So: use it to parse, not to reason about structure.

What does the real CSE 340 Project 2 grade on?

Typically the exact text of the symbol lists, nullable set, and FIRST / FOLLOW sets, checked against a reference for a batch of grammars. Our sections 1–4 are that; 5–7 are the extension into the transforms and the verdict.

Could I use this to check my hand-written parser's grammar?

Yes — that's exactly its job. Write your grammar in the .grammar format, run the tool, and if section 7 says LL(1) with a clean table, a predictive recursive-descent parser (Module 19) or a table-driven one (Module 26) will work with no backtracking.

Why not also emit the parser code?

That's Module X15 (a parser generator) — it takes this analysis and prints Java/JS source. Kept separate because code generation has its own concerns (naming, formatting, runtime library) that would bloat this module.
