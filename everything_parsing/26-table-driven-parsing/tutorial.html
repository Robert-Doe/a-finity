Everything Parsing · Module 26 · Part III — Top-Down Parsing

Table-Driven Predictive Parsing

Module 19 parsed with recursion — one function per nonterminal, the call stack doing the bookkeeping. Module 25 built the table. This module throws away the recursion: an explicit stack, the table, and a loop. The stack holds the unfinished part of the sentential form; the loop expands nonterminals via table lookup and matches terminals against the input. Same leftmost derivation, same parse tree, zero grammar-specific code.

The payoff

One 40-line loop parses any LL(1) grammar. Swap the table, parse a different language. The production sequence it emits, replayed leftmost, reproduces the input exactly — the proof it's doing the same thing recursive descent does.

01

The Big Analogy — the to-do list you keep re-topping

You're assembling flat-pack furniture. Your to-do list is a stack of sticky notes. The top note says "build the frame." You look it up in the manual: step 12 says "the frame = left panel + back + right panel." You replace that one note with three new notes — "right panel", "back", "left panel" — stacked so "left panel" is on top, because that's what you do first.

Now the top note is "left panel." The manual says a left panel is just a physical part — so you go to the box, find the part labelled "left panel," and if it matches, you fit it and throw the note away. If the box hands you a "right panel" when your note says "left panel," you've got the wrong kit — stop.

The stack is always "everything still to do, in order." The manual is the parsing table. A note naming a sub-assembly (nonterminal) gets looked up and expanded; a note naming a part (terminal) gets matched against the box (the input) and discarded. When the stack is empty and the box is empty, the furniture is built — accept.

02

What Happens, Step by Step

  1. Push $, then the start symbol. Append $ to the input. Set the lookahead to the first token.
  2. Loop on the stack top X:
    • X = $: if lookahead is $ → accept; else "input left over" error.
    • X a terminal: if X equals the lookahead → pop, advance the lookahead; else "expected X" error.
    • X a nonterminal: look up M[X][lookahead]. Blank → error. One production X → Y₁…Yₙ → record it, pop X, attach n child nodes, push Yₙ…Y₁ (so Y₁ is on top). Empty RHS → push nothing, add one epsilon child.
  3. The recorded productions, in order, are a leftmost derivation of the input.

The state, drawn

Stack evolution — id + id * id (top on the right)

  stack                       input           action
  $ E                         id + id * id $  expand E -> T Ep
  $ Ep T                      id + id * id $  expand T -> F Tp
  $ Ep Tp F                   id + id * id $  expand F -> id
  $ Ep Tp id                  id + id * id $  match id
  $ Ep Tp                     + id * id $     expand Tp -> epsilon   (M[Tp][+] = 5)
  $ Ep                        + id * id $     expand Ep -> + T Ep    (M[Ep][+] = 1)
  $ Ep T +                    + id * id $     match +
  $ Ep T                      id * id $       expand T -> F Tp
  ...                         ...
  $ Ep                        $               expand Ep -> epsilon
  $                           $               ACCEPT

The stack IS a sentential form

  read the stack bottom-to-top and prepend what's been matched:

  matched: (nothing)   stack: E              form: E
  matched: (nothing)   stack: T Ep           form: T Ep
  matched: id          stack: Tp Ep          form: id Tp Ep
  matched: id          stack: Ep             form: id Ep
  matched: id +        stack: T Ep           form: id + T Ep
  ...
  matched: id + id * id  stack: (empty)      form: id + id * id

  each row is one step of the leftmost derivation. the "form" column is exactly
  what Module 19's replay produces, and what Module 5 called a sentential form.

An error — blank cell

  input  id +           (an expression can't end on an operator)

   ...
   6  top +   look +   match
   7  top T   look $   error: M[T][$] blank cell

  M[T][$] is empty: no way to start a T (a term) at end of input.
  REJECTED: no production for T on '$' at position 2
04

The Code, Explained

The (symbol, node) pairing builds the tree for free

Each stack entry carries the parse-tree node it belongs to. When a nonterminal expands, its node gets one child per RHS symbol, and those child nodes are pushed with their symbols. So by the time a terminal is matched, its node is already sitting in the right place in the tree — no second pass, no reconstruction from the production list.

Replay: the executable proof

replay(productions) starts at the start symbol and applies each recorded production to the leftmost nonterminal. If the parser did its job, the final form is the input, token for token. This is Module 19's "the call stack is the leftmost derivation" — but now there's no call stack, just a data stack and a table, and the claim still holds. The table parser and the recursive parser produce the identical production sequence for any input.

Limits — what this module cannot do yet

Can't do yet

  • Recover from an error and keep parsing — Module 27 (panic mode, FOLLOW sync sets).
  • Run semantic actions / build an AST (not the concrete tree) during the walk — Part V (Modules 37–39).
  • Lex its own input — fixtures are pre-tokenised terminal names.
  • Parse a non-LL(1) grammar — a conflicted cell stops it (Module 29 for more lookahead; Part IV for LR).
  • Report more than the first error.

Can do

  • Parse any LL(1) grammar with one fixed loop.
  • Build the concrete parse tree in the same pass.
  • Emit the leftmost derivation and verify it reproduces the input.
  • Reject malformed input with the stack top, lookahead, and position.
  • Do all of it with no recursion and no per-grammar code.

Getting a blank or broken result?

Parse loops forever — RHS pushed forward, or A not popped before the pushes.
Tree has no epsilon leaves — an empty RHS still needs one epsilon child node.
replay disagrees with the input — a non-leftmost expansion crept in; always take the leftmost nonterminal.
Trailing tokens accepted — you didn't append $ to the input or seed the stack with $.

Brain Exercise

(1) At some step the stack (bottom→top) is $ Ep Tp and the lookahead is ). What are the next few steps? (2) The recursive-descent parser (Module 19) and this one produce the same production sequence. Name one practical thing the table-driven version does better, and one thing the recursive version does better.

Answers

(1) Top is Tp. M[Tp][)] = Tp → epsilon — pop Tp, add an epsilon leaf. Top is now Ep. M[Ep][)] = Ep → epsilon — pop, add leaf. Top is $; if the lookahead were also $ we'd accept, but it's ), so this ) must be getting matched by a ) that an enclosing F → ( E ) pushed below — so just below $ on the real stack there'd be a ). (In isolation, $ Ep Tp with lookahead ) and nothing below $ would then error.)

(2) Table-driven: no stack-overflow risk on deeply nested input (the stack is heap data, not call frames), and the parser is grammar-agnostic — a generator emits just the table. Recursive descent: far easier to drop in custom error messages, semantic actions, and hand-tuned lookahead at a specific rule, and it's more readable.

08

There Are No Dumb Questions

If it's the same as recursive descent, why learn both?

Recursive descent is what you hand-write; table-driven is what a generator emits and what the theory analyses. Seeing they're the same algorithm — call stack ↔ data stack, if-ladder ↔ table row — is the point. LR parsing (Part IV) is only ever table-driven, so the stack machine model matters there.

Why build the concrete tree and not the AST directly?

The concrete tree is the faithful record of which productions fired. The AST drops chain rules and punctuation — that's a separate, deliberate transformation (Module 39) with its own choices. Building the concrete tree first keeps this module about parsing, not tree design.

What happens at a conflicted cell (non-LL(1) grammar)?

The parser sees a cell with two productions, can't choose, and reports an error. It doesn't guess. To parse such a grammar you either add lookahead (Module 29), resolve the cell by hand, or move to LR (Part IV).

Is the stack ever huge?

Its depth is bounded by the deepest right-hand-side nesting the input forces — roughly the parse tree's height. For pathological deeply-nested input (((((((...))))))) it grows linearly with nesting depth, but it's heap data, so there's no fixed recursion limit to hit.

Where does lexing fit?

In front. Modules 9–18 turn source text into a token stream; this parser consumes that stream. Here the fixtures skip the step by giving terminal names directly. A full front end chains lexer → parser.
