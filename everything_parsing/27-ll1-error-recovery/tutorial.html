LL(1) Error Recovery

Module 26's parser quits at the first bad token. Real compilers report a whole screen of errors from one run. This module adds panic-mode and phrase-level recovery: when a table lookup fails, either skip input until a synchronizing token (from FOLLOW), pop the stuck nonterminal, or assume a missing terminal was there — then keep parsing. Every branch makes progress, so it always finishes.

The payoff

( id + ) — Module 26 stops at ). With recovery: "skipping T (lookahead in FOLLOW)", parse continues, reaches ACCEPT, reports one clean error at position 3.

01

The Big Analogy — reading aloud past a coffee stain

You're reading a report aloud to a room. Halfway down a paragraph, a coffee stain blots out three words. A nervous reader stops dead and refuses to continue. A competent reader says "…something illegible here…" and picks up at the start of the next sentence — because sentence boundaries are reliable places to resume; you know what a sentence should look like.

That's panic mode. When the parser is stuck expanding some nonterminal A and the next token makes no sense, it throws away tokens until it sees one that could legitimately come after A — a token in FOLLOW(A), the parsing equivalent of "the start of the next sentence." Then it drops A off the stack and carries on.

Sometimes the fix is smaller: the reader sees "the cat sat the mat" and silently reads "on" — a single obviously-missing word. That's phrase-level recovery: a terminal the grammar demanded isn't in the input, so assume it was there, note it, and move on without discarding anything.

02

What Happens, Step by Step

Same loop as Module 26, with three failure cases handled instead of aborting:

  1. Top is a terminal X, lookahead is not X → phrase-level: record "inserted missing X", pop X, do not advance the input.
  2. Top is a nonterminal A, M[A][lookahead] is blank (or has a conflict) → panic mode:
    • lookahead ∈ FOLLOW(A) (or is $) → record "skipping A", pop A, keep the input where it is.
    • otherwise → record "discarding 'lookahead'", advance the input by one, keep A on the stack.
  3. Top is $, lookahead is not $ → record "extra input", discard the token, continue.

Cases 1 and 2a pop the stack; cases 2b and 3 advance the input. Nothing else changes state. So every iteration makes measurable progress toward "stack empty and input consumed" — the loop terminates.

04

The Code, Explained

The termination argument, in one line

Give the parser state a "size" = (tokens left to read) + (symbols on the stack). Every normal step and every recovery branch strictly decreases it — a match removes a token and a stack symbol; a discard removes a token; a phrase-level insert or a FOLLOW-sync removes a stack symbol. A strictly decreasing non-negative integer can't decrease forever. Done.

Recovery guesses — and guesses can cascade

When panic mode skips a nonterminal it's assuming the programmer's intent. If it's wrong, the next few tokens get parsed in the wrong context and you get spurious follow-on errors. Real compilers cap the total (~20), suppress errors within a few tokens of a previous one, or use error-correcting recovery (Burke–Fisher, Appendix X9). This module keeps it simple: report everything, let the count speak.

05

Limits — what this module cannot do yet

Can't do yet

  • Suppress cascading follow-on errors, or cap the count.
  • Least-cost repair — try small insertions/deletions and pick the cheapest (Burke–Fisher, Appendix X9).
  • Build a parse tree with error nodes marking the damaged regions.
  • Use grammar-author-supplied error productions (yacc-style).
  • Recover inside the lexer — that's Module 17 (this is one layer up).

Can do

  • Report every error in one run, with positions, and reach end of input.
  • Panic mode with FOLLOW-set synchronization (skip a nonterminal).
  • Panic mode by discarding a stray token.
  • Phrase-level recovery: insert a missing terminal.
  • Guarantee termination on any input.

Getting a blank or broken result?

Recovery loops forever — a branch that neither pops the stack nor advances the input. Each panic branch must do exactly one.
Missing-terminal errors never fire — handle "terminal on top ≠ lookahead" before falling into panic mode.
One error becomes twenty — expected; that's the cascade. Cap or suppress in a real tool.
Sync set skips too much — use FOLLOW(A) only, not FIRST ∪ FOLLOW.

Brain Exercise

(1) On id id + id, the parser is at stack top Tp with lookahead id. FOLLOW(Tp) = { ) + $ }. Which panic branch fires, and why is that the right call? (2) Suppose we used FIRST(A) ∪ FOLLOW(A) as the sync set. On ( id + ) at stack top T, lookahead ) — same result? Now try lookahead id after some earlier damage. What changes?

Answers

(1) id ∉ FOLLOW(Tp), so the "discard the token" branch fires — drop the stray second id and retry Tp. Right call: a bare id where an operator was expected is junk; skipping it lets Tp → epsilon fire on the following + and the rest parses.

(2) For ) at top T: unchanged — ) ∈ FOLLOW(T), pop T. The difference shows when the lookahead is in FIRST(A): with the bigger sync set the parser would stop discarding and re-try A immediately (resume without loss), instead of throwing the token away. Useful when the earlier damage was a spurious token and the real content starts right here. It's a refinement, not needed for a correct LL(1) table's blank cells.

08

There Are No Dumb Questions

Why is it called "panic mode"?

Dragon Book terminology. The parser "panics": abandons its current attempt, discards input as fast as it can, and races to a token it trusts. Crude, but robust and easy to implement — still the default in many production compilers.

Is this the same recovery as the lexer's (Module 17)?

Same idea, one layer up. The lexer skips characters to a character where a token can start; the parser skips tokens to a token in a FOLLOW set. Both report, resynchronize, continue.

Does phrase-level insertion ever make things worse?

It can — if the terminal wasn't actually "missing" but the real problem was elsewhere, inserting it papers over the symptom and the true error surfaces later, misattributed. In practice, single-token insertions for closers (), ], ;) are reliable enough that most parsers do them.

Why not just fix the grammar so there are no errors?

The errors are in the input, not the grammar — a programmer typed something malformed. The grammar is fine; the parser's job is to describe what's wrong helpfully and, ideally, keep checking the rest of the file.

How do real compilers avoid the error cascade?

Several tactics: suppress any error within k tokens of a previous one; hard-cap the total (GCC stops at ~20); prefer error-correcting recovery that minimises disruption; and let grammar authors write explicit error productions for known-tricky spots.
