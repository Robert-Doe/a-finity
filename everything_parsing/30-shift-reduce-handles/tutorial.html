Everything Parsing · Module 30 · Part IV — Bottom-Up Parsing

Handles, Shift-Reduce & Viable Prefixes

Top-down parsing (Part III) predicts a production and works down to the tokens. Bottom-up parsing goes the other way: hold the tokens on a stack, and whenever the top of the stack matches a production's right-hand side — a handle — replace it with the left-hand side. Keep reducing until only the start symbol is left. The reductions, played in reverse, are a rightmost derivation. And it parses left-recursive grammars directly.

The payoff

The grammar E → E + T | T that Part III had to transform away? Bottom-up parses it as written — you reduce E + T back to E, left recursion and all.

01

The Big Analogy — assembling, not disassembling

Top-down parsing is like following the assembly manual from step 1: "the product is a frame plus a lid; a frame is four rails plus a base…" — you keep expanding until you're holding actual screws.

Bottom-up parsing is the packing crew in reverse. Parts come down the conveyor belt one at a time (the tokens). You set them on a workbench (the stack). The moment the parts on the right end of your bench form a complete sub-assembly — "two rails and a crosspiece? that's a side panel" — you snap them together and the sub-assembly replaces those parts on the bench. You never plan ahead; you just watch the right end of the bench and combine whatever's ready. When the whole bench holds one finished product, you're done.

That completed group you snap together is the handle. The rule for "what counts as a completed group" is a production read right-to-left. And the trick — the thing Module 31 builds — is a little machine that watches the bench and tells you instantly whether the right end is a handle yet, or whether you should wait for one more part.

02

What Happens, Step by Step

  1. Stack empty, cursor at the first token.
  2. Look at the top of the stack:
    • If the top |β| symbols equal some production's RHS β and reducing there leads to a complete parse → reduce: pop β, push the LHS A. That β was the handle.
    • Otherwise → shift: push the next input token, advance the cursor.
  3. Repeat until the stack is exactly [start] and the input is consumed → accept. If neither move works → syntax error.
  4. The sequence of reductions, reversed, is a rightmost derivation of the input.

The hard part is step 2's "and reducing there leads to a complete parse." A real LR parser knows this in O(1) from its state (Module 31). This module figures it out by trying and backtracking.

03

The state, drawn

Shift-reduce trace — id + id * id

  STACK          ACTION                          INPUT
  (empty)        shift id                        id + id * id $
  id             reduce F -> id   (handle id)    + id * id $
  F              reduce T -> F                   + id * id $
  T              reduce E -> T                   + id * id $
  E              shift +                         + id * id $
  E +            shift id                        id * id $
  E + id         reduce F -> id                  * id $
  E + F          reduce T -> F                   * id $
  E + T          shift *          <- NOT reduce E -> E + T yet!   * id $
  E + T *        shift id                        id $
  E + T * id     reduce F -> id                  $
  E + T * F      reduce T -> T * F  (handle T * F)   $
  E + T          reduce E -> E + T  (handle E + T)   $
  E              ACCEPT                          $

Why "shift" at E + T with * ahead

  the stack top E + T IS the RHS of  E -> E + T.  reducing is legal syntax.
  but the NEXT token is '*', and '*' can only extend the T (T -> T * F).
  reduce now and you lose the chance -- 'E * ...' isn't a right-sentential form.

  so: reduce  E + T -> E  only when the lookahead can't extend T.
  that decision is exactly what the LR automaton (Module 31) encodes.
  it is also why '*' binds tighter than '+': T grows first.

Reductions reversed = rightmost derivation

  reductions (bottom-up order):
    F->id, T->F, E->T, F->id, T->F, F->id, T->T*F, E->E+T

  reversed:
    E => E + T => E + T * F => E + T * id => E + F * id
      => E + id * id => T + id * id => F + id * id => id + id * id

  each => expands the RIGHTMOST nonterminal. final form == the input.

Two handles = ambiguity — E → E + E on id + id + id

  reach stack  E + E  with '+' ahead.
    reduce  E + E -> E  , then shift + , ... -> ACCEPT   (left-associative reading)
    shift + , ... , reduce the RIGHT E + E first , ...  -> ACCEPT   (right-assoc)
  TWO accepting moves from one state = a shift-reduce conflict.
  the grammar has no precedence/associativity; Module 35 adds it.
04

The Code, Explained

"Reduce first, then shift" + backtracking = the canonical parse

For an unambiguous grammar there's exactly one accepting sequence of moves. Trying reductions before shifts, and backing out of dead ends, finds it without any lookahead reasoning. The cost is exponential search in the worst case — which is precisely why Module 31 replaces it with a DFA that answers "shift or reduce?" in constant time.

Viable prefixes are a regular language

A viable prefix is any string of grammar symbols that can sit on the stack during some valid parse — equivalently, a prefix of a right-sentential form that doesn't extend past its handle. There are infinitely many, but the set of them is regular: a finite automaton can recognise them. That automaton — states = sets of "LR items" — is the entire engine of an LR parser. Module 31 constructs it.

Limits — what this module cannot do yet

Can't do yet

  • Decide shift-vs-reduce in O(1) — needs the viable-prefix DFA (Module 31).
  • Handle grammars with ε-productions in the shift-reduce search (the fixtures avoid them).
  • Parse without backtracking / exponential worst case.
  • Resolve a shift-reduce conflict by precedence — Module 35.
  • Report errors at a precise point (the DFS just says "no parse").
  • Build the parse tree (only the reduction sequence).

Can do

  • Parse left-recursive grammars directly, bottom-up.
  • Produce the full shift-reduce trace with handles marked.
  • Show the reductions reversed form a rightmost derivation of the input.
  • Detect a shift-reduce / reduce-reduce conflict and name the state.
  • Demonstrate that precedence falls out of reduction order.

Getting a blank or broken result?

"no parse found" for valid input — try every reduction whose RHS is a stack suffix, then shift; raise the search cap.
Reversed reductions aren't a rightmost derivation — replace the rightmost occurrence of the LHS when replaying.
Over-shifts, never reduces — try reductions before shifts.
Conflict missed — at each state count how many distinct moves reach ACCEPT, not just the one the parser took.

07

Brain Exercise

(1) Trace the shift-reduce parse of id * id with the expr grammar. At which step could you legally reduce T -> F but must not? (2) The stack contents E + T * appears mid-parse. Is it a viable prefix? Is E * T?

Answers

(1) shift id → id; reduce F -> id → F; reduce T -> F → T. Now the stack is T and the lookahead is *. You could reduce E -> T (the stack top T is that RHS), but you must not — * extends the T via T -> T * F, and E * ... is not a right-sentential form. Shift * instead.

(2) E + T * is a viable prefix — it's a prefix of the right-sentential form E + T * F (whose handle is T * F), stopping before the handle's end. E * T is not — no right-sentential form of this grammar starts E * (an E is never immediately followed by *). A shift-reduce parser's stack can never hold E * T.

08

There Are No Dumb Questions

Why is bottom-up "more powerful" than top-down?

An LR parser doesn't have to commit to a production until it has seen the entire right-hand side plus one lookahead token. An LL parser must pick the production from just the first token(s). Seeing more before deciding means LR(1) handles every LL(1) grammar and many that no LL(k) grammar can express — including all left-recursive ones.

Is the handle always on top of the stack?

Yes — that's the key structural fact. In a rightmost derivation reversed, each reduction happens at the right end of what's been built, which is exactly the top of the stack. You never have to search the middle of the stack for a handle.

What's the difference between a shift-reduce and a reduce-reduce conflict?

Shift-reduce: from one state, both shifting the next token and reducing by some production are valid. Reduce-reduce: two different productions could both reduce the current stack top. Both mean the grammar (or the chosen parser class) can't decide with the available lookahead.

Does the shift-reduce parser build a parse tree?

It can — attach a subtree to each symbol as it's pushed, and when you reduce A -> β, make a new A node whose children are the subtrees of the popped β. This module only records the reduction sequence; the tree is a small addition (and Part V builds ASTs this way).

Why does this module use exponential backtracking?

Purely to make the mechanics concrete before the machinery. Module 31's DFA turns "is the stack top a handle, given the lookahead?" into a table lookup, and the real LR parser is linear-time with no backtracking at all.
