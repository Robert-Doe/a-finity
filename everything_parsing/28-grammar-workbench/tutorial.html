The GrammarWorkbench

Hand it a language's grammar exactly as the spec writes it, in EBNF, and it tells you whether a one-token-lookahead parser can handle it. If not, it names the rule, the token, and the chain of derivations that causes each conflict. Once the grammar is clean, it builds the LL(1) table and parses real Ajoda programs using the tokens Capstone A produced.

One real conflict, found and fixed

Ajoda's grammar as specified: 24 EBNF rules → 82 BNF productions → 1 conflict: Statement on IDENT. Assignment and expression statements both start with a name. Fold assignment into ExprStmt and it's LL(1). factorial.ajoda then parses in 176 expansions; a missing ; is caught at 3:5.

The Big Analogy — a building inspector with the blueprints

An architect hands over blueprints drawn in the office's usual shorthand: "repeat this window along the wall," "optional balcony here." The inspector can't sign off on shorthand, so the first job is to expand it into every concrete piece, labelling each one with the page it came from.

Then the real check: at every doorway, can a visitor tell which room they're entering by looking one step ahead? If two rooms share the same doorway, the inspector doesn't just say "fails." They walk you through it: "this door leads to the assignment room, and this other corridor winds through eleven hallways and ends at the same door."

Once the plan passes, the inspector hands you a floor map, and you walk an actual visitor (a real program) through the building to prove every step has exactly one way forward.

02

What Happens, Step by Step

  1. Read the EBNF. A rule starts at Name ::= and runs until the next one, so alternatives can continue on the next line with a leading |. "quoted" text is a literal token; an UPPER_CASE name nobody defines is a token class from the scanner; any other undefined name is an error.
  2. Desugar. Each bracket becomes a helper nonterminal named after its rule: { X } → R_repN → X R_repN | ε, [ X ] → R_optN → X | ε, ( X | Y ) → R_grpN → X | Y. A group with one branch is just inlined. Repetition is right-recursive on purpose, so desugaring never creates left recursion.
  3. Check for left recursion (Module 23). If present, remove it with Paull's algorithm and continue on the rewritten grammar.
  4. Compute PREDICT for every production (Modules 20–22). Group by nonterminal and lookahead; any lookahead claimed by two productions is a conflict.
  5. Explain each conflict. For each production involved, find a chain of leftmost derivations that reaches the token, or report that the production can vanish and the token is in FOLLOW.
  6. If there are no conflicts, build the table (Module 25) and run the table-driven parser (Module 26) on token files written by Module 16.

The conflict, traced

  Statement on IDENT:
    [Statement -> AssignStmt]  via Statement -> AssignStmt -> IDENT
    [Statement -> ExprStmt]    via Statement -> ExprStmt -> Expression -> LogicalOr
                                   -> LogicalAnd -> Equality -> Comparison -> Term
                                   -> Factor -> Unary -> Call -> Primary -> IDENT

  x = 1;   and   x + 1;   look identical until the second token.

The repair

  before:  Statement  ::= LetStmt | AssignStmt | ... | ExprStmt
           AssignStmt ::= IDENT "=" Expression ";"
           ExprStmt   ::= Expression ";"

  after:   Statement  ::= LetStmt | ... | ExprStmt
           ExprStmt   ::= Expression [ "=" Expression ] ";"

  The parser reads an expression first and decides it was an assignment target
  when it sees "=". Checking that the left side is actually assignable becomes
  semantic analysis's job.

The Code, Explained

Lowering a bracket to a helper

const name = fresh(owner, it.k);              // e.g. Term_rep1
addNt(name, owner);                             // origin: Term_rep1 came from Term
const alts = it.body.seqs.map(s => lowerSeq(s, owner));
if (it.k === "rep") {
  for (const a of alts) bodies.get(name).push([...a, name]);   // X R_rep
  bodies.get(name).push([]);                                        // | epsilon
} else if (it.k === "opt") {
  for (const a of alts) bodies.get(name).push(a);
  bodies.get(name).push([]);
} else {
  for (const a of alts) bodies.get(name).push(a);
}

Explaining a conflict

Why walk past nullable symbols?

In A → B C, the token can come from C only if B can vanish. The loop keeps going while the current symbol is nullable and stops at the first one that isn't, which is exactly the FIRST-of-a-sequence rule from Module 21, run backwards to recover a path instead of a set.

Crazy detail — the token file is the interface

This module never imports the scanner. It reads fixtures/*.tokens, plain line:col KIND lexeme lines that Module 16 wrote. Keywords and operators become quoted terminals ("fn", "<="); IDENT, INT_LIT and FLOAT_LIT stay as token classes. That one mapping, terminalOf, is the entire contract between the two capstones.

05

Limits — what this module cannot do yet

Can't do yet

  • Fix a conflict automatically. Left factoring can't help here: the two productions start with different nonterminals.
  • Build a syntax tree. The parser accepts or rejects; trees come with syntax-directed translation (Part V).
  • Recover from a syntax error and continue (Module 27's technique, not wired in here).
  • Use more than one token of lookahead (Module 29).

Can do

  • Read a real language's grammar in EBNF, as written.
  • Desugar brackets into named, traceable helper rules.
  • Detect and remove left recursion.
  • Find every LL(1) conflict and explain it as a derivation chain.
  • Build the table and parse real programs, reporting errors at line:col.

Getting a blank or broken result?

'Foo' is not defined: a rule name is misspelled, or a token class isn't written in UPPER_CASE.
A rule swallows the next one: every rule must start with Name ::= on its own line position; continuation lines start with |.
Every keyword is a parse error: the token file uses different spellings than the grammar's quoted literals. Regenerate it with Module 16.
The error names a helper you don't recognize: check the helpers: list; each one names the bracket it came from.

07

Brain Exercise

(1) The repaired grammar accepts 1 + 2 = 3;. Is that a bug in the parser? Where should it be rejected? (2) Ajoda's if has an optional else, yet the workbench finds no dangling-else conflict. Why not? What single change to the grammar would create one?

Answers

(1) Not a bug: the grammar now says "an expression, optionally followed by = and another expression." Whether the left side can be assigned to is a question about meaning, not shape, so semantic analysis rejects it ("left side of = must be a variable"). Many real languages parse assignment exactly this way.

(2) Ajoda requires braces: the branch after if (...) is a Block, so an else can only follow a closing } that belongs to exactly one if. Nothing ends in a bare IfStmt that another else could attach to. Allow a single Statement as the branch ("if" "(" Expression ")" Statement [ "else" Statement ]) and "else" lands in both PREDICT sets of IfStmt_opt1: the classic conflict.

08

There Are No Dumb Questions

Why desugar { X } to right recursion instead of left?

R → X R | ε is LL-friendly; R → R X | ε is left-recursive and would force a Paull pass on every repetition. Both describe the same strings. Associativity is decided later, when the tree is built, not by which way the helper recurses.

Why not let the tool fix the conflict itself?

Because the right fix depends on what the language means. Folding assignment into expressions is one choice; adding a second token of lookahead is another; making = an expression operator is a third. Each has consequences for semantic analysis. A tool that picks one silently hides a design decision.

45 nonterminals from 24 rules. Isn't that a lot of helpers?

Every { }, [ ] and multi-branch ( ) costs one. Hand-written recursive descent hides them in loops and ifs; a table-driven parser needs them spelled out. Naming them after their rule is what keeps the error messages readable.

The missing-; error lists 18 expected tokens. Can it be friendlier?

Yes. The list is honest: after x + 1 any operator could continue the expression. A friendlier message picks the likeliest fix ("missing ;?") by checking whether inserting one token would let the parse continue. That's the error-repair idea from Module 27 and Appendix X9.
