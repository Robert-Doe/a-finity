Everything Parsing · Module 25 · Part III — Top-Down Parsing

The LL(1) Parsing Table

Everything from Modules 20–24 converges here. Build a two-dimensional table M[A][t]: given nonterminal A on the stack and lookahead token t, which production do you apply? Fill each production into the columns of its PREDICT set. If no cell ever gets a second production, the grammar is LL(1) and this table is the parser. Every double-booked cell is a concrete non-LL(1) witness.

The payoff

The whole expression grammar collapses to a 5-row by 7-column table of production numbers. Parse id + id * id with nothing but a stack and lookups — no recursion, no grammar-specific code.

The Big Analogy — the dispatcher's wall chart

An emergency dispatcher has a laminated wall chart. Down the side: the kind of call ("structure fire", "medical", "traffic"). Across the top: the key detail from the caller ("smoke visible", "chest pain", "injuries"). Each cell says exactly which unit to send. No judgement calls mid-crisis — cross-reference the row and column, read the cell, dispatch.

The parser's table is that chart. Row = the nonterminal it's currently trying to build. Column = the one token it's looking at. Cell = the production to apply. The entire "how do I parse this language" decision is precomputed into a grid; at runtime the parser does lookups.

Building the chart is the careful part, done once, offline. For each production A → α, you ask "which caller-details would lead here?" — that's PREDICT(A → α) — and write this production into those columns of row A. If two productions ever want the same cell, the chart is ambiguous: the dispatcher would have two units to send and no way to choose. That's a grammar that isn't LL(1).

02

What Happens, Step by Step

Build

  1. Columns = every terminal that appears in the grammar, plus $.
  2. Start with every cell empty.
  3. For each production p = A → α: compute PREDICT(p) (Module 20 — FIRST(α), and if α is nullable, also FOLLOW(A)).
  4. For each token t ∈ PREDICT(p): add p to M[A][t].
  5. Any cell now holding two or more productions is a conflict. No conflicts ⇒ LL(1).

Use (preview of Module 26)

  1. Stack starts as [ $, start ]; input ends with $.
  2. Top is a terminal: it must equal the lookahead — pop and advance, or error.
  3. Top is a nonterminal A: look up M[A][lookahead]. Blank → syntax error. One production A → X₁…Xₙ → pop A, push Xₙ…X₁ (so X₁ ends up on top).
  4. Top is $ and lookahead is $ → accept.

  row E has 0 in three columns: E -> T Ep is the only choice, whenever E is

Parsing id + id * id with the table

  step  action
   0     expand E -> T Ep
   1     expand T -> F Tp
   2     expand F -> id
   3     match id
   4     expand Tp -> epsilon         (lookahead '+', M[Tp][+] = 5)
   5     expand Ep -> + T Ep          (M[Ep][+] = 1)
   6     match +
   7     expand T -> F Tp
   8     expand F -> id
   9     match id
  10     expand Tp -> * F Tp          (lookahead '*', M[Tp][*] = 4)
  11     match *
  12     expand F -> id
  13     match id
  14     expand Tp -> epsilon
  15     expand Ep -> epsilon
  16     stack $ , lookahead $  ->  ACCEPT

  the sequence of "expand" lines IS a leftmost derivation (Module 19), now
  produced by table lookup instead of a call stack.

A conflict — M[Sp][else]

  Sp -> else S     PREDICT { else }
  Sp -> epsilon    PREDICT { else $ }      (else from FOLLOW(Sp))

  M[Sp][else] := Sp -> else S       then      M[Sp][else] := Sp -> epsilon   COLLISION

  one cell, two productions. the grammar is not LL(1); left factoring
  (Module 24) removed the shared "if b then S" prefix but not this.

The Code, Explained

Building the table

The table-driven parse loop

Push the RHS in reverse

A → X₁ X₂ X₃: push X₃, then X₂, then X₁, so X₁ is on top and gets processed first. The stack always holds "the rest of the sentential form, left end up" — the same object recursive descent kept implicitly in its call frames (Module 19).

Limits — what this module cannot do yet

Can't do yet

  • Build the parse tree / drive semantic actions during the walk — Module 26 (and Part V).
  • Recover from a blank cell and keep parsing — Module 27 (panic mode, FOLLOW sync sets).
  • Resolve a conflict by policy (prefer the shift for dangling else) — a hand edit to the cell, formalised in Module 35 for LR.
  • Handle LL(2)+ — a single lookahead column only (Module 29).
  • Parse anything an LR grammar can but LL can't — Part IV.

Can do

  • Build M[A][t] for any grammar from its PREDICT sets.
  • Decide LL(1) and name every conflicted cell (nonterminal, token, both productions).
  • Place FOLLOW-driven cells for nullable productions correctly.
  • Distinguish a blank cell (error) from an explicit epsilon cell.
  • Run the table over an input with an explicit stack, to ACCEPT.

Getting a blank or broken result?

A nullable production is missing from the table — fill from PREDICT (which includes FOLLOW for nullable α), not FIRST alone.
$ has no column — add it.
Conflict silently lost — you overwrote the cell; keep a list and check size > 1.
Parse loops forever — you pushed the RHS in the wrong order, or didn't pop A before pushing.

07

Brain Exercise

(1) For the expression table, what is M[F][+], and what does the parser do when it lands there? (2) The dangling-else conflict cell M[Sp][else] holds Sp → else S and Sp → ε. If you had to keep one, which, and what behaviour does that give?

Answers

(1) M[F][+] is blank. If the parser is expanding F and sees +, it's a syntax error — no factor can start with +. (This happens e.g. on input id + + id after the first + is consumed.)

(2) Keep Sp → else S. That means: whenever an else is available, attach it to the nearest unmatched if. This is the conventional resolution — "else binds to the closest if" — and it's what C, Java, and friends do. Keeping Sp → ε instead would make else attach to the outermost if, which nobody wants.

08

There Are No Dumb Questions

Is the table just the PREDICT sets in a different shape?

Essentially yes — it's PREDICT sets transposed into a (nonterminal × token) grid. The value the table adds is the collision check: filling the grid surfaces exactly which cell two productions fight over, which the per-rule PREDICT view can also show but the grid makes unmissable.

Why is a blank cell an error and not "do nothing"?

"Do nothing" would leave the nonterminal on the stack unexpanded and the parser stuck. A blank cell means the grammar has no way to derive the current token from the current nonterminal — the input is not in the language. The parser reports the position and (Module 27) tries to recover.

Recursive descent (Module 19) had no table. What changed?

Nothing, conceptually. Recursive descent encodes M[A][t] as the if/switch statements inside parseA, and the stack as the call stack. The table makes the same information data instead of code — which is what a parser generator emits, and what Module 26 executes.

Can I edit a conflicted cell by hand to force a choice?

Yes, and real tools do — yacc/Bison resolve shift-reduce conflicts by a default rule and let you override with precedence declarations (Module 35). For LL(1) you'd just pick one production for the cell and document it. It's no longer "LL(1)" in the pure sense, but it parses.

How big do these tables get for a real language?

Rows = nonterminals (dozens to low hundreds), columns = tokens (dozens). So thousands of cells, mostly blank. Stored sparsely. LR tables (Part IV) are much larger — thousands of states — which is why they're always generated, never hand-written.
