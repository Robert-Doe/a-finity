Ambiguity &Disambiguation

Some grammars give one string two parse trees — and therefore two meanings. This module builds a tool that finds every tree a grammar assigns a string, exhibits the classic ambiguities, and shows the two standard rewrites that force a grammar back to one tree per string without changing the language it accepts.

Ambiguity is not academic

Under E → E + E | E * E | id, the string id + id * id has two trees. With id = 2 one computes 6, the other 8. Same grammar, same input, two answers. A language cannot ship like that.

01

The Big Analogy — "the girl saw the boy with the binoculars"

Read that sentence. Who has the binoculars?

Reading 1: the girl used binoculars to see the boy. ("with the binoculars" attaches to saw.)

Reading 2: the girl saw a boy who was holding binoculars. ("with the binoculars" attaches to the boy.)

Same words, same order, two structures — because English grammar lets a "with …" phrase hang off either a verb or a noun, and nothing in the sentence says which. That is ambiguity: one string, two parse trees, two meanings.

id + id * id is the same situation with arithmetic. Does * id attach to the second id ("add, then multiply") or to the whole id + id ("multiply the sum")? The grammar E → E + E | E * E | id allows both, so both trees exist.

Two ways out, and languages use both:

  • Restructure so only one reading is grammatical — split E into precedence tiers. (This is "rewrite the sentence.")
  • Adopt a fixed rule — "a * always binds tighter than a +," "an else always matches the nearest then." (This is "we agree that 'with' attaches to the nearest noun.")
02

What Happens, Step by Step

  1. Find every leftmost derivation of the target string. Breadth-first over sentential forms. Prune a branch if it has more terminals than |w|, or if its finished terminal prefix (everything left of the leftmost nonterminal) doesn't already match w.
  2. Turn each into a parse tree (Module 5's build). Distinct leftmost derivations → distinct trees.
  3. Ambiguous for w iff two or more distinct trees. Ambiguous grammar iff ambiguous for some w.
  4. Witness search: walk the language in (length, lexicographic) order; the first string with ≥ 2 trees is the smallest witness.
  5. Disambiguate by hand: one nonterminal tier per precedence level; left-recursion for left-associativity. Then re-run steps 1–3 and confirm one tree per string.
  6. Confirm same language: compare the two grammars' bounded enumerations.

The state, drawn

Two trees for id + id * id (ambiguous grammar)

  TREE A  →  (id + (id * id))  =  6            TREE B  →  ((id + id) * id)  =  8

  E                                           E
  +- E                                        +- E
  |  +- id                                    |  +- E
  +- +                                        |  |  +- id
  +- E                                        |  +- +
     +- E                                     |  +- E
     |  +- id                                 |     +- id
     +- *                                     +- *
     +- E                                     +- E
        +- id                                    +- id

  the '+' is the root                          the '*' is the root
  → multiply first, then add                   → add first, then multiply

The disambiguated grammar: one tree, always

  E -> E + T | T        T -> T * F | F        F -> ( E ) | id

  '+' can only appear at the E level, '*' only at the T level.
  T nests inside E, so '*' nests inside '+', so 'id * id' groups first.
  Every string gets exactly ONE tree — the "(id + (id * id))" one.

Dangling else — if x then if x then a else b

  TREE A: else with the INNER if          TREE B: else with the OUTER if
  S                                       S
  +- if x then                            +- if x then
  +- S                                    +- S  = (if x then a)
     +- if x then a else b                +- else
                                          +- S  = b

  "if x then (if x then a else b)"        "if x then (if x then a) else b"

The Code, Explained

The search, and the prune that makes it fast

The prefix prune (form.subList(0, i) must match) is what turns a hopeless exponential search into an instant one: a wrong first token dies at depth 1, not after the whole string is generated.

Ambiguity made concrete — the two trees compute different numbers

// Main.evalExpr — id = 2, walk the tree
if (k.size() == 3) {
  if (k.get(0).symbol.equals("(")) return evalExpr(k.get(1));
  long a = evalExpr(k.get(0)), b = evalExpr(k.get(2));
  return switch (k.get(1).symbol) {
    case "+" -> a + b;
    case "*" -> a * b;
  };
}
// TREE A → 6,  TREE B → 8
Crazy detail — you cannot write a "is this grammar ambiguous?" checker

It is undecidable. No algorithm takes an arbitrary context-free grammar and answers yes/no. Our smallestAmbiguousString only searches strings up to a length bound — a null result means "no witness this short," never "unambiguous." And some languages are inherently ambiguous: every grammar for { aⁱbʲcᵏ : i = j or j = k } is ambiguous. See DECISIONS.md.

05

Limits — what this module cannot do yet

Can't do yet

  • Decide whether a grammar is ambiguous — only find witnesses up to a length bound.
  • Disambiguate automatically. The rewrites are done by hand and verified; there's no transform.
  • Prove two grammars generate the same language — only compare bounded enumerations.
  • Handle a grammar with unit or ε cycles — the search would spin (Modules 16, 23).
  • Resolve the dangling else inside the grammar without adding tiers — that's Module 35's shift-preference.

Can do

  • Enumerate every parse tree a grammar assigns a given string.
  • Report a grammar ambiguous for a string, with all its trees rendered.
  • Find the smallest ambiguous string up to a bound.
  • Show ambiguity means different values, not just different pictures.
  • Verify a hand-disambiguated grammar has one tree per string and the same bounded language.
  • Exhibit precedence and associativity ambiguity, and the dangling else.

Getting a blank or broken result?

allTrees returns 0 — the string isn't in the language; check it against Derivation.enumerate first.

smallestAmbiguousString returns null for a grammar you know is ambiguous — its shortest witness is longer than maxLen. Raise the bound. (It still can't certify unambiguous.)

07

Brain Exercise

Both trees for id + id + id evaluate to 6, because addition is associative. So is that ambiguity harmless — can the parser just pick either tree?

Then: name a binary operator where the two trees give different answers, and one where they always agree no matter the values.

Answer

Not harmless. Even when the value is the same, the tree isn't — and everything downstream keys off the tree: type checking, code generation, error messages ("expected ) after the second id"), source maps, refactoring tools, pretty-printers. A language spec has to state which tree, or two conforming implementations disagree about the program's structure even when they agree about its result. "Addition associates left" is in the spec of every real language for exactly this reason.

Disagree: subtraction. (8 - 4) - 2 = 2 but 8 - (4 - 2) = 6. Same for division, exponentiation (2^(2^3) = 256 vs (2^2)^3 = 64), and string --like operations. Always agree: + and * on numbers, min, max, boolean and/or, string concatenation, set union — the associative operators. Even for these, see the previous paragraph: the parser still must commit.

08

There Are No Dumb Questions

Is every grammar with E -> E op E ambiguous?

If it has two or more operators at that shape, or one operator that could associate either way — yes. E -> E + E | id alone is ambiguous (id + id + id has two trees). The fix is always the same: a nonterminal tier per precedence level, and pick a recursion side per operator for its associativity.

The disambiguated grammar is left-recursive. Module 5 said that's a problem!

Left recursion breaks a top-down parser (Module 16). It has nothing to do with ambiguity. The tiered grammar E -> E + T | T is unambiguous and left-recursive — those are independent properties. Module 16 removes the recursion while keeping it unambiguous; the tree shape is preserved.

Can every ambiguous grammar be fixed?

No, on two counts. (1) Deciding whether a given grammar is ambiguous is undecidable — you can't even always tell if there's a problem. (2) Some context-free languages are inherently ambiguous: every grammar that generates them is ambiguous. The expression language is not one of those, which is why the E/T/F rewrite works.

How do real parser generators handle the dangling else?

yacc/Bison see it as a shift-reduce conflict and resolve it by preferring to shift — which means "keep reading, attach the else to the nearest then." That's the same rule C, Java, and most languages specify. Module 35 covers exactly this.

smallestAmbiguousString returned null. Is my grammar unambiguous?

Only "no ambiguous string of length ≤ maxLen." It is not a certificate. There is no algorithm that certifies a CFG unambiguous — if you need certainty, you restructure the grammar into a form whose parsing method (LL, LR) cannot be ambiguous, which is what Parts III–IV are about.

What's Next

You've now seen what grammars can do too much of. Module 7 — The Chomsky Hierarchy & Pumping Lemmas shows what they can't do at all. A regular grammar provably cannot match aⁿbⁿ — it has no way to remember how many as it saw. A context-free grammar provably cannot match aⁿbⁿcⁿ. You'll build the pumping argument as code: given a candidate regular grammar and a target language, produce the specific string it must accept but shouldn't.
