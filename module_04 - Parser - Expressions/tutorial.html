Module 04

Parser — Expressions

Turning a flat token stream into a structured tree

Prerequisites: Module 01 — Source Module 02 — Lexer Module 03 — Symbol Table
Before continuing, make sure you know: the Token struct and all its fields, how lexer_next() works (one call = one token, advances position), and what a tree data structure is (nodes with parent/child relationships, recursive traversal).

01 — The Story Analyst

Analogy

The Script Supervisor (Module 02, the Lexer) labelled every word in the script: "this is a noun", "this is a verb", "this is an adjective". She produced a flat list of labelled words — a token stream.

Now the Story Analyst reads that labelled list and understands structure. When she sees the sentence "John hit Mary hard", she knows:

  • "hit" is the main action (the root of the tree)
  • "John" is the subject (left child)
  • "Mary hard" is the object group (right child) — and within that, "hard" modifies "hit", not "Mary"

She draws a tree. Your parser is that Story Analyst. It reads the token stream and constructs the Abstract Syntax Tree (AST).

Here is the concrete example. The token stream for 3 + 4 * 2 on the left, and the AST it becomes on the right:

Token Stream

  • INT_LIT 3
  • PLUS +
  • INT_LIT 4
  • STAR *
  • INT_LIT 2
  • EOF

Abstract Syntax Tree

+ / \ 3 * / \ 4 2

Notice that * is deeper in the tree than +. Deeper = higher precedence = computed first. The tree structure encodes precedence automatically. That is the main job of a parser.

02 — Precedence and Recursion

Why 3 + 4 * 2 equals 11, not 14

We all learn in school that multiplication happens before addition. But why? And how does a parser know?

In our recursive descent parser, precedence is encoded as layers of functions. The function that handles + and - always calls the function for * and / to get its operands. That means multiplication is always parsed first — it is "deeper" in the call stack.

The call stack as a precedence ladder

When the parser sees 3 + 4 * 2, the call sequence looks like this:

parse_expr entry point
parse_logical && ||
parse_comparison == != < > <= >=
parse_additive + − ← handles 3 + …
parse_multiplicative * / % ← handles 4 * 2
parse_unary −x
parse_primary 3 4 2 foo(…) (…)

parse_additive calls parse_multiplicative to get its left operand. So by the time parse_additive sees the +, it already has an entire multiply-group as the left side. The tree comes out right automatically.

03 — The Grammar

Here is the formal grammar for Module 04 expressions. Each rule is one function in parser.c.

expr = logical
Top-level entry point — delegates everything to logical.
logical = comparison (('&&' | '||') comparison)*
Logical AND/OR — lowest precedence among binary operators.
comparison = additive (('=='|'!='|'<'|'>'|'<='|'>=') additive)*
Relational operators — compare two numeric values.
additive = multiplicative (('+' | '-') multiplicative)*
Addition and subtraction.
multiplicative = unary (('*' | '/' | '%') unary)*
Multiplication, division, modulo — higher precedence than addition.
unary = '-' unary | primary
Prefix negation — right-recursive so -(-(x)) works.
primary = INT_LIT | IDENT '(' arglist ')' | IDENT | '(' expr ')'
Atoms: literals, identifiers, function calls, parenthesised sub-expressions.
arglist = (expr (',' expr)*)?
Zero or more comma-separated expressions inside a function call.

04 — Reading parse_additive

Let's walk through the most instructive function line by line. The same pattern repeats in parse_logical, parse_comparison, and parse_multiplicative.

static Node *parse_additive(Parser *p) {
    /* Parse the left operand first — higher-precedence multiplication. */
    Node *left = parse_multiplicative(p);

    /* Left-associativity via while loop.
     * Each iteration consumes one operator and one right operand.
     * 3 + 4 + 5  becomes  ((3 + 4) + 5)  — left-leaning tree. */
    while (check(p, TOK_PLUS) || check(p, TOK_MINUS)) {

        /* Encode the operator before advancing (advancing overwrites current). */
        char op   = check(p, TOK_PLUS) ? '+' : '-';
        int  line = p->current.line;  /* record source line for error messages */
        advance(p);                   /* consume + or - */

        /* Parse the right operand — again at the higher-precedence layer. */
        Node *right = parse_multiplicative(p);

        /* Build a BINARY node that holds both operands. */
        Node *n  = node_new(AST_BINARY, line);
        n->op    = op;
        n->left  = left;
        n->right = right;

        /* The new node BECOMES the left operand for the next iteration.
         * This is the key to left-associativity: folding left. */
        left = n;
    }

    return left;
}

The while loop is the standard fix for left-recursive grammars. On every iteration it consumes at least one token (the operator), so the loop is guaranteed to terminate.

After parsing 3 + 4 + 5, the tree looks like:

  BINARY '+'
    BINARY '+'
      INT 3
      INT 4
    INT 5

The 3 + 4 subtree is on the left, which means it is evaluated first — correct left-to-right behaviour.

05 — The AST Node

Every construct in the language — literals, operators, calls — becomes one Node. We use a single "fat" struct where different node kinds use different subsets of the fields:

struct Node {
    NodeKind  kind;   /* tag: what kind of node is this? */
    long      ival;   /* integer value — AST_INT_LIT only */
    char     *sval;   /* heap name — IDENT, CALL, ASSIGN, VAR_DECL, FUNC */
    char      op;     /* operator char — UNARY and BINARY */
    Node     *left;   /* first child */
    Node     *right;  /* second child */
    Node     *extra;  /* third child — else branch in AST_IF */
    Node    **args;   /* dynamic array — call args, block stmts, func params */
    int       nargs;  /* count of entries in args[] */
    int       line;   /* source line for error messages */
};

This is called the tagged-union pattern (or discriminated union). The kind field is the tag — it tells us which other fields are valid. Unused fields are zeroed by memset in node_new, so NULL-checks are always safe.

Example: node_print output for foo(1, 2 + 3)

  CALL 'foo' (2 args)
    INT 1
    BINARY '+'
      INT 2
      INT 3

The CALL node stores the function name in sval and keeps its arguments in the args[] dynamic array. The second argument 2 + 3 is itself a subtree.

Brain Exercise

Challenge

You try to write the grammar rule for additive as left-recursive:

additive = additive ('+' | '-') multiplicative
         | multiplicative

What happens when you turn this directly into a recursive descent function in C?

Show answer

Infinite recursion. The function's first action is to call itself before consuming any input token. Every call to parse_additive immediately calls parse_additive again, which calls it again — the call stack grows until the process crashes with a stack overflow.

The fix is to rewrite the rule using a * (repeat) instead of left recursion:

additive = multiplicative (('+' | '-') multiplicative)*

In code, this becomes a while loop. Every iteration consumes at least one token (the operator), so the loop always terminates.

Q & A

Why a tree and not a list?
Because trees naturally capture nesting and precedence. A flat list of tokens like [3, +, 4, *, 2] can't represent "multiply before add" without extra parentheses or an additional pass. A tree represents it structurally: the * node is a child of the + node, so it is evaluated first automatically during any tree traversal.
What's the difference between parse_expr and parse_additive?
parse_expr is the public entry point for expression parsing — it is the name callers use. Internally it just calls parse_logical, which eventually calls parse_additive. They are different precedence layers in the same hierarchy. parse_additive only handles + and -; anything higher-precedence is handled by the functions below it in the call chain.
Why does parse_primary handle function calls?
Because foo(a, b) starts with an identifier, just like a variable reference foo. We cannot tell it is a call until we see the ( that follows the name. parse_primary is the right place to check for this: we have already consumed the identifier, we peek at the next token, and if it is ( we continue parsing an argument list. If it is not (, we return a plain AST_IDENT node.
