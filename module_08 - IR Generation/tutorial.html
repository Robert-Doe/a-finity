Section 01

The Analogy — Storyboard Artist

Analogy: Imagine a film production. The script is your C source. The script analyst (parser + semantic checker) reads it and builds a structured breakdown — the AST — capturing every dramatic intent. Now the storyboard artist enters. Their job is to take that script analysis and draw out every single camera shot in sequence. No ambiguity. No nested structure. Just a flat stack of panels, each showing one atomic action: "camera pans left", "actor picks up glass", "cut to close-up". That ordered stack of panels is your IR.

Every panel in a storyboard corresponds to one IRInstr. The sticky notes the artist sticks on each panel — "this shot is labelled TAKE_3", "this prop is called 'the glass'" — correspond to temporary registers (t0, t1, …) and label names (L0, L1, …).

Just like a storyboard, the IR is:

  • Flat — no nesting, no tree, just a linked list you walk top to bottom.
  • Unambiguous — each instruction does exactly one thing.
  • Order-preserving — you can read it left-to-right and know exactly what happens when.
  • Machine-independent — no register names, no memory addresses; those come later.

The AST captures intent (what the program means). The IR captures sequence (what the program does, step by step). Every later phase — optimiser, register allocator, code generator — works on the IR, not the AST.

Section 02

The IR Instruction Set

The full instruction set is defined in ir.h as the IROp enum. Every instruction has at most three operand fields: dst, src1, src2. Unused fields are set to IR_NO_TEMP (the sentinel value -1). 

typedef enum {
    /* Value-producing instructions ─────────────────────────── */
    IR_ICONST,  /* t_dst = ival                  load an integer constant      */
    IR_COPY,    /* t_dst = t_src1               copy one temp to another       */

    /* Arithmetic ───────────────────────────────────────────── */
    IR_ADD,     /* t_dst = t_src1 + t_src2                                       */
    IR_SUB,     /* t_dst = t_src1 - t_src2                                       */
    IR_MUL,     /* t_dst = t_src1 * t_src2                                       */
    IR_DIV,     /* t_dst = t_src1 / t_src2                                       */
    IR_MOD,     /* t_dst = t_src1 % t_src2                                       */
    IR_NEG,     /* t_dst = -t_src1              unary negation                    */

    /* Comparisons (result is 1 or 0) ───────────────────────── */
    IR_LT,      /* t_dst = t_src1 <  t_src2                                      */
    IR_GT,      /* t_dst = t_src1 >  t_src2                                      */
    IR_LEQ,     /* t_dst = t_src1 <= t_src2                                      */
    IR_GEQ,     /* t_dst = t_src1 >= t_src2                                      */
    IR_EQ,      /* t_dst = t_src1 == t_src2                                      */
    IR_NEQ,     /* t_dst = t_src1 != t_src2                                      */

    /* Logical (eager — no short-circuit in Module 08) ─────── */
    IR_AND,     /* t_dst = t_src1 && t_src2   both operands always evaluated     */
    IR_OR,      /* t_dst = t_src1 || t_src2                                      */

    /* Control flow ─────────────────────────────────────────── */
    IR_LABEL,   /* LABEL name                  define a jump target               */
    IR_JUMP,    /* JUMP name                   unconditional branch               */
    IR_JUMPZ,   /* JUMPZ t_src1 name           branch to name if t_src1 == 0     */

    /* Function calls ───────────────────────────────────────── */
    IR_PARAM,   /* PARAM t_src1               push one argument for next call    */
    IR_CALL,    /* t_dst = CALL name (nargs)   call function, capture return val  */
    IR_RETURN,  /* RETURN t_src1              return value (IR_NO_TEMP = void)   */

    /* Local variable memory ────────────────────────────────── */
    IR_STORE,   /* STORE name = t_src1        write to named local variable       */
    IR_LOAD,    /* t_dst = LOAD name          read from named local variable      */
} IROp;

Section 03

How irgen Walks the AST

IR generation is a recursive descent over the AST — the same idea as the parser, but this time we are consuming a tree and producing a list. The entry point irgen() iterates over the top-level AST_PROGRAM children, calling gen_function() for each AST_FUNC node. 

/* Simplified call hierarchy */

irgen(Node *program)
  for each AST_FUNC child:
    gen_function(IRProg *, Node *func)
      gen_stmt(IRFunc *, Node *body_block)    /* recurse on each statement */
        /* AST_BLOCK   → recurse on each child statement */
        /* AST_RETURN  → gen_expr() the return value, emit IR_RETURN */
        /* AST_IF      → gen_expr() cond, emit JUMPZ + labels */
        /* AST_WHILE   → emit top-of-loop LABEL, gen_expr() cond, JUMPZ, body, JUMP back */
        /* AST_VAR_DECL→ increment n_locals; emit IR_STORE if there is an initialiser */
        /* AST_EXPR_STMT→ gen_expr() for side-effects, discard result temp */
        /* AST_ASSIGN  → gen_expr() the rhs, emit IR_STORE */

      gen_expr(IRFunc *, Node *expr)          /* returns result temp number */
        /* AST_INT_LIT → emit IR_ICONST, return dst */
        /* AST_IDENT   → emit IR_LOAD,   return dst */
        /* AST_UNARY   → gen_expr(operand), emit IR_NEG, return dst */
        /* AST_BINARY  → gen_expr(left), gen_expr(right), emit IR_ADD/SUB/… */
        /* AST_ASSIGN  → gen_expr(rhs), emit IR_STORE, return rhs temp */
        /* AST_CALL    → gen_expr each arg + IR_PARAM, emit IR_CALL, return dst */

Focus on AST_BINARY — the workhorse for expressions: 

case AST_BINARY: {
    /* 1. Map the source operator to an IROp */
    IROp op;
    switch (n->op) {
        case TOK_PLUS:  op = IR_ADD; break;
        case TOK_MINUS: op = IR_SUB; break;
        case TOK_LT:    op = IR_LT;  break;
        /* … and so on … */
    }
    /* 2. Evaluate left operand (recursive) → result in temp 'left' */
    int left  = gen_expr(f, n->args[0]);
    /* 3. Evaluate right operand (recursive) → result in temp 'right' */
    int right = gen_expr(f, n->args[1]);
    /* 4. Allocate a fresh destination temp */
    int dst   = ir_new_temp(f);
    /* 5. Emit the binary instruction */
    IRInstr *instr = ir_new_instr(op);
    instr->dst  = dst;
    instr->src1 = left;
    instr->src2 = right;
    ir_append(f, instr);
    return dst;   /* caller uses this temp as their src1 or src2 */
}

And the AST_WHILE control-flow pattern: 

case AST_WHILE: {
    int loop_lbl = ir_new_label(f);   /* e.g. 0 → "L0" */
    int end_lbl  = ir_new_label(f);   /* e.g. 1 → "L1" */

    /* ── top of loop ── */
    emit IR_LABEL L0

    /* ── evaluate condition ── */
    int cond = gen_expr(f, n->args[0]);
    emit IR_JUMPZ t_cond L1        /* exit loop if cond is false */

    /* ── loop body ── */
    gen_stmt(f, n->args[1]);

    /* ── back edge ── */
    emit IR_JUMP L0

    /* ── after loop ── */
    emit IR_LABEL L1
}

Section 04

Translating sample.c — The Actual IR Output

Here is sample.c — the program we compile:

int add(int a, int b) {
    return a + b;
}

int main(void) {
    int i;
    int sum;
    i   = 1;
    sum = 0;
    while (i < 6) {
        sum = add(sum, i);
        i   = i + 1;
    }
    return sum;
}

Running make run prints this IR (one instruction per line, temporaries named t0, t1, …, labels named L0, L1):

  t10 = ADD t8 t9
  STORE i = t10
  JUMP L0
  LABEL L1
  t11 = LOAD sum
  RETURN t11

Trace Through the While Loop

The pattern for while (i < 6) is textbook:

  1. LABEL L0 — top of loop; the back-edge jump lands here.
  2. t2 = LOAD i and t3 = ICONST 6 — materialise both operands of the condition.
  3. t4 = LT t2 t3 — compute the boolean result (1 or 0).
  4. JUMPZ t4 L1 — if the condition is false (t4 == 0), exit the loop by jumping to L1.
  5. Loop body instructions …
  6. JUMP L0 — back edge: go re-evaluate the condition.
  7. LABEL L1 — merge point after the loop.

Trace Through the Function Call

The call add(sum, i) follows the PARAM / CALL convention:

  1. Evaluate argument 0: t5 = LOAD sum, then PARAM t5.
  2. Evaluate argument 1: t6 = LOAD i, then PARAM t6.
  3. t7 = CALL add (2 args) — the callee pops 2 PARAMs and returns its value into t7.
  4. STORE sum = t7 — write the result back to the local variable sum.

Troubleshooting

  • "implicit declaration of function" — check that every .h is included at the top of the .c that uses it.
  • "undefined reference to …" — make sure the SRCS list in the Makefile includes every .c file.
  • parse/semantic errors — the driver aborts before calling irgen() if the front-end fails; fix sample.c first.

Section 06

Brain Exercise

Challenge

In Module 08, IR_OR takes two already-evaluated temporaries and produces a result: 

t2 = OR t0 t1

Given only the instructions available in Module 08 (no new ops allowed), how would you translate the C assignment: 

x = a || b;

into IR? (Assume a, b, and x are already declared local variables.)

Show answer

Evaluate each operand to its own temporary, apply IR_OR, then store the result:

t0 = LOAD a          /* evaluate operand a */
t1 = LOAD b          /* evaluate operand b */
t2 = OR t0 t1      /* eager logical OR   */
STORE x = t2        /* write result to x  */

This is eager evaluation: both a and b are always loaded, even if a is already true. C's actual || must not evaluate b when a is true — that is the short-circuit guarantee. Implementing short-circuit correctly requires inserting a conditional jump between the two LOAD instructions, which is the topic of Module 09.

Section 07

Q&A

Why does every variable access go through IR_LOAD and IR_STORE instead of just assigning each variable a permanent temporary at declaration time?

Because C variables live in memory (the stack frame), not in registers. Using IR_LOAD/IR_STORE makes the IR honest: it says "read from memory, write to memory," which is exactly what the hardware will do unless a later register-allocation pass decides to promote a variable to a register. Mapping variables directly to permanent temporaries would bake a register-allocation decision into the IR generator — the wrong layer.

Why is IR_NO_TEMP set to -1 rather than 0?

Zero is a valid temporary number (t0). If IR_NO_TEMP were 0, then a freshly memset-zeroed IRInstr would silently look like it had t0 in all three operand slots, producing wrong IR that is hard to debug. With -1, every initialisation bug shows up immediately as an impossible temporary number.

Why does ir_append maintain both head and tail pointers instead of just head?

Without a tail pointer, every append would have to walk the entire list to find the last node — O(N) per append, O(N²) overall for a function with N instructions. Keeping tail makes each append O(1), at the cost of a single extra pointer per IRFunc struct — a trivial price.

Why use a linked list of IRInstr nodes instead of a dynamic array?

Two reasons. First, node addresses are stable: if we allocate IRInstr nodes on the heap and a later pass holds a pointer to one (e.g. a JUMPZ that needs to be back-patched), a dynamic array reallocation would invalidate that pointer. Second, inserting an instruction between two existing ones requires only pointer surgery — no shifting of array elements. The downside (no random access, worse cache locality) matters more once the IR is very large; a later module could switch to a chunked arena if needed.

Section 08

What's Next

Module 09 — IR Optimisation: Constant Folding

The IR you built in Module 08 is correct but unoptimised. Take a look at the add function's IR: 

  t0 = LOAD a
  t1 = LOAD b
  t2 = ADD t0 t1
  RETURN t2

If a caller passes two integer literals — say add(3, 4) — the compiler already knows the result is 7 at compile time. Constant folding is the pass that detects ICONST + ICONST patterns and collapses them into a single ICONST, eliminating the arithmetic instruction entirely.

Module 09 also introduces the short-circuit fix for && and ||: a dedicated gen_cond() path that threads "true label / false label" through expression generation so the second operand is only evaluated when needed.

You will reuse every file from Module 08 unchanged. Module 09 adds a new opt.c / opt.h layer that sits between irgen() and ir_print().
