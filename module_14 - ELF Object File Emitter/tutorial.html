Section 01

Analogy: The Post-Production House

Imagine your compiler pipeline as a film studio:

  • The source file is the script
  • The parser and IR are the director turning the script into raw footage
  • The optimizer is the film editor cutting unnecessary frames
  • The x86enc layer (Module 13) produces edited reels of actual film — bytes of machine code

But edited reels alone cannot be shown in a cinema. They need to be packaged into a deliverable format that the cinema's projector can understand.

The Post-Production House

The ELF emitter (elf_emit.c) is the post-production house. It takes the edited film reels (machine code bytes) and packages them into a standard deliverable format (an ELF64 .o file). The distributor (the linker, gcc -no-pie) can then combine multiple reels from different studios (other .o files) into a finished film (a runnable binary executable).

The key insight: we don't need to produce the final movie ourselves. We just need to package our reels correctly so the distributor knows what they contain and where each scene starts.

Section 02

What Is an ELF File?

ELF stands for Executable and Linkable Format. It is the standard binary format on Linux (and WSL). There are two major variants relevant to us:

e_typeNameRole
ET_REL Relocatable object A .o file — not directly runnable; contains machine code and symbol tables; must be linked
ET_EXEC Executable Directly runnable; all addresses resolved; produced by the linker from one or more ET_REL files

We produce ET_REL. The file has this overall structure:

┌─────────────────────────────────────────┐ │ ELF Header (64 bytes) │ e_type=ET_REL, e_machine=EM_X86_64 │ e_shoff → section headers │ points to the section header table ├─────────────────────────────────────────┤ │ .text — SHT_PROGBITS │ raw machine code bytes ├─────────────────────────────────────────┤ │ .symtab — SHT_SYMTAB │ one Elf64_Sym per exported function ├─────────────────────────────────────────┤ │ .strtab — SHT_STRTAB │ null-terminated symbol names ├─────────────────────────────────────────┤ │ .shstrtab — SHT_STRTAB │ null-terminated section names ├─────────────────────────────────────────┤ │ Section Header Table (5 × 64 bytes) │ null, .text, .symtab, .strtab, .shstrtab └─────────────────────────────────────────┘

The ELF header at the top points to the section header table at the bottom (via e_shoff). Each section header describes one section: its type, its byte offset in the file, its size, and any links to other sections.

ET_REL vs ET_EXEC

In ET_REL mode, symbol addresses (the st_value field in .symtab) are offsets within their section, not absolute addresses. The linker reads these offsets, determines the final load address for each section, and patches all call/jump targets accordingly. That is why we can emit call rel32 with a zero displacement for calls between our own functions — the linker fills in the correct relative offset.

Section 03

The .text Section

The .text section is where your machine code lives. In our emitter, functions are added one at a time with elf_add_func(), which simply concatenates each function's bytes into a flat text[] buffer:

void elf_add_func(ElfEmitter *e, const char *name,
                  const uint8_t *code, size_t code_len) {
    e->sym_offsets[e->n_syms] = e->text_size;  // where this func starts
    e->sym_sizes  [e->n_syms] = code_len;
    strncpy(e->sym_names[e->n_syms], name, 63);
    memcpy(e->text + e->text_size, code, code_len);
    e->text_size += code_len;
    e->n_syms++;
}

Each function also gets a global symbol in .symtab so the linker can identify it by name. The symbol's st_value is the byte offset within .text where the function begins, and st_size is its length in bytes.

Section flags

.text has flags SHF_ALLOC | SHF_EXECINSTR: the OS should map it into memory (ALLOC) and the bytes are executable instructions (EXECINSTR).

Section 04

Building the ELF Manually

The core of Module 14 is elf_write(). Here is a walk-through of each step:

Step 1 — Build the string tables in memory

Before writing the ELF header we need to know the sizes of .strtab and .shstrtab so we can calculate file offsets.

// .strtab: \0, then each function name null-terminated
strtab[0] = '\0';
for each function i:
    sym_name_off[i] = strtab_size;
    append name + '\0' to strtab;

// .shstrtab: fixed string "\0.text\0.symtab\0.strtab\0.shstrtab"

Step 2 — Compute file layout

offset 0 → ELF header (64 bytes) offset 64 → .text (text_size bytes) offset 64+text_size → .symtab ((1 + n_syms) × 24 bytes) offset ... → .strtab (strtab_size bytes) offset ... → .shstrtab (fixed size) offset ... (8-aligned)→ Section Header Table (5 × 64 bytes)

Step 3 — Write the ELF header

The header is 64 bytes. Key fields:

  • e_ident: magic bytes 7f 45 4c 46 + class/endian/version bytes
  • e_type = ET_REL, e_machine = EM_X86_64
  • e_shoff: byte offset of the section header table
  • e_shnum = 5 (null, .text, .symtab, .strtab, .shstrtab)
  • e_shstrndx = 4 (index of .shstrtab section)

Step 4 — Write sections sequentially

After the header, write: .text bytes → .symtab entries → .strtab → .shstrtab → pad to 8-byte alignment → section header table.

Step 5 — Write section headers

Five Elf64_Shdr structures, each 64 bytes:

IndexNamesh_typesh_flagssh_link / sh_info
0(null)SHT_NULL0—
1.textSHT_PROGBITSALLOC|EXECINSTR—
2.symtabSHT_SYMTAB0link=3 (.strtab), info=1 (first global)
3.strtabSHT_STRTAB0—
4.shstrtabSHT_STRTAB0—
Little-endian helpers

All multi-byte values in ELF64 on x86-64 are little-endian. We use simple helper functions — write_u16, write_u32, write_u64 — that write each byte individually in the right order into the output buffer.

Section 05

Run It

Compile the compiler, compile sample.c, link it, and run:

$ make link gcc -Wall -Wextra -Werror -std=c11 -c source.c -o source.o gcc -Wall -Wextra -Werror -std=c11 -c lexer.c -o lexer.o ... (compiling all modules) ... gcc -Wall -Wextra -Werror -std=c11 -o mycc14 source.o lexer.o symtab.o ast.o parser.o sema.o ir.o opt.o regalloc.o x86enc.o codegen.o elf_emit.o main.o ./mycc14 sample.c -o sample14.o compiled 2 functions to sample14.o gcc -no-pie sample14.o -o sample14_bin && ./sample14_bin; echo "exit: $?" exit: 55

Exit code 55 is the 10th Fibonacci number — exactly what fib(10) should return. The machine code we emitted byte-by-byte runs correctly through the entire pipeline from source to ELF to binary.

Verify with readelf

You can inspect your output object file:

readelf -a sample14.o

Look for: Type: REL (Relocatable file), section .text, and symbol entries for fib and main marked GLOBAL FUNC.

Section 06

Brain Exercise

Question

The .o file stores function names in .symtab. Why does the linker need function names? Couldn't it just use byte offsets?

Answer: Byte offsets only make sense within a single .o file. When you write a program spread across multiple source files — say main.c calls fib() which is defined in fib.c — each file is compiled to its own .o. At the time main.o is produced, the compiler has no idea where fib will end up in memory. It cannot write a numeric offset because that offset is unknown.

Names solve this. main.o records a symbolic reference to the name fib. fib.o records a symbol definition for fib at a known offset within its own .text. The linker reads both files, matches the reference to the definition by name, calculates the final address, and patches the call instruction in main.o with the correct relative offset.

Without names, the linker would need some other shared coordinate system across files — which would require knowing the final layout before linking begins. That is a chicken-and-egg problem. Names are the clean solution.

Section 07

Q & A

Why is the null section header (index 0) required?

The ELF specification reserves section index 0 as a sentinel meaning "no section" or "undefined". Many fields use section index 0 as a null reference — for example, undefined symbols in .symtab have st_shndx = SHN_UNDEF = 0. The null section header physically occupies index 0 in the section header table to ensure every other section gets a non-zero index that can be used unambiguously as a reference.

What does sh_info = 1 mean in the .symtab section header?

For SHT_SYMTAB, the ELF specification defines sh_info as the index of the first global symbol in the symbol table. Symbols with index less than sh_info are local; those at sh_info and above are global. We have exactly one local entry — the mandatory null entry at index 0 — so sh_info = 1, meaning all subsequent entries (our function symbols) are global.

Why does .symtab's sh_link point to .strtab (section 3)?

The ELF spec defines sh_link for SHT_SYMTAB as the section index of the associated string table. Each Elf64_Sym has an st_name field that is a byte offset into that string table. The linker (and tools like readelf) follow sh_link to find where those byte offsets should be looked up.

Why do we align the section header table to an 8-byte boundary?

The ELF64 Elf64_Shdr struct contains 64-bit fields and is designed to be 8-byte aligned. While many tools tolerate unaligned section headers, the ELF specification recommends natural alignment and readelf may warn about misalignment. Since our section sizes are not necessarily multiples of 8, we pad with zero bytes between the last section and the section header table to ensure alignment.
