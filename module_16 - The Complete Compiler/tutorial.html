Section 00

You Built a Compiler

Module 1 started with a single C struct and a question: what even is a source file? Module 2 taught you to walk a string one character at a time, classify each byte, and produce a stream of tokens — the first machine-readable abstraction. Module 3 added a grammar, a recursive-descent parser, and your first real AST node. Module 4 introduced symbol tables so names could mean something. Module 5 ran the first semantic checks: "is that variable declared?" Module 6 lowered the AST to a flat, architecture-neutral IR — three-address code that no real CPU executes, but every real compiler uses. Module 7 layered on an optimiser that folded constants at compile time and eliminated dead code. Modules 8 and 9 produced actual x86-64 assembly — registers, the stack frame, the ABI. Module 10 switched to NASM text output so you could read every instruction your compiler emitted. Modules 11 and 12 refined the code generator with better addressing and proper ABI calling conventions. Module 13 added multi-function programs. Module 14 introduced a while loop and the branch-and-jump pattern. Module 15 gave the compiler a voice: a print statement backed by raw Linux syscalls in runtime.asm. And now — Module 16 — you wire every single one of those pieces into one executable, mycc, that takes a .c file and hands you back a running binary.

Section 02

The Driver

driver.c is the movie director's chair. It holds no creative opinion of its own — it just calls the right department at the right time, checks whether each step succeeded, and prints a timing report at the end.

Command-line interface

mycc <input.c> [-o <output>]

If -o is omitted, the output name is derived by stripping the .c suffix: foo.c → foo.

How driver.c wires the pipeline

// 1. Open source file
source_open(&src, input_file);

// 2. Initialise and warm the lexer
lexer_init(&lex, &src);

// 3. Parse
parser_init(&parser, &lex);
ASTNode *program = parse_program(&parser);

// 4. Semantic analysis — abort on errors
sema_check(&sema, program);

// 5. IR generation
IRProgram *ir = irgen(program);

// 6. Optimise
opt_all(ir);

// 7. Emit NASM to /tmp/mycc_XXXX.asm
codegen(ir, asm_fp);

// 8. Assemble
system("nasm -f elf64 /tmp/foo.asm -o /tmp/foo.o");

// 9. Find runtime.o (same dir as mycc, fallback to ./runtime.o)
// 10. Link
system("gcc -no-pie /tmp/foo.o runtime.o -o output");

// 11. Print timing table
print_timing_table(timing, ntiming);

Notice what jumps out: all of our compiler phases combined take under 0.3 ms. The assembler takes 14 ms. The linker takes 39 ms. This is why Google, Facebook, and Mozilla invested in distributed build systems — the bottleneck was never the compiler front-end.

Finding runtime.o
The driver first looks for runtime.o in the same directory as the mycc binary (using argv[0]). If that file does not exist, it falls back to ./runtime.o in the current working directory. This means make test from the project root always works, and you can also install mycc to /usr/local/bin next to runtime.o and it will still find the runtime.

The Test Suite

Five programs in tests/. Each one exercises a different feature. Together they form a regression ladder: if all five pass, the compiler is working.

How run_tests.sh validates a test

$COMPILER "$src" -o /tmp/test_bin 2>/dev/null  # compile
actual_out=$(/tmp/test_bin 2>/dev/null)          # run and capture stdout
actual_exit=$?                                   # capture exit code

# check exit code; if expected_out non-empty, check stdout too

Adding a new test

Add a .c file to tests/, then add one line to run_tests.sh:

run_test "t6_mytest" tests/t6_mytest.c 42 ""

The four arguments are: name, source file, expected exit code, expected stdout (empty string means "don't check stdout").

Why exit code as the primary signal?
Exit codes are visible without any print support and are the same mechanism that GCC's own test suite (DejaGNU) uses. A compiler that returns correct exit codes but broken stdout is rarer than the reverse, which is why stdout is a secondary, opt-in check.

Section 05

What This Compiler Can and Cannot Do

Honesty is part of engineering. Here is a precise account of what mycc handles and what it deliberately omits — and why.

  • strings / char* Requires a data section, pointer types, null-terminator semantics, and a print_str syscall shim. Adds ~300 lines; omitted to keep focus on pipeline architecture.
  • arrays / int a[N] Needs address arithmetic in the IR (IR_ARRAYLOAD/IR_ARRAYSTORE), stack-frame sizing for the array, and bounds-check semantics. Good Module 17 exercise.
  • structs / unions Requires a full type system with field offsets. Doubles the sema pass in complexity.
  • pointers / & * Alias analysis, address-taken variables, load/store IR ops. Triples the optimiser complexity.
  • float / double SSE2/AVX registers (xmm0–xmm7), a second calling convention lane, and FP literal parsing. Completely separate code path.
  • multiple types Only int and void. A real type system needs a type lattice, implicit conversions, and promotion rules.
  • preprocessor No #include, #define, or macros. The preprocessor is essentially a separate language — GCC implements it as an entirely separate pass.
  • multiple source files One .c → one binary. Separate compilation requires an object-file cache, symbol export tables, and a linker script.
  • stdlib (malloc, printf…) The only runtime function is print_int. The C standard library is an ocean; we shipped a rowboat on purpose.
  • switch / break / continue Implementable (switch becomes a chain of JUMPZ; break/continue need a target-label stack), but omitted to keep the grammar minimal.
  • variadic functions The ABI for ... requires va_list, register dumps, and a different calling convention path. Not needed for the course subset.
Section 06

Brain Exercise

🧠 Spot the bug

You add print(fib(10)); to t5_fibonacci.c and the program prints 55 correctly. But you also change main so it looks like this: 

int main(void) {
    print(fib(10));
    // forgot return statement
}

The program still prints 55, but the exit code is wrong. What is the most likely cause, and how do you fix it?

Reveal answer

When main has no return statement, the function falls through to the implicit ret at the end of the code generator's epilogue. At that point, rax contains whatever the last instruction left in it — which is the return value of print_int (typically syscall's byte-count return, i.e., 3 for "55\n"). The shell interprets rax mod 256 as the exit code, so you get 3 instead of 0 or 55.

Fix: always end main with an explicit return 0; (or return 55; if that is your intent). The version in t5_fibonacci.c correctly has return 55; after the print statement.

Deeper lesson: the C standard says falling off the end of main implicitly returns 0 — but only in real C compilers that know the return type of main is special. Our mycc does not implement that special case. Always write the return.

Section 07

Where to Go From Here

The course is over but the compiler is not finished — compilers are never finished. Here are six concrete extension projects, ordered roughly by difficulty.

a. Arrays

Add int a[10]; and a[i] = x;. You need AST_INDEX, an address-arithmetic IR op, and stack-frame sizing for the array block. The interesting sub-problem is bounds checking: do you add it at compile time (constant indices) or emit a runtime guard?

b. String Literals

Put "hello\n" literals in a section .rodata block, represent them as pointer IR operands, and write a print_str function in runtime.asm using sys_write with a computed length. The lexer change is small; the type-system change is the interesting part.

c. Multiple Source Files

Add an #include-like directive that reads a second file, parses it, and merges its function list into the current AST_PROGRAM. Now you need extern declarations in the sema pass and a two-phase link step. This teaches what a real linker actually resolves.

d. Real Register Allocator

Replace the one-slot-per-temp strategy with Chaitin-Briggs graph coloring. Build a liveness analysis pass over the IR, construct an interference graph, color it with the 15 general-purpose x86-64 registers, and spill only what cannot be colored. Expect 2× speedup on tight loops.

e. ARM64 Backend

Add a codegen_arm64.c that emits AArch64 assembly instead of x86-64. The IR is already architecture-neutral, so only the backend changes. Test on an Apple M-series Mac (native) or a Raspberry Pi. The calling convention and instruction encoding are completely different — a great way to see what the IR abstraction is worth.

f. Self-Hosting

Rewrite mycc itself in the subset of C that mycc can already compile — no structs, no standard library except print. Getting a compiler to compile itself is one of the most satisfying milestones in language implementation. It forces you to dog-food every limitation you omitted and proves the compiler is Turing-complete enough to describe itself.

Which extension first?
If you are comfortable with C and want the biggest payoff per line of code written, start with d (register allocator) — the IR infrastructure you built in Modules 6–7 is exactly the foundation you need, and the improvement in output quality is immediately visible. If you want to understand the full software stack better, start with e (ARM64 backend) — it forces you to think about what is truly in the compiler versus what is just x86-64 habit.
