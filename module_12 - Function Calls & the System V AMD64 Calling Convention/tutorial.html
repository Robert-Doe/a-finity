Section 01

The Analogy: Casting Director

Imagine a film set where every actor has a fixed role in every scene. There is no improv: the casting sheet is law.

The Casting Sheet

In each function-call "scene," the Casting Director (the calling convention) assigns:

  • rdi — Lead Actor (argument 0)
  • rsi — Supporting Actor (argument 1)
  • rdx — Antagonist (argument 2)
  • rcx — Comic Relief (argument 3)
  • r8 — Cameo #1 (argument 4)
  • r9 — Cameo #2 (argument 5)
  • rax — The Director's Cut (return value)

If you put the wrong actor in the wrong role — say you load argument 1 into rdx instead of rsi — the callee reads garbage. It cannot tell that you made a mistake; it just picks up whatever is in rsi. The scene plays out wrong, the movie is ruined, and the credits say "stack corruption."

The calling convention is the guarantee that both sides of the call agree on who plays which role. The System V AMD64 ABI is that casting sheet for all 64-bit Linux (and macOS) C programs.

Break It and You Get

Mismatched register assignments → wrong argument values → undefined behavior → segfault or silent wrong answer. The CPU never detects the error; only the wrong output tells you something went awry.

Section 02

The System V AMD64 Register Map

Here is the full argument-and-return register table you need to memorise:

RegisterRoleSave class
rdiInteger argument 0Caller-saved
rsiInteger argument 1Caller-saved
rdxInteger argument 2Caller-saved
rcxInteger argument 3Caller-saved
r8Integer argument 4Caller-saved
r9Integer argument 5Caller-saved
raxReturn valueCaller-saved

There are two classes of general-purpose register in the ABI:

Caller-Saved Registers

rax, rcx, rdx, rsi, rdi, r8, r9, r10, r11

The callee is free to overwrite these at any time. If the caller needs the values across a call, it must save them itself (on the stack) before the call and reload them after.

Callee-Saved Registers

rbx, r12, r13, r14, r15, rbp, rsp

The callee promises to restore these before returning. If a function wants to use rbx, it must push rbx at the top and pop rbx before ret. The caller can leave values in these registers across any function call.

In Module 12, our code generator only needs to use the argument registers and rax — it loads arguments from stack slots into rdi/rsi/rdx, emits call, and stores rax into the destination slot. The callee-saved registers matter more in Module 13 (Register Allocator), where we start keeping live values in registers across calls.

Section 03

Stack Frame Layout

Every function we compile uses a standard frame layout. Here is an ASCII diagram showing what the stack looks like during a function's execution:

  High addresses (older frames above)
  ┌─────────────────────────┐
  │   ... caller's frame    │
  ├─────────────────────────┤  ← rbp + 16  (arg 7+ if > 6 args)
  │   return address        │  ← rbp + 8
  ├─────────────────────────┤
  │   saved old rbp         │  ← rbp + 0   (rbp points HERE)
  ├─────────────────────────┤
  │   local variable a      │  ← rbp - 8
  ├─────────────────────────┤
  │   local variable b      │  ← rbp - 16
  ├─────────────────────────┤
  │   local variable c      │  ← rbp - 24
  ├─────────────────────────┤
  │   (padding if needed)   │
  └─────────────────────────┘  ← rsp  (grows downward)
  Low addresses

Prologue sequence (what we emit at the top of every function):

push    rbp         ; save caller's base pointer
mov     rbp, rsp   ; set our base pointer
sub     rsp, N     ; reserve N bytes for locals (N = 8 * n_locals, 16-byte aligned)

Epilogue sequence:

add     rsp, N     ; release local storage
pop     rbp         ; restore caller's base pointer
ret                 ; pop return address and jump there
16-Byte Alignment Requirement

The System V AMD64 ABI requires that rsp be 16-byte aligned immediately before any call instruction. A call pushes an 8-byte return address, so at function entry rsp % 16 == 8. After push rbp, rsp % 16 == 0. We must ensure our sub rsp, N keeps rsp 16-byte aligned. If N is already a multiple of 16, we are fine; otherwise we round up. Violating this rule causes a segfault inside printf or any SSE-heavy library function.

Section 04

From IR_PARAM + IR_CALL to Assembly

Consider a call to clamp(x, lo, hi) — three integer arguments. Here is the sequence of IR instructions the front end emits:

; assume x is at [rbp-8], lo at [rbp-16], hi at [rbp-24]

IR_LOAD   t0, "x"     ; t0 = x
IR_LOAD   t1, "lo"    ; t1 = lo
IR_LOAD   t2, "hi"    ; t2 = hi
IR_PARAM  t0          ; first arg
IR_PARAM  t1          ; second arg
IR_PARAM  t2          ; third arg
IR_CALL   "clamp", dst=t3  ; call; result in t3
IR_STORE  "a", t3      ; a = result

Our Module 12 code generator accumulates IR_PARAM instructions into a buffer. When it hits IR_CALL, it emits the argument loads followed by the call:

; load locals into argument registers
mov     rax, qword [rbp-8]   ; load t0 (x)
mov     rdi, rax             ; → arg0
mov     rax, qword [rbp-16]  ; load t1 (lo)
mov     rsi, rax             ; → arg1
mov     rax, qword [rbp-24]  ; load t2 (hi)
mov     rdx, rax             ; → arg2

; align stack and call
push    rax                  ; 8-byte pad to maintain 16-byte alignment
call    clamp
pop     rcx                  ; discard padding

; capture return value
mov     qword [rbp-32], rax  ; store t3 → a

Notice the structure: load from slot → move to argument register → call → move from rax → store to slot. That is the entire calling convention in four steps.

Why the padding push?

At the point of our call we have already done push rbp (−8) and sub rsp, N. The padding push rax adds another −8 so that rsp % 16 == 0 immediately before call pushes the return address. The pop rcx after restores the balance. The value of rax is overwritten by call's return, so it is safe to use as throwaway padding.

Section 06

Brain Exercise

🧠

The Seventh Argument

Our clamp function takes 3 arguments — they fit comfortably in rdi, rsi, rdx.

Question: What if you called a C function with 7 arguments? The first 6 go in the six argument registers — but where does the 7th argument go?

Reveal the Answer

The 7th argument (and any beyond) is pushed on the stack by the caller, in right-to-left order (so argument 7 is pushed first if there are more). The callee finds it at [rbp+16] (argument 6 would be at [rbp+16], argument 7 at [rbp+24], etc. — above the return address and saved rbp).

We do not implement stack-passed arguments in Module 12. Supporting them requires the caller to compute how many bytes of stack args to push, align the stack correctly accounting for those pushes, and have the callee know their offsets above rbp. GCC handles this automatically. We skip it here for clarity.

Section 07

Q & A

Q: Why does rsp need to be 16-byte aligned before a call?
The x86-64 System V ABI mandates 16-byte stack alignment at every call instruction. SSE and AVX instructions (used internally by many standard library functions, including printf) require 16-byte alignment for their memory operands. If rsp is misaligned by even 8 bytes when a callee executes a 128-bit movaps or similar instruction, the CPU raises a general-protection fault — which Linux turns into a segfault. The bug can be maddeningly hard to find because the crash happens deep inside printf, not at the misaligned call.
Q: What is a "callee-saved" register?
A callee-saved (or "non-volatile") register is one that a function (the callee) must preserve across its execution. If the callee wants to use rbx, it must push rbx at the start and pop rbx before ret. The caller is therefore guaranteed that rbx, r12–r15, rbp, and rsp hold the same values after a call as they did before. Caller-saved registers (rax, rcx, rdx, rsi, rdi, r8–r11) may be freely clobbered by the callee — the caller must save them itself if it needs them later.
Q: Why do we save incoming parameters to stack slots immediately on function entry?
Because rdi, rsi, and rdx are caller-saved registers. The moment our function makes any nested call (even a call to clamp in main), those registers are overwritten with the new arguments. If we kept the original parameter values only in rdi/rsi/rdx, they would vanish on the first nested call. Writing them to named stack slots ([rbp-8], [rbp-16], etc.) immediately in the prologue means we can always reload them from a stable location, no matter how many nested calls the function makes.
Q: Why does our compiler only support 6 arguments?
The System V AMD64 ABI provides exactly 6 integer argument registers: rdi, rsi, rdx, rcx, r8, r9. Arguments 7 and beyond must be pushed on the stack by the caller in reverse order, and the callee must access them at positive offsets from rbp (above the saved rbp and return address). Implementing this correctly requires tracking how many bytes of stack arguments exist in both the caller's codegen (to push them and align the stack) and the callee's codegen (to compute the right offsets). We omit this for clarity. Every real function we compile in the tutorial needs at most 4 arguments.

Sample Program: clamp

This is the C program used throughout Module 12. The compiler reads it, generates IR, and emits the assembly shown in Section 05.

int clamp(int x, int lo, int hi) {
    if (x < lo) { return lo; }
    if (x > hi) { return hi; }
    return x;
}

int main(void) {
    int a; int b; int c;
    a = clamp(0 - 3, 0, 10);  // → clamp(-3,0,10) = 0
    b = clamp(15, 0, 10);      // → clamp(15,0,10) = 10
    c = clamp(5, 0, 10);       // → clamp(5,0,10)  = 5
    return a + b + c;           // → 0 + 10 + 5 = 15
}
