MODULE 10 / 16

x86-64 Code Generation

Turning your optimized IR into real NASM assembly that a CPU can execute.

1. Meet the Camera Crew

The Analogy: Think of your IR as a shot list — a director's precise plan for every scene: "close-up on the actor's face," "pan left," "cut to the window." The shot list is abstract. Now a camera crew arrives and actually films each shot. They translate each abstract instruction into physical actions: which camera, which lens, which angle, which reel.

The code generator is the camera crew. The IR instructions are the shot list. The CPU is the camera — it only understands very specific commands. A real film camera doesn't know what "dramatic scene" means; it just records light. A real CPU doesn't know what "add two numbers" means in the abstract — it knows add rax, [rbp - 8].

In this module we write codegen.c: it walks every IRInstr in every IRFunc and emits the corresponding NASM x86-64 assembly instructions to a text file.

Source → Lexer → Parser → Sema → IR → Opt → CodeGen → NASM .asm

2. What is NASM?

NASM (Netwide Assembler) is a free, portable assembler for x86 and x86-64. It takes a text .asm file — which is almost 1:1 with raw machine instructions — and produces an ELF object file (.o) that the linker (ld or gcc) can turn into an executable.

The two-step process after our compiler runs:

# Step 1: Assemble (NASM text → ELF object)
nasm -f elf64 sample.asm -o sample.o

# Step 2: Link (ELF object → executable)
gcc -no-pie sample.o -o sample_bin

# Run it!
./sample_bin
echo "exit: $?"
Tip: On Windows, install NASM inside WSL (Windows Subsystem for Linux): sudo apt install nasm gcc. Then run make assemble from the WSL terminal inside module_10/.

3. The Stack Frame

Our code generator uses the simplest possible strategy for storing values: everything goes on the stack. Each IR temporary ti and each named local variable gets its own 8-byte slot.

For the add function in sample.c, the frame looks like this after the prologue:

Higher addresses ┌─────────────────────────────────┐ │ return address │ ← pushed by `call add` ├─────────────────────────────────┤ rbp → │ saved rbp │ ← pushed by `push rbp` ├─────────────────────────────────┤ rbp - 8 │ t0 (temp 0) = 3 │ rbp - 16 │ t1 (temp 1) = 4 │ rbp - 24 │ t2 (t0 + t1) = 7 │ │ ... more temp slots ... │ ├─────────────────────────────────┤ │ local 'a' (param) = 3 │ ← named var slots │ local 'b' (param) = 4 │ start at rbp - 2056 └─────────────────────────────────┘ rsp → (bottom of frame) Lower addresses

The formula is simple:

  • Temporary t_i lives at [rbp - (i+1)*8]
  • Named local slot j lives at [rbp - (256 + j + 1)*8]

Yes, we reserve 256 temp slots even if we only use 3. That wastes stack space, but it keeps the logic dead simple. Real compilers compute the exact live range of each temp and pack slots tightly — that's register allocation, a topic for a later module.

4. Function Prologue & Epilogue

Every function generated by our compiler starts with a prologue that sets up the stack frame, and ends with an epilogue that tears it down.

PhaseAssemblyPurpose
Prologuepush rbpSave caller's frame pointer
mov rbp, rspOur frame pointer = current stack top
sub rsp, NReserve N bytes for locals & temps
Epiloguemov rsp, rbpDiscard our locals (restore rsp)
pop rbpRestore caller's frame pointer
retJump back to caller

We emit these at the start and end of every function. The N in sub rsp, N is rounded up to a multiple of 16 bytes to keep the stack 16-byte aligned, as required by the System V AMD64 ABI.

6. The System V AMD64 ABI — How Functions Talk to Each Other

When two functions call each other they need to agree on: how to pass arguments, where to find the return value, and which registers each side is allowed to clobber. This agreement is the Application Binary Interface (ABI).

On Linux x86-64, the System V AMD64 ABI says:

PurposeRegisters
First 6 integer/pointer argumentsrdi, rsi, rdx, rcx, r8, r9
Return valuerax
Caller-saved (caller must preserve if needed)rax, rcx, rdx, rsi, rdi, r8–r11
Callee-saved (callee must restore)rbx, rbp, r12–r15
Stack alignment at call16-byte aligned

Our code generator handles the first 6 arguments only (enough for educational programs). For add(3, 4): 

; Before calling add(3, 4):
mov rax, 3          ; load arg 1
mov rdi, rax        ; put in first arg register
mov rax, 4          ; load arg 2
mov rsi, rax        ; put in second arg register
call add            ; call the function
; After the call, rax holds the return value (7)
mov [rbp - 24], rax ; spill return value to temp slot

7. What Does sample.c Compile To?

Here is the input:

int add(int a, int b) {
    return a + b;
}

int main(void) {
    int x;
    x = add(3, 4);
    return x;
}

And here is the assembly our compiler emits (slightly trimmed for clarity):

; Generated by my_compiler Module 10 code generator
bits 64
section .text

global add
add:
    push rbp
    mov rbp, rsp
    sub rsp, 2064           ; frame for temps + locals

    ; Spill parameters from registers to stack
    mov [rbp - 2064], rdi   ; param 'a'
    mov [rbp - 2072], rsi   ; param 'b'

    ; LOAD a → t0
    mov rax, [rbp - 2064]
    mov [rbp - 8], rax

    ; LOAD b → t1
    mov rax, [rbp - 2072]
    mov [rbp - 16], rax

    ; ADD t2 = t0 + t1
    mov rax, [rbp - 8]
    add rax, [rbp - 16]
    mov [rbp - 24], rax

    ; RETURN t2
    mov rax, [rbp - 24]
    mov rsp, rbp
    pop rbp
    ret

global main
main:
    push rbp
    mov rbp, rsp
    sub rsp, 2064

    ; ICONST t0 = 3
    mov rax, 3
    mov [rbp - 8], rax

    ; ICONST t1 = 4
    mov rax, 4
    mov [rbp - 16], rax

    ; PARAM t0 → rdi
    mov rax, [rbp - 8]
    mov rdi, rax

    ; PARAM t1 → rsi
    mov rax, [rbp - 16]
    mov rsi, rax

    ; CALL add → t2
    call add
    mov [rbp - 24], rax

    ; STORE t2 → local 'x'
    mov rax, [rbp - 24]
    mov [rbp - 2064], rax

    ; LOAD x → t3
    mov rax, [rbp - 2064]
    mov [rbp - 32], rax

    ; RETURN t3
    mov rax, [rbp - 32]
    mov rsp, rbp
    pop rbp
    ret

section .note.GNU-stack noalloc noexec nowrite progbits
Note: The constant folding pass in Module 09 can fold add(3, 4) calls only when the entire expression is constant — function calls are not folded since they may have side effects. The IR still contains the call. The optimizer does fold simple arithmetic like 3 + 4 when both operands are constants in the same function.

8. Brain Exercise

🧠 Think About It

When main calls add(3, 4), the arguments 3 and 4 are passed in registers rdi and rsi respectively.

Question: What register holds the return value of add when it returns to main? And what is the very next assembly instruction that our code generator emits to preserve that value?

Answer:
The return value lives in rax — this is the System V AMD64 ABI rule: integer return values go in rax.

The very next instruction emitted after call add is:
mov [rbp - 24], rax

This spills the return value from rax into the destination temporary's stack slot (t2 at rbp - 24). Why do we spill it immediately? Because rax is a caller-saved register — the next instruction or function call could overwrite it. Once it's on the stack, it's safe until we explicitly load it.
🧠 Think About It

We emit cqo before every idiv.

Question: What does cqo do, and what would happen if we forgot it?

Answer:
cqo (Convert Quadword to Octaword) sign-extends rax into rdx:rax, forming a 128-bit signed dividend for idiv.

If you forget it, rdx contains whatever garbage was left from the previous instruction. For small positive values this may still give the right answer (if rdx happens to be zero), but for negative numbers or after certain operations rdx will be nonzero, making the 128-bit dividend completely wrong. Worse: if rdx is sufficiently large, idiv can trigger a divide exception (signal SIGFPE), crashing your program.
