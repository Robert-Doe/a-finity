1. Meet the Film Editor

Imagine you have just finished shooting a film. You hand the raw footage to your editor. The script says what should happen; the raw footage is your IR. But the director (you, the programmer) left in a lot of rough material:

  • Quick shots that could be one shot — a camera cut to an actor picking up a pen, then a cut where the pen value is already known. Why cut away at all? This is constant folding: compute the result now, not at screening time.
  • Scenes after a hard cut to credits — the director yelled "CUT!" (an unconditional jump), but the camera kept rolling for five more seconds. Nobody will ever see those frames. This is dead-code elimination: throw away unreachable instructions.
  • Continuity issues — in one scene the prop is called "the red briefcase" and in the next it becomes "the case." The editor notices they are the same object and uses one consistent name throughout. This is copy propagation: replace a temporary alias with the original.

The editor does not reshoot anything. She just rearranges and trims what already exists. That is exactly what our optimizer does: it rewrites the IR in place, instruction by instruction, without changing what the program means.

2. A Quick IR Refresher

From Module 08 you know that the IR is a singly-linked list of IRInstr nodes. Each instruction has an opcode, up to two source temporaries (src1, src2), a destination temporary (dst), and an optional integer literal (ival) or string name (name).

The instructions that matter most for optimization are:

Instruction Meaning Relevant pass
tN = ICONST v Load the integer constant v into temporary tN Constant folding (source & result)
tN = ADD tA tB tN = tA + tB Constant folding (fold if tA and tB are known)
tN = COPY tA tN = tA (just a rename) Copy propagation (replace later uses of tN with tA)
JUMP L5 Go to label L5 unconditionally Dead-code elimination (instructions after this are dead)
LABEL L5 Branch target Dead-code elimination (ends the dead zone)

3. Pass 1: Constant Folding

Goal: if both operands of an arithmetic instruction are compile-time constants, compute the answer at compile time and replace the instruction with a single ICONST.

The Algorithm

We maintain a small array indexed by temporary number:

int  is_const[MAX_TEMPS];   /* 1 if this temp has a known constant value */
long const_val[MAX_TEMPS];  /* the value, when is_const is 1 */

Then we make one forward pass through the instruction list:

for each instruction in:
  if in.op == IR_ICONST:
      is_const[in.dst] = 1
      const_val[in.dst] = in.ival

  else if in.op is arithmetic AND
          is_const[in.src1] AND is_const[in.src2]:
      result = compute(in.op, const_val[in.src1], const_val[in.src2])
      rewrite in to:  IR_ICONST  dst=in.dst  ival=result
      is_const[in.dst] = 1
      const_val[in.dst] = result

  else if in writes in.dst:
      is_const[in.dst] = 0   /* runtime value — we don't know it */

Before and After for a = 3 + 4

BEFORE FOLDING
  t0 = ICONST 3
  t1 = ICONST 4
  t2 = ADD t0 t1
  STORE a = t2
AFTER FOLDING
  t0 = ICONST 3
  t1 = ICONST 4
  t2 = ICONST 7  ← folded!
  STORE a = t2

Notice that t0 and t1 are still in the list — constant folding only rewrites the binary instruction itself. The now- unused ICONST instructions for 3 and 4 are harmless; a later "dead store" pass (not in this module) could remove them.

Key insight: we do not need to remove the old ICONST instructions for the optimization to be correct. The code generator will simply never use t0 or t1 because nothing reads them after folding.

4. Pass 2: Dead-Code Elimination After Unconditional Jumps

Goal: remove instructions between an IR_JUMP and the next IR_LABEL — they can never be reached.

Why Does This Happen?

Consider an if statement without an else clause:

if (x < 10) {
    return 0;
}

The IR generator emits this as:

  JUMPZ t_cond L1          ; skip if condition is false
  t_ret = ICONST 0
  RETURN t_ret
  JUMP L2                  ← unconditional jump to merge point
  LABEL L1                 ← else label (merge)
  ...
  LABEL L2                 ← end label

After the RETURN there is a JUMP L2. The instructions between that JUMP and LABEL L1 are dead. In this simple case there are none — but in more complex programs, especially with nested ifs, dead regions do appear.

The Algorithm

in_dead_zone = false
for each instruction in (with pointer to previous):
  if in.op == IR_LABEL:
      in_dead_zone = false   /* label ends the dead zone */
      keep instruction
  else if in_dead_zone:
      unlink and free instruction
  else:
      if in.op == IR_JUMP:
          in_dead_zone = true
      keep instruction
BEFORE DEAD-CODE
  JUMP L2
  t9 = ICONST 0  ← dead
  t10 = ADD t9 t9  ← dead
  LABEL L2
AFTER DEAD-CODE
  JUMP L2
  LABEL L2
Limitation: this pass only handles the simple JUMP → dead instructions → LABEL pattern. It does not remove entire unreachable basic blocks (e.g., a block that has a label but no jump targeting that label). Full dead-block removal requires a control-flow graph — that comes in a later module.

5. Pass 3: Copy Propagation

Goal: when we see t2 = COPY t1, replace all subsequent uses of t2 with t1 (until t2 is re-assigned).

Why Copies Appear

Our IR generator is simple and sometimes produces a copy when it could have used the original temporary directly. Copy propagation cleans those up.

The Algorithm

sub[t] = t  for all t    /* identity: no substitution by default */

for each instruction in:
  if in.op == IR_COPY:
      resolved = sub[in.src1]   /* follow chains */
      sub[in.dst] = resolved
      in.src1 = resolved        /* rewrite copy source too */
  else:
      in.src1 = sub[in.src1]   /* apply substitution to sources */
      in.src2 = sub[in.src2]
      if in writes in.dst:
          sub[in.dst] = in.dst  /* dst is redefined — reset */
BEFORE COPY PROP
  t0 = ICONST 7
  t1 = COPY t0
  STORE a = t1
AFTER COPY PROP
  t0 = ICONST 7
  t1 = COPY t0  (src stays t0)
  STORE a = t0  ← t1 replaced

The COPY instruction itself is not removed — its source is rewritten to t0 (already was) and the use of t1 in STORE is replaced with t0. A later "dead-copy" pass (or the code generator) would notice that t1 is never read after this and could drop the COPY entirely.

6. Full Before / After: sample.c

Here is exactly what our optimizer does to the IR generated from sample.c. Pay attention to how the constant literals 3, 4, 2, 5 collapse into 7 and 10 in the main function, while square is left completely unchanged (its operand x is a runtime value, not a constant).

Function: square

BEFORE
  t0 = LOAD x
  t1 = LOAD x
  t2 = MUL t0 t1
  RETURN t2
AFTER (unchanged)
  t0 = LOAD x
  t1 = LOAD x
  t2 = MUL t0 t1
  RETURN t2

Both LOADs produce runtime values (x is a parameter); is_const is 0 for both, so the MUL cannot be folded.

Function: main

BEFORE
  t0 = ICONST 3
  t1 = ICONST 4
  t2 = ADD t0 t1
  STORE a = t2
  t3 = ICONST 2
  t4 = ICONST 5
  t5 = MUL t3 t4
  STORE b = t5
  t6 = LOAD a
  PARAM t6
  t7 = CALL square (1 args)
  STORE c = t7
  t8 = LOAD c
  t9 = LOAD b
  t10 = ADD t8 t9
  RETURN t10
AFTER
  t0 = ICONST 3
  t1 = ICONST 4
  t2 = ICONST 7   ← folded
  STORE a = t2
  t3 = ICONST 2
  t4 = ICONST 5
  t5 = ICONST 10  ← folded
  STORE b = t5
  t6 = LOAD a
  PARAM t6
  t7 = CALL square (1 args)
  STORE c = t7
  t8 = LOAD c
  t9 = LOAD b
  t10 = ADD t8 t9
  RETURN t10

The ADD for 3+4 is folded to ICONST 7. The MUL for 2*5 is folded to ICONST 10. The call to square and all the LOAD/STORE pairs remain unchanged — they depend on runtime values.

7. Brain Exercise

After constant folding turns a = 3 + 4 into a = 7, can the optimizer also fold c = square(a) into c = 49? Why or why not?

Show answer ↓

No. Even though we know at compile time that a == 7 after folding, the optimizer cannot fold the call square(a) into 49.

Here is why:

  • Our optimizer works on one function at a time (intra-procedural). It does not look inside square.
  • From the caller's point of view, a function call is a black box. The callee might modify global state, produce different results depending on hidden state, or have other side effects that we must not eliminate.
  • To fold square(7) → 49, we would need either function inlining (copy square's body into main and then fold) or inter-procedural constant propagation (analyze the call graph across function boundaries). Both are significantly more complex and are left for later modules.

This is the key boundary of local optimization: anything that crosses a function call boundary is out of scope.

8. Pass Order and Implementation Notes

Why This Order?

We run the passes in this order: fold → copy prop → dead code. Here is the reasoning:

  1. Fold first — creates new ICONST instructions. Copy propagation immediately benefits because the constants are now represented as clean ICONST temps that can be substituted directly.
  2. Copy prop second — replaces aliases with original temps, reducing the number of indirections the code generator has to deal with.
  3. Dead code last — constant folding and copy propagation never create new unreachable regions, so running dead-code elimination last catches any unreachable code that was already there in the unoptimized IR.

How to Add a New Pass

Adding a new optimization is a four-step process:

  1. Add a declaration void opt_my_pass(IRFunc *fn); in opt.h.
  2. Implement the pass with a linear scan in opt.c.
  3. Call it from opt_all in the right position.
  4. Test it with a sample program designed to trigger the pattern.
The one-scan rule: each pass in this module makes exactly one forward pass through the instruction list. This keeps the time complexity of each pass at O(N) where N is the number of instructions. Even running all three passes is only O(3N) = O(N).

The IR_MAX_TEMPS Limit

The constant-folding and copy-propagation passes use fixed-size arrays of size IR_MAX_TEMPS = 1024. If you compile a very large function that allocates more than 1024 temporaries, those arrays are too small and the optimization silently skips temps beyond the limit. For this course, functions stay well under that limit. A production optimizer would use dynamically-sized arrays.

What We Are Not Doing (Yet)

Missing optimization Why not in Module 09
Common subexpression elimination Requires hashing or value numbering — covered in a later module
Strength reduction (replace * with shifts) Architecture-specific — better handled in code generation
Loop invariant code motion Requires loop detection and a control-flow graph
Function inlining Requires inter-procedural analysis and a call graph
Dead-store elimination Requires liveness analysis (backward data flow)

Each of these is a genuine compiler optimization used in production compilers like GCC and LLVM. We add them incrementally in later modules once we have the data structures to support them.
