Module 03 — Symbol Table

Remembering what names mean — variables, functions, and where they live.

00 Before You Start

Prerequisites:   Module 01 — Source & I/O  |  Module 02 — Lexer / Tokeniser    You should know: the Source struct, the Token struct, and how to call lexer_next in a loop.
Must Know Before Continuing

The symbol table's job is to answer the question "What does this name refer to?" every time the parser or code generator needs to know. You need to understand Modules 01 and 02 because the demo in this module lexes a real source file and then scans the token stream to populate the table.

You should also know that at this stage we are building a flat, scope-unaware table on purpose. You will see the scope problem clearly in Section 03 — and the solution arrives in Module 07.

01 The Big Analogy — The Casting Director's Binder

Imagine a film production. The Casting Director keeps a physical binder with one tab per actor. Each tab records: the actor's name, their role type (lead / extra), and their dressing room number so the production assistant can find them quickly.

When the director says "Get me the actor playing Alice", the casting director does not re-read the entire script — she flips to the A section of the binder and reads off: Alice — Lead — Dressing Room 12.

Head First Moment

Your symbol table is that binder. Every time the compiler sees a declaration like int result;, it adds a tab: name = result, kind = VAR, dressing-room-number = −8 (its offset in the stack frame). Later, when the code generator needs to emit an instruction that reads result, it opens the binder and looks up result to find where it lives.

Here is what the binder looks like for sample.c:

NameKindOffset / Params
add FUNCparams = 2
a VAR offset = −8
b VAR offset = −16
main FUNCparams = 0
resultVAR offset = −8

02 The Symbol Struct

typedef struct {
    char    name[64];  /* null-terminated identifier, max 63 usable chars  */
    SymKind kind;      /* SYM_VAR or SYM_FUNC                              */
    int     offset;    /* VAR: bytes below frame pointer; FUNC: param count */
} Symbol;
FieldMeaning
name[64] The identifier as a null-terminated C string. 64 bytes are embedded directly in the struct so no heap allocation is needed. Names longer than 63 characters are truncated (rare in practice).
kind SYM_VAR for variables declared with int; SYM_FUNC for function names. Module 07 will add SYM_TYPE for user-defined types.
offset Dual-purpose field. For SYM_VAR: the byte distance from the frame pointer to where the variable lives on the stack (negative because the stack grows downward). For SYM_FUNC: the number of parameters the function declares. In Module 07 this becomes a proper Type * field.

Why the 64-character limit?

Embedding char name[64] directly in the struct means the entire SymTab is one contiguous block of memory — no pointer chasing, no heap fragmentation, excellent cache locality. The C99 standard requires implementations to support at least 63 significant characters for internal identifiers, so 64 bytes (63 usable + null terminator) meets the spec for the programs in this course. A production compiler uses an identifier intern table and stores only a pointer, removing the length limit entirely.

03 The Scope Problem (Preview)

Consider this program with two functions that each declare a local variable named i:

function_a

int function_a(void) {
    int i;
    i = 10;
    return i;
}

function_b

int function_b(void) {
    int i;
    i = 99;
    return i;
}

These two i variables are completely independent — they live at different stack offsets in different stack frames. Yet our flat SymTab treats them as the same name. The second call to symtab_add("i", ...) will return -1 because a symbol named i already exists.

This Is Intentional

We are building the flat table knowing it is wrong for nested scopes. The flat table is correct for the very simple programs we compile in Modules 03–06 (single-function programs with unique names). Module 07 replaces it with a scope stack: a stack of SymTab instances, one per block. symtab_add pushes into the top frame; symtab_lookup searches from top to bottom, finding the innermost binding. Building the flat version first means you understand exactly what problem the scope stack solves.

04 Adding and Looking Up Symbols

symtab_add

int symtab_add(SymTab *st, const char *name, SymKind kind, int offset)
{
    /* reject if at capacity */
    if (st->count >= SYMTAB_MAX) return -1;

    /* linear scan for duplicate names */
    for (int i = 0; i < st->count; i++) {
        if (strcmp(st->entries[i].name, name) == 0)
            return -1;  /* already exists */
    }

    /* insert at the next free slot */
    Symbol *sym = &st->entries[st->count];
    strncpy(sym->name, name, sizeof(sym->name) - 1);
    sym->name[sizeof(sym->name) - 1] = '\0'; /* force null termination */
    sym->kind   = kind;
    sym->offset = offset;

    return st->count++;  /* return index of the new entry */
}

The return value is the index of the new entry, or -1 on failure. Callers check for -1 to detect redeclaration errors.

symtab_lookup

Symbol *symtab_lookup(SymTab *st, const char *name)
{
    for (int i = 0; i < st->count; i++) {
        if (strcmp(st->entries[i].name, name) == 0)
            return &st->entries[i];  /* found — return pointer into array */
    }
    return NULL;  /* not found */
}

The returned pointer points directly into the SymTab.entries array. It is valid until the next call to symtab_add (which may shift nothing, since we only append) and until the SymTab itself goes out of scope. Do not free it.

Typical usage pattern

SymTab st;
symtab_init(&st);

/* add a variable declared as: int result; */
int idx = symtab_add(&st, "result", SYM_VAR, -8);
if (idx < 0) {
    fprintf(stderr, "error: 'result' already declared\n");
}

/* later: look up result to find its stack offset */
Symbol *sym = symtab_lookup(&st, "result");
if (sym == NULL) {
    fprintf(stderr, "error: 'result' undeclared\n");
} else {
    printf("result lives at offset %d\n", sym->offset);
    /* prints: result lives at offset -8 */
}

05 Why No Hash Table Yet

Linear scan is O(n). For a table with 50 symbols, the worst case is 50 comparisons. At 10 MHz of function calls per second, 50 comparisons takes 5 microseconds — completely invisible. So why do production compilers use hash tables?

Consider a large C++ file with 50,000 declarations and 1,000,000 name references. With linear scan, name resolution alone takes 50,000 × 1,000,000 / 2 ≈ 25 billion comparisons. With a hash table it is roughly 1,000,000 comparisons. That is the difference between seconds and milliseconds.

What a Hash Table Would Need

To replace the linear array with a hash table you would need:

  • A hash function for strings (e.g. FNV-1a, djb2).
  • A collision resolution strategy (open addressing with linear probing, or chaining with linked lists).
  • A resize/rehash policy when the load factor exceeds a threshold (typically 0.7).
  • An iterator that visits all entries in insertion order (for symtab_dump).

That is easily 150 lines of carefully tested code. At Module 03 we buy simplicity by paying O(n) lookup. The DECISIONS.md file records this trade-off explicitly.

07 Brain Exercise

Scenario

Two functions both declare a local variable called i. You call symtab_add("i", SYM_VAR, -8) for the first function, then symtab_add("i", SYM_VAR, -8) for the second function's declaration. What happens?

Show answer

The second call to symtab_add returns -1. The linear scan finds an existing entry with name == "i" and rejects the insert as a duplicate.

This is the fundamental limitation of the flat table: it cannot represent two different variables that happen to share the same name in different scopes. The flat table was correct for single-function programs, but as soon as two functions are involved, name collisions are inevitable.

This is precisely the motivation for Module 07's scope stack. With a scope stack, you push a fresh SymTab when entering a function body and pop it when leaving. Each function's i lives in its own frame, so there is never a collision.

08 There Are No Dumb Questions

Q: Why not just use a C array of strings to store the names?

A plain array of strings only stores names. We also need to know what kind of thing each name is (variable or function) and where it lives (stack offset or parameter count). The Symbol struct bundles all three pieces of information together in one record so lookup returns everything the code generator needs in a single step.

Q: What does offset mean for a function?

At Module 03, offset stores the parameter count for functions — a convenient integer that fits the field without requiring a separate field. In Module 07, when the compiler needs to call a function and set up its stack frame, offset for functions will be repurposed or replaced by a proper Type * that records the return type and parameter types. The field name is admittedly imprecise for the function case; production compilers use separate union members or a type pointer.

Q: Why linear search and not binary search?

Binary search requires the entries to be in sorted order. To keep them sorted, we would either sort the array on every insert (expensive) or sort the whole array before every lookup batch (also expensive). For a table with fewer than 50 symbols, the O(n) linear scan is faster in practice because it has no sorting overhead and fits entirely in a single cache line. Binary search starts paying off at several hundred entries — by which point you should use a hash table instead.

09 What's Next

Module 04 — Parser: Expressions

You can read tokens and remember names. Now you need to understand structure. The token stream for 3 + 4 * 2 is just five tokens in a row — it does not tell you that multiplication binds tighter than addition. The parser builds a tree that makes operator precedence explicit: the * node is a child of the + node, not a sibling.

That tree is called an Abstract Syntax Tree (AST). Every subsequent module — type checking, optimisation, code generation — works on the AST rather than on the flat token stream.
