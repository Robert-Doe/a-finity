# Module 11 — Design Decisions

## 1. Why `jz` (jump-if-zero) for IR_JUMPZ rather than `je`

`jz` and `je` are **exactly the same machine instruction** — both encode to opcode `0x74` (short) or `0x0F 84` (near).  The CPU makes no distinction.

We choose `jz` because **it conveys intent**.  `je` means "jump if equal," which implies a *comparison* between two values happened just before (e.g. `cmp rax, rbx`).  `jz` means "jump if the zero flag is set," which is the direct consequence of `test rax, rax` — we are testing whether a *single value* is zero, not comparing two things.

Using `jz` after `test rax, rax` is idiomatic, self-documenting assembly that matches exactly what IR_JUMPZ means: "jump if the value is zero (false)."

---

## 2. Why `test rax, rax` instead of `cmp rax, 0`

Both instructions set the Zero Flag identically when `rax == 0`, so either works logically.  We prefer `test rax, rax` for two reasons:

**Size:** `test rax, rax` encodes as 3 bytes (`REX.W 0x85 /r`).  `cmp rax, 0` encodes as 7 bytes (`REX.W 0x81 /7 imm32`) because the zero immediate needs a 32-bit encoding in the 64-bit form.  Shorter instructions = smaller code cache footprint.

**Convention:** `test rax, rax` is the idiomatic x86-64 way to check whether a register is zero.  Any experienced assembly programmer reading the code will recognise it immediately; `cmp rax, 0` might cause them to wonder why you didn't use the idiomatic form.

## 3. How the label namespace avoids collisions with user function names

IR labels are generated by `label_str()` in `ir.c`, which produces strings of the form `L<integer>` (e.g., `L0`, `L1`, `L42`).

In the code generator (`codegen.c`), labels are emitted as **NASM local labels** using the `.` prefix: `.L0:`, `.L1:`, etc.  NASM local labels are scoped to the nearest preceding global label — they cannot be referenced from outside the function.

Function names (`abs_val`, `sum_to`, `main`) are declared `global` and emitted *without* the `.` prefix.  Since no user function can be named `.L<something>` (dots are not valid C identifiers), the two namespaces are completely disjoint.  The compiler never needs to check for collisions because the structural difference (`.` prefix vs no prefix) enforces separation at the assembler level.

## 4. Why we emit the GNU-stack note section

```nasm
section .note.GNU-stack noalloc noexec nowrite progbits
```

On Linux with the ELF format, the kernel decides whether to make the stack executable based on hints in the program's `PT_GNU_STACK` program header.  The linker (`ld`) constructs this header by examining every input object file:

- If **all** objects have a `.note.GNU-stack` section marked non-executable, the linker marks the stack **NX** (non-executable).
- If **any** object is missing the section, the linker assumes it might need an executable stack and marks it **executable** — a significant security vulnerability that allows code-injection attacks (shellcode) to run directly on the stack.

By emitting this section in every `.asm` file we produce, we ensure our compiled code cooperates with the OS's memory protection.  This is especially important because we are generating assembly directly — without it, our binaries would have an unnecessarily permissive security posture even though our code never executes data on the stack.

## 5. How slot allocation for temps differs from slot allocation for locals

**Temps** are created by the IR generator every time a new intermediate value is needed (`new_temp()` in `ir.c`).  Each call increments `IRFunc.next_temp` and returns the next integer.  Temps are ephemeral: once a value is consumed (used as `src1`/`src2` in a later instruction), that slot could theoretically be reused — but in our simple implementation, slots are never reused.  Slot `n` lives at `[rbp - (n+1)*8]`.

**Locals** (named variables declared with `int x;`) are also allocated via `local_slot()` in `ir.c`, which calls `new_temp()` internally.  The difference is that locals are **looked up by name**: if `i` already has a slot, `local_slot("i")` returns the same slot every time.  Temps have no names and are never re-looked-up.

In `codegen.c`, the `LocalMap` structure rebuilds the name→slot mapping by scanning IR instructions in order, mirroring what `local_slot()` did during IR generation.  This avoids passing the Gen state from `ir.c` to `codegen.c`, keeping the two phases cleanly decoupled through the `IRProg` data structure.
