Section 01

The Stunt Coordinator Analogy

Picture a movie script. It says:

"If the hero fails to catch the ledge, cut to Scene 42."

That sentence is high-level intention. But on set, nobody just decides the hero fails and teleports to Scene 42. A stunt coordinator builds the physical mechanism: a wire rig, a trapdoor, a camera cut triggered by a radio signal at the exact right moment.

Your C compiler is that stunt coordinator for if statements. The C source code is the script — it says "if x is less than zero, do this, otherwise do that." The compiler's job is to build the physical mechanism in assembly: actual labels that mark where to jump, and actual jz instructions that read a CPU flag and either take the jump or fall through.

The Central Insight

A CPU has no concept of "if." It only has: "set this flag based on the last operation, then optionally jump to this address if that flag is set."

Your compiler translates the intent of if/while into the mechanism of flags and jumps.

The key actors in this mechanism are:

  • Labels — named positions in the code (like "Scene 42").
  • Comparison instructions (cmp, test) — compute a result and set CPU flags.
  • Conditional jump instructions (jz, jl, jg, …) — read those flags and jump (or not).
Section 02

How if/while Become IR Labels and Jumps

Let's trace a simple if/else through the compiler. Start with this C code:

int abs_val(int x) {
    if (x < 0) {
        return 0 - x;
    } else {
        return x;
    }
}

After parsing and IR generation, the IR for abs_val looks like this (simplified — actual temp numbers may differ):

; Parameter x is stored at slot 0 (local named "x")
FUNC abs_val:
  STORE  x = rdi            ; save incoming parameter
  LOAD   t1 = x
  ICONST t2 = 0
  LT     t3 = t1, t2       ; t3 = (x < 0) → 1 or 0
  JUMPZ  t3, L0            ; jump to L0 (else) if t3 == 0 (condition is false)
  ; ── then branch ──
  ICONST t4 = 0
  LOAD   t5 = x
  SUB    t6 = t4, t5       ; 0 - x
  RETURN t6
  JUMP   L1               ; skip else branch
L0:                        ; else label
  LOAD   t7 = x
  RETURN t7
L1:                        ; end label
The Key Inversion

Notice that JUMPZ t3, L0 jumps to the else branch when the condition is false (zero), NOT to the then-branch when the condition is true.

This is the natural structure: the then-branch comes right after the condition check (no jump needed if true), and we use a jump to skip over it when the condition is false. Section 06 explores why irgen works this way.

Now let's look at a while loop — sum_to from our sample program:

while (i < n) {
    s = s + i;
    i = i + 1;
}

IR translation:

L2:                         ; top of loop (test label)
  LOAD   t8  = i
  LOAD   t9  = n
  LT     t10 = t8, t9      ; t10 = (i < n)
  JUMPZ  t10, L3           ; exit loop if i >= n (t10 is false/zero)
  ; ── loop body ──
  LOAD   t11 = s
  LOAD   t12 = i
  ADD    t13 = t11, t12
  STORE  s   = t13
  LOAD   t14 = i
  ICONST t15 = 1
  ADD    t16 = t14, t15
  STORE  i   = t16
  JUMP   L2               ; back to top
L3:                         ; after loop

The loop structure is: emit the test label, compute condition, jump past body if false, run body, unconditionally jump back to test, emit end label. This is exactly how C compilers have done it since the 1970s.

Section 03

From IR_JUMPZ to x86 jz — the test+jz Pattern

When the code generator sees IR_JUMPZ src1, name, it emits three x86-64 instructions:

; IR: JUMPZ t3, L0
mov  rax, qword [rbp - 32]   ; load t3 from its stack slot
test rax, rax                ; compute rax AND rax, set ZF if result = 0
jz   .L0                       ; jump if ZF is set (rax was zero)

Let's understand each instruction:

mov rax, [rbp - N]

Load the value of temp t3 from its stack slot into rax. Temp n lives at [rbp - (n+1)*8].

test rax, rax

test performs bitwise AND of its two operands and sets CPU flags based on the result, but does NOT store the result anywhere.

  • If rax == 0: result is 0, so the Zero Flag (ZF) is set to 1.
  • If rax != 0: result is non-zero, so ZF is cleared to 0.

Why not cmp rax, 0? Both set ZF identically when rax is zero. But test rax, rax is 3 bytes while cmp rax, 0 is 7 bytes (the immediate zero needs a 32-bit encoding). Shorter code fits better in the instruction cache.

jz .L0

jz (jump-if-zero) jumps to the label if ZF is set — i.e., if the last test or cmp found a zero result.

Why jz instead of je? They're the same opcode. We say jz because we're testing for zero (a boolean false), not testing for equality between two values. The word choice documents the intent.

Put together, the pattern says: "load the boolean into rax; if it's zero (false), take the jump." This is compact, idiomatic, and exactly what every C compiler for x86 does.

IR_JUMPZ t3, L0
→
mov rax, [slot]
→
test rax, rax
→
jz .L0
Section 04

Comparison Instructions — cmp + set* + movzx

Before we can branch on a condition like x < 0, we need to evaluate it and store the result (0 or 1) in a temp. The IR represents this as IR_LT dst, src1, src2. Here's how we lower it to assembly:

; IR: LT  t3 = t1, t2   (t3 = t1 < t2, as 0 or 1)
mov   rax, qword [rbp - 16]  ; load t1
cmp   rax, qword [rbp - 24]  ; compare with t2 (sets flags)
setl  al                      ; al = 1 if rax < [t2], else al = 0
movzx rax, al                 ; zero-extend byte result to 64 bits
mov   qword [rbp - 32], rax  ; store result into t3's slot

Let's break down the non-obvious parts:

cmp rax, [memory]

cmp a, b computes a - b and sets the CPU flags (Carry, Zero, Sign, Overflow) but discards the result. The flags capture the relationship between a and b.

set* al

The set* family reads the flags and writes a single byte (0 or 1) into a byte register. al is the low byte of rax. Available variants:

InstructionConditionC equivalent
setlLess than (signed)<
setgGreater than (signed)>
setleLess-or-equal (signed)<=
setgeGreater-or-equal (signed)>=
seteEqual (zero flag)==
setneNot equal!=
movzx rax, al

movzx (move with zero-extension) copies al (8 bits, value 0 or 1) into rax (64 bits), filling the upper 56 bits with zeros.

Without this step, rax might have garbage in the upper bytes, which would break subsequent arithmetic.

The full pattern for each comparison IR op:

IR Opcode

IR_LT   dst, s1, s2
IR_GT   dst, s1, s2
IR_LEQ  dst, s1, s2
IR_GEQ  dst, s1, s2
IR_EQ   dst, s1, s2
IR_NEQ  dst, s1, s2

x86-64 set* used

setl   al
setg   al

setge  al
sete   al

Section 05

Run It — Assembly Output for abs_val

After running make run, the compiler emits a sample11.asm file. Here's the annotated assembly for abs_val, showing every branch instruction in context:

global abs_val
abs_val:
    push  rbp
    mov   rbp, rsp
    sub   rsp, 128              ; reserve frame (rounded to 16 bytes)

    ; save parameter x (rdi) into its stack slot
    mov   qword [rbp - 8], rdi

    ; t1 = x
    mov   rax, qword [rbp - 8]
    mov   qword [rbp - 16], rax

    ; t2 = 0
    mov   rax, 0
    mov   qword [rbp - 24], rax

    ; t3 = (t1 < t2)  →  x < 0
    mov   rax, qword [rbp - 16]
    cmp   rax, qword [rbp - 24]
    setl  al
    movzx rax, al
    mov   qword [rbp - 32], rax

    ; JUMPZ: if condition (t3) is zero (false), jump to .L0 (else branch)
    mov   rax, qword [rbp - 32]
    test  rax, rax
    jz    .L0

    ; ── then branch: return 0 - x ──
    mov   rax, 0
    mov   qword [rbp - 40], rax
    mov   rax, qword [rbp - 8]
    mov   qword [rbp - 48], rax
    mov   rax, qword [rbp - 40]
    sub   rax, qword [rbp - 48]
    mov   qword [rbp - 56], rax
    mov   rax, qword [rbp - 56]  ; return value
    mov   rsp, rbp
    pop   rbp
    ret

    ; unconditional jump past else branch
    jmp   .L1

.L0:                           ; else branch
    mov   rax, qword [rbp - 8]
    mov   qword [rbp - 64], rax
    mov   rax, qword [rbp - 64]  ; return x
    mov   rsp, rbp
    pop   rbp
    ret

.L1:                           ; end of if/else
    ; fallthrough return 0
    xor   rax, rax
    mov   rsp, rbp
    pop   rbp
    ret
Local Labels (.L0, .L1, …)

In NASM, labels starting with . are local — they are scoped to the nearest preceding global label (abs_val in this case). This means .L0 inside abs_val and .L0 inside sum_to are completely different labels and never conflict. It's also why they can't collide with user function names, which are always declared globally without a dot.

To run the complete pipeline and see the exit code:

make assemble
# Expected output:
# exit code: 50   (abs_val(-5)=5, sum_to(10)=45, 5+45=50)
🧠 Brain Exercise

The Question:

IR_JUMPZ jumps when src1 is zero (false). But in C, an if statement executes the then-branch when the condition is true (non-zero). These are opposite!

So how does irgen bridge this gap? Why does the generated IR use JUMPZ to handle an if statement whose condition is true? Doesn't that jump in the wrong direction?

Think about it, then reveal the answer

irgen inverts the structure of the jump.

Instead of "jump INTO the then-branch when true," irgen generates "jump OVER the then-branch when false."

The then-branch is placed immediately after the condition check, so no jump is needed when the condition is true — execution just falls through. The JUMPZ is emitted to skip past the then-branch to the else label when the condition IS false (zero).

  t = condition
  JUMPZ t, Lelse      ; jump OVER then when condition is FALSE
  <then stmts>        ; reached by FALL-THROUGH when condition is TRUE
  JUMP  Lend
Lelse:
  <else stmts>
Lend:

This is the canonical pattern used by virtually every C compiler. The key insight: the then-branch never needs a jump to reach it. Only the else-branch and the end need labels, because those are positions you jump TO, not fall into.

If you tried to use "jump when true" instead, you'd need to jump into the then-branch (placing it out of order) or use a NOT instruction to flip the condition — both are more complicated and produce worse code.

Section 07

Q & A

Q1 What happens at runtime if a function has no explicit return statement? Does our compiler handle it?

In C, reaching the end of a non-void function without a return is undefined behavior. Our compiler handles it gracefully by emitting a fallthrough return at the end of every function:

xor   rax, rax   ; rax = 0 (return 0)
mov   rsp, rbp
pop   rbp
ret

This is after all IR instructions, so it's only reached if no IR_RETURN was executed. It prevents a crash, but the return value (0) is arbitrary. A production compiler would warn about this at the semantic analysis stage.

Q2 Why does the frame size get rounded up to a multiple of 16?

The System V AMD64 ABI (the Linux calling convention) requires that rsp must be 16-byte aligned immediately before any call instruction. When our function is called, push rbp decrements rsp by 8 bytes (to save the old rbp). If we then subtract an odd multiple of 8 from rsp, the result won't be aligned to 16. Rounding the frame size up to the next multiple of 16 ensures alignment is always maintained.

Misaligned rsp causes a SIGBUS (on some CPUs) or performance penalties when SSE/AVX instructions access the stack.

Q3 Could we use cmp rax, 0 + je instead of test rax, rax + jz? Would the assembly work identically?

Yes, it would produce identical runtime behavior. Both sequences:

Our approach (preferred)

test rax, rax
jz   .L0

Alternative (also correct)

cmp rax, 0
je  .L0

…set the Zero Flag identically and branch identically. We prefer test rax, rax because it's 4 bytes shorter (no 32-bit immediate needed), uses idiomatic x86 style, and the choice of jz communicates "this is a zero-test" rather than "this is an equality comparison."

Q4 What would need to change to support break and continue inside while loops?

We'd need to track the loop end label and loop test label in the code generator's context as we descend into loop bodies:

  • break → emit IR_JUMP Lend (where Lend is the label after the loop).
  • continue → emit IR_JUMP Ltest (where Ltest is the condition-check label at the top).

In irgen, this means passing lend_id and ltest_id down through the statement generator whenever we enter a while loop. In the parser, break and continue would become new AST node kinds (AST_BREAK, AST_CONTINUE). Nested loops would use a stack of label pairs.
