Module 07
Semantic Analysis

The Script Doctor who finds plot holes in your code before the audience does.

1. What Is Semantic Analysis?

Imagine a film crew that has just finished writing a storyboard — every panel drawn, every scene blocked out, every line of dialogue written down. The Script Doctor now reads the whole storyboard from start to finish, not to check spelling or grammar (that was the parser's job), but to look for plot holes:

  • "In scene 3 you reference a character named Marcus — but Marcus was never introduced!"
  • "In scene 7 you call the prop master with three requests, but the prop department only accepts two."
  • "You wrote this scene as a comedy but then killed the main character — inconsistent tone!"

The Script Doctor does not rewrite the storyboard; they just produce a list of problems. Our semantic analyser does exactly the same thing to the AST.

By the time we reach semantic analysis:

  • The source text has been tokenised (Module 03).
  • The tokens have been parsed into an AST (Modules 05–06).

The AST is syntactically valid — it has the right shape — but it may still reference names that don't exist, or call functions with the wrong number of arguments. Those are semantic errors: the structure is fine but the meaning is broken.

Key insight: The parser can tell you that x = foo(1, 2, 3); is syntactically correct (it follows the grammar). Only the semantic analyser can tell you that foo was defined to take two parameters, not three.

2. The Three Things We Verify

Our simplified language has only int variables and functions, which means we only need to verify three families of property:

2.1 Variable Declaration Before Use

Every variable (every bare name that is not a function call) must have been declared with int x; before it is read or assigned. Using an undeclared variable is the most common beginner mistake:

int main(void) {
    x = 5;  // ERROR — x was never declared
    return x;
}

2.2 Function Call Validity

Every call site must reference a known function, and the number of arguments at the call must exactly match the number of parameters in the definition:

int add(int a, int b) { return a + b; }

int main(void) {
    int r;
    r = add(1);        // ERROR — add wants 2 args, got 1
    r = mystery(1);  // ERROR — mystery is not defined
    return r;
}

2.3 No Duplicate Declarations in the Same Scope

You cannot declare the same variable name twice in the same scope:

int main(void) {
    int x;
    int x;  // ERROR — x is already declared here
    return x;
}

3. The Two-Pass Algorithm

Here is the key problem: a function might be called before it is defined in the file (think of main calling multiply which is defined further down). A single-pass walk would see the call before it has recorded the function's definition — and flag it as an error incorrectly.

We solve this with two passes over the AST:

AST_PROGRAM ↓
Pass 1: collect all function names & param counts
builds: FuncEntry funcs[] in SemaCtx
↓
Pass 2: walk each function body — check variables & calls
uses: SymTab (scope stack) + FuncEntry funcs[]

Pass 1 in code

/* In check_node for AST_PROGRAM: */
/* Pass 1 */
for (int i = 0; i < n->nargs; i++) {
    Node *fn = n->args[i];
    if (fn && fn->kind == AST_FUNC)
        register_func(ctx, fn->sval, fn->nargs);
}
/* Pass 2 */
for (int i = 0; i < n->nargs; i++)
    check_node(ctx, st, n->args[i]);

After pass 1 we know every function name and how many parameters it takes. Pass 2 can then validate call sites from any function, regardless of source order.

4. Tracking Variables with a Scope Stack

Variables in C are scoped: a variable declared inside an if block is not visible outside it. We track this with a scope stack:

  • Entering a function → push a parameter scope, seed it with parameter names.
  • Entering a block { } → push a new scope.
  • Seeing int x; → define x in the current (top) scope.
  • Seeing a bare name x → lookup from the top scope downward.
  • Leaving a block → pop its scope; all names in it vanish.
/* symtab.h API */
void symtab_push_scope(SymTab *st);          // open a new level
void symtab_pop_scope (SymTab *st);          // close the current level
int  symtab_define   (SymTab *st, const char *name); // 0=duplicate
int  symtab_lookup   (SymTab *st, const char *name); // 0=not found
Why two scopes per function?
The parameter scope is pushed before entering the body block. The body block's { } then pushes a second scope on top. This means a local variable with the same name as a parameter is a duplicate in the inner scope — which is exactly what C compilers report.

5. Walking the AST — Node by Node

The central function is check_node(ctx, st, n). It is a big switch on n->kind. Here are the interesting cases:

AST_IDENT — bare variable reference

case AST_IDENT:
    if (!symtab_lookup(st, n->sval))
        SEMA_ERR(ctx, n->line,
                 "'%s' used before declaration", n->sval);
    break;

AST_CALL — function call

case AST_CALL: {
    FuncEntry *fe = lookup_func(ctx, n->sval);
    if (!fe) {
        SEMA_ERR(ctx, n->line,
                 "call to undefined function '%s'", n->sval);
    } else if (n->nargs != fe->nparams) {
        SEMA_ERR(ctx, n->line,
                 "'%s' called with %d args but defined with %d",
                 n->sval, n->nargs, fe->nparams);
    }
    check_args(ctx, st, n->args, n->nargs); // still check args
    break;
}

AST_BLOCK — new scope

case AST_BLOCK:
    symtab_push_scope(st);
    check_args(ctx, st, n->args, n->nargs);
    symtab_pop_scope(st);
    break;

6. Running the Samples

Clean program: sample.c

int multiply(int a, int b) {
    return a * b;
}

int main(void) {
    int x;
    int result;
    x = 6;
    result = multiply(x, 7);
    if (result > 40) {
        return result;
    } else {
        return 0;
    }
}
$ ./sema sample.c
semantic check passed

Broken program: sample_bad.c

int foo(int a) {
    return b;         // ERROR: b is not declared
}

int main(void) {
    int x;
    x = foo(1, 2);   // ERROR: foo takes 1 arg, not 2
    return y;         // ERROR: y is not declared
}
$ ./sema sample_bad.c
sema error: 'b' used before declaration (line 2)
sema error: 'foo' called with 2 args but defined with 1 (line 7)
sema error: 'y' used before declaration (line 8)
3 semantic errors

Notice that we found all three errors in one run. We didn't stop after the first one.

7. Brain Exercises

Brain Exercise 1 — Duplicate function names

What happens if two functions in the same file have the same name?

int add(int a, int b) { return a + b; }
int add(int x)         { return x + 1; }

In Pass 1, register_func checks the function table before inserting. If the name already exists it prints:

sema error: function 'add' defined more than once

The first definition's parameter count stays in the table. This means call sites checked in Pass 2 are validated against the first definition. A production compiler would also mark the original definition's location in the error — a useful improvement for a later module.

Brain Exercise 2 — Nested blocks

Consider this code:

int main(void) {
    int x;
    x = 10;
    if (x > 5) {
        int y;   // y is only visible inside this if-block
        y = x + 1;
    }
    return y;  // ERROR — y is out of scope here
}

Draw the scope stack at each point and trace through symtab_lookup. Why does the lookup for y in the return statement fail?

Answer: when the if-block's AST_BLOCK node is processed, its scope is pushed, y is defined, and then the scope is popped before returning to the outer level. When the return y statement is checked, the stack only contains the outer scopes where y was never defined.

8. Questions & Answers

Why don't we stop at the first error?
Because fixing one error, recompiling, finding the next error, and repeating is exhausting. We want to hand the programmer a complete list. The cost is that some later errors may be caused by an earlier one (e.g. if x is undeclared, every use of x will also error), but that's a small price for seeing everything at once.
What if a function has no return statement? Do we catch that?
Not in this module. Verifying that every execution path through a function reaches a return requires building a control-flow graph — that's a bigger analysis step we save for a later module. For now, if a function falls off the end, the compiler silently allows it (just like early versions of C).
Why does the scope stack push twice per function (once for parameters, once for the body block)?
The AST_BLOCK handler always pushes a scope when it enters a block. The body { } is an AST_BLOCK, so it pushes one level. But parameters must be visible inside that block, so they need to live in an enclosing scope. We push a parameter scope in AST_FUNC before walking the body, giving parameters a scope that wraps the body scope.
Could we add type checking later without rewriting sema.c?
Yes. The logical extension is to attach a Type field to each Node and fill it in during the semantic walk (type synthesis). Then binary-expression nodes can verify that both operands have compatible types (type checking). The walk structure in check_node would stay the same; we'd just add type propagation logic inside each case. That is planned for when we add pointers.
